## 1. 목표
v0.1~v0.8로 완성된 스캔→요약→위키→인덱싱→그래프→검색 파이프라인을 **브라우저 GUI**로 쓸 수
있게 한다. 개발자가 `pip install git+https://…` 로 설치하고 `corpbrain gui` 를 실행하면 로컬
서버가 뜨고 브라우저에서 화면 6개를 쓴다. GUI 서버는 CLI와 **동급의 얇은 어댑터**이며 코어에
비즈니스 로직을 더하지 않는다. 신규 런타임 의존성은 **0개**이고 외부 통신 규칙(로컬 Ollama와
옵트인된 Anthropic 외 0)은 그대로 유지된다. [사용자 결정]

  축(어떤 프로젝트에서 일할 것인가)을 이번에는 만들지 않는다.** 워크스페이스는 `--out` 하나다.

## 3. 완료의 정의
검증 방식(전반) [사용자 결정]: **API 계층은 자동 테스트, 화면은 수동 스모크**로 가른다.
GUI 서버는 CLI와 동급 어댑터이므로 이 저장소의 기존 잣대를 그대로 댄다 — 표시 로직은 순수
함수 단위테스트, 어댑터는 상태코드와 배선. 프론트엔드는 자동 판정하지 않으며 `docs/SMOKE.md`
시나리오로 사람이 확인한다.

**테스트 배치** [TH6 · 사용자 결정]: 기존 **성격별 분류 축**을 그대로 따르고 새 디렉터리·
`conftest.py`를 만들지 않는다.

| 대상 | 위치 |
|---|---|
| 순수 함수 (`handle()` · `format_sse()` · 위키 파서) | `tests/unit/test_gui_*.py` |
| 서버 ↔ 코어 배선 · 상태코드 | `tests/test_gui.py` · `tests/test_gui_*.py` (CLI 관용구와 대칭) |
| `bind` 불변식 | `tests/security/test_network_invariant.py` (기존 파일) |
| 코어 변경(취소 훅 · 그래프 이벤트 · `iter_edges()`) | `tests/unit/` · `tests/integration/` 기존 자리 |

`tests/gui/` 디렉터리는 만들지 않는다 — 분류 축이 「성격별」과 「기능별」 둘로 섞이고, CLI는
평면인데 GUI만 디렉터리가 되는 비대칭이 생긴다.

1. 모든 HTTP 엔드포인트(§4.3)가 기대 JSON 본문과 상태코드를 낸다.
   - 검증: **요청 처리 순수 함수를 직접 호출**하는 테스트로 단언한다(§4.10.3). 브라우저를
     띄우지 않으며 대부분의 케이스에서 소켓도 열지 않는다.
2. 토큰 없는 요청이 **401**, 허용되지 않은 `Origin`·`Host` 헤더를 가진 요청이 **403**이다.
   - 검증: 헤더를 달리한 요청 **5종**(토큰 없음 / 잘못된 토큰 / 잘못된 `Origin` / 잘못된 `Host` /
     **`Origin` 없는 POST**)이 401·403인지, 그리고 **`Origin` 없는 GET은 통과**하는지를 함께
     단언한다 — §4.2의 메서드별 규칙이 양방향으로 고정된다. 마지막 하나가 없으면 「전부 403」
     구현이 테스트를 통과하면서 첫 화면을 막는다.
3. **네트워크 불변식** — 서버가 여는 듣는 소켓의 바인드 주소가 `127.0.0.1`뿐이다.
   - 검증: `tests/security/test_network_invariant.py`의 `SocketWatcher`를 **`bind`까지 감시하도록
     넓히고** 같은 파일에 케이스를 추가한다 [TH2 · 사용자 결정]. 새 파일로 분리하지 않는다 —
     소켓 패치 관용구가 복제되고, 감시장치가 공허하게 통과하지 않음을 증명하는
     `test_watcher_flags_a_gateway_bypass`의 보호를 받지 못한다(v0.6·v0.7·v0.8 결정 계승).
   - **현재 감시장치로는 이 항목을 측정할 수 없다** — `watch_sockets`는
     `socket.socket.connect`와 `socket.create_connection`만 패치해 **나가는 연결만** 본다.
     `bind` 기록을 더하는 것이 이 항목의 선행 작업이다.
   - 패치한 `bind`는 **주소를 기록한 뒤 원래 `bind`에 그대로 넘긴다**(pass-through).
     [제안 후 승인 · 2026-08-27 정정]
     - 초판은 「기록하고 **가로챈다**(실제로 바인드하지 않는다)」로 적었으나 그러면 안 된다.
       `ThreadingHTTPServer`는 `server_bind()` 직후 `server_activate()`에서 `listen()`을 부르고,
       **바인드되지 않은 TCP 소켓에 `listen()`을 걸면 커널이 `0.0.0.0`의 임의 포트로 자동
       바인드한다.** 「듣는 소켓은 127.0.0.1뿐」을 단언하려는 테스트가 오히려 전 인터페이스에
       소켓을 여는 셈이 되고, `server_address`도 `('0.0.0.0', 0)`이 되어 서버 객체가 일관되지
       않은 상태로 남는다.
     - 가로채기를 택했던 근거는 「같은 fixture의 `connect` 차단과 부딪치지 않게」였는데,
       `bind`는 `connect`가 아니라 **애초에 부딪치지 않는다.** 실제로 바인드한 뒤 즉시
       `server_close()` 하면 나가는 연결이 하나도 생기지 않는다.
   - 상수만 단언하는 방식(`HOST == "127.0.0.1"` 확인)은 택하지 않는다 — 상수는 맞는데 실제
     `bind` 호출이 다른 값을 쓰는 경우를 놓쳐 감시장치가 공허하게 통과한다.
4. 스캔 SSE 스트림의 이벤트 순서가 `RunStarted → … → RunFinished`이고, **그래프 단계 이벤트가
   마지막 `FileGenerated`와 `RunFinished` 사이에 나타난다.**
   - 검증: **두 축으로 나눠 각각 단언한다** [TH4 · 사용자 결정].
     ① `gateway.request_json`을 스텁한 코퍼스로 코어 `run_scan(on_event=…)`을 돌려 **이벤트
     시퀀스**를 단언한다 — 이 항목이 실제로 겨냥하는 성질이며 소켓·스레드·타이밍이 개입하지
     않는다. ② `format_sse(event) -> str` 순수 함수가 SSE 프레임 문법(`data: …\n\n`)을 맞게
     내는지 따로 단언한다.
   - **끝나지 않는 스트림을 테스트에서 통과시키지 않는다.** 실제 서버를 띄워 SSE를 읽고
     타임아웃으로 끊는 방식은 타임아웃 상수가 들어와 CI에서 가장 자주 깨지는 종류의 테스트가
     된다.
   - `Response.body`를 이터레이터까지 받도록 넓히지 않는다 — 타입이 두 종류가 되어 모든
     호출부가 둘을 가려야 한다. 스트리밍은 §4.10.3의 `handle()` 밖에서 다룬다.
5. 스캔 진행 중 두 번째 스캔 요청이 **409**이고, 진행 중이던 스캔은 영향받지 않는다.
   - 검증: **「진행 중」 상태를 주입한 뒤 `handle()`을 불러** 409를 단언한다 [TH5 · 사용자 결정].
     이것은 스레드 경합이 아니라 **상태 판정**이므로 실제 동시 실행이 필요 없다.
6. 취소 요청 후 **부분 `ScanResult`가 정상 반환**되고, 그때까지 생성된 `.md`가 디스크에 남으며
   종료 코드가 실패로 뒤바뀌지 않는다.
   - 검증: `should_cancel`이 **「N번째 문서 뒤에 `True`」를 돌려주는 술어**로 코어를 돌려
     단언한다. T1이 취소 훅을 순수 술어로 정한 덕에 스레드 없이 정확한 지점을 재현한다.
   - **취소 전에 인덱싱돼 있던 문서의 벡터가 그대로 남는다**를 함께 단언한다 — 방문하지 않은
     문서가 고아로 오판돼 지워지지 않아야 한다(§4.7). 같은 술어로 재현되므로 케이스가 하나
     늘 뿐이다.
   - **5·6번 어디에도 `sleep`·`threading.Event`·`Barrier`를 쓰지 않는다.** 타이밍 의존 테스트는
     CI 부하에 따라 간헐 실패하고, 깨질 때마다 대기 시간을 늘려 전체 테스트가 느려진다.
     동기화 장치를 쓰는 방식도 택하지 않는다 — 데드락 가능성이 생기고, 코어에 없는 `threading`을
     테스트가 들이게 된다.
7. 코어 단위 검증 2종:
   - 취소 훅이 **파일 루프 경계에서** 멈춘다 — 진행 중이던 문서는 마치고, 그다음 문서는
     시작하지 않는다.
   - 그래프 단계 이벤트가 `reduce()`를 통과해 `StatusSnapshot`에 반영된다.
   - 검증: `tests/unit/` 단위테스트.
8. 위키 상세 응답이 front-matter **5키**(`engine` 포함)와 7섹션을 **필드로 분리해** 담는다.
   프론트엔드 코드에 마크다운 파서가 없다.
   - 검증: 렌더된 위키를 입력으로 준 `parse_wiki_document()` 단위테스트 + 응답 스키마 단언.
   - **기존 `parse_wiki_markdown()`의 3-튜플 반환이 그대로임**을 함께 단언한다 — 래퍼로
     남긴다는 §4.6 결정이 지켜지는지가 기존 호출부 세 곳의 안전을 가른다.
9. `uv build`로 만든 wheel에 **정적 자산(HTML·CSS·JS)이 들어가고**, 그 wheel을 설치한 깨끗한
   환경에서 `corpbrain gui`가 기동한다.
   - 검증: CI에 `uv build` + wheel 설치 + 기동 스모크 단계를 추가한다. 현재 CI는 휠을 빌드해
     본 적이 없으므로 이 단계 자체가 신규다.
   - 기동 스모크는 **`corpbrain gui --no-browser`로 띄우고**, stdout에 토큰이 실린 URL이 나오는
     것을 확인한 뒤 프로세스를 종료한다 [제안 후 승인 · 2026-08-27 추가]. 서버는 포그라운드로
     떠 `Ctrl+C`까지 살아 있으므로(§4.1) 종료 절차가 없으면 CI가 타임아웃까지 매달린다.
     `--no-browser`가 없으면 CI 러너에서 브라우저를 여는 명령이 된다.
   - `dist/`는 이미 `.gitignore`에 있어 아래 항목10의 작업 트리 청결 검사와 부딪치지 않는다.
10. `uv run ruff check .`와 `uv run pytest`가 exit 0이고, CI의 작업 트리 청결 검사
    (`git status --porcelain`)를 통과한다.
    - 검증: 두 명령의 종료 코드 + CI 통과.

## 4. 인터페이스 계약

### 4.1 CLI [사용자 결정]
```
corpbrain gui
  --out DIR            위키·인덱스·그래프 DB 위치 (기본 ./corpbrain_wiki)
  --no-browser         브라우저를 자동으로 열지 않는다
```
- 포트는 **임의 할당**(OS가 고르는 빈 포트)이며 플래그로 지정하지 않는다.
- **바인드 주소는 `127.0.0.1` 상수다.** 플래그로 바꿀 수 없다(§2).
- 기동 시 토큰이 실린 URL을 stdout에 내고 브라우저를 자동으로 연다. `--no-browser`로 끈다.
  [제안 후 승인]
- 포그라운드로 떠 있고 `Ctrl+C`로 종료한다.

### 4.2 접근 통제 [사용자 결정]
- **1회용 토큰**을 기동 시 생성해 URL 쿼리에 싣는다. 토큰은 **파일에 쓰지 않고** 프로세스
  수명과 같이 간다 — 서버를 다시 띄우면 새 토큰이 된다.
- 이후 모든 요청은 **토큰 + `Origin`/`Host` 검증**을 모두 통과해야 한다. 토큰만으로는 부족하다
  — 브라우저가 다른 사이트에서 `127.0.0.1`로 보내는 요청(CSRF·DNS rebinding)은 Origin이
  가르고, 같은 머신의 다른 프로세스는 토큰이 가른다.
- 근거: GUI에는 상태를 바꾸는 엔드포인트(스캔 시작)가 있고 위키 본문은 사내 자료다.
- **두 헤더의 판정 규칙은 서로 다르다** [제안 후 승인 · 2026-08-27 추가]. 「헤더가 **없을** 때
  어떻게 하는가」를 적어 두지 않으면 구현이 어느 쪽으로 가든 하나씩 깨진다.

  | 헤더 | 규칙 |
  |---|---|
  | `Host` | **항상 필수.** `127.0.0.1:<port>`와 정확히 일치하지 않으면 403 |
  | `Origin` — 상태를 바꾸는 메서드(POST·DELETE 등) | **필수.** 값이 다르거나 **없으면** 403 |
  | `Origin` — 조회 메서드(GET) | **부재를 허용한다.** 값이 있으면 일치해야 하고, 없으면 통과. 토큰·쿠키는 그대로 요구한다 |

  - **부재를 허용하지 않으면 첫 화면이 뜨지 않는다.** 브라우저는 주소창 이동(최상위 GET
    내비게이션)에 `Origin`을 붙이지 않는다. 기동 시 여는
    `http://127.0.0.1:<port>/?token=…` 이 정확히 그 요청이므로, 「없음 = 허용되지 않음」으로
    구현하면 서버가 **자기 자신에게 403**을 낸다.
  - 반대로 모든 메서드에서 부재를 허용하면 다른 사이트가 보내는 Origin 없는 요청이 들어온다.
    상태를 바꾸는 메서드에서만 필수로 두면 그 구멍이 닫히고, 조회 GET은 쿠키의
    `SameSite=Strict`와 토큰이 함께 가른다.
  - `Host` 검증을 메서드로 가르지 않는 이유는 그것이 CSRF가 아니라 **DNS rebinding**을 막기
    때문이다 — 공격자 도메인이 `127.0.0.1`로 해석되게 만든 뒤 보내는 요청은 조회든 변경이든
    똑같이 막혀야 한다.
- **부트스트랩 토큰은 첫 접속에서 `HttpOnly` 세션 쿠키로 교환한다** [T6 · 사용자 결정].
  쿠키는 `HttpOnly` · `SameSite=Strict` · `Secure` 없음(`http://127.0.0.1`)이며 서버 프로세스
  수명과 같이 간다. 프론트엔드는 부팅 직후 `history.replaceState`로 URL에서 토큰 쿼리를
  지운다.
  - **이유는 `EventSource`다.** 브라우저 `EventSource`는 **커스텀 헤더를 붙일 수 없어**
    「모든 요청에 `Authorization: Bearer …`」라는 표준 답이 SSE 엔드포인트 하나에서 깨진다.
    쿠키는 `fetch`와 `EventSource`가 **자동으로 함께** 나르므로 인증 경로가 하나로 유지된다.
  - **모든 요청에 쿼리 파라미터로 싣는 방식은 택하지 않는다.** 토큰이 브라우저 히스토리·
    개발자도구 네트워크 탭·리퍼러에 반복 노출되고, 모든 호출부가 토큰을 손으로 이어 붙여야
    한다.
  - **`fetch`만 헤더를 쓰고 SSE만 쿼리를 쓰는 방식도 택하지 않는다.** 인증 경로가 둘로 갈려
    서버 검증 코드와 테스트가 두 배가 되고, 「왜 SSE만 다른가」를 아는 사람만 유지보수할 수
    있게 된다.
  - 쿠키 단독은 CSRF에 약하지만 **위에서 이미 `Origin`/`Host` 검증을 함께 요구**하므로 그
    구멍이 닫혀 있다. 두 장치는 서로를 대체하지 않는다.

### 4.3 서버 API [제안 후 승인 · §2·§4.4~§4.6의 결정에서 파생]
정적 자산 서빙 + JSON 엔드포인트 + SSE 1개로 구성한다. 각 엔드포인트는 코어 함수 하나에
대응하며 서버는 호출·직렬화·경로 해석·상태코드 매핑만 한다.

| 화면 | 코어 호출 | 성격 |
|---|---|---|
| 대시보드 | `diagnose()` · `SqliteGraphStore.stats()` | 조회 |
| 플랜 & 스캔 | `plan_scan()` · `run_scan(on_event=…, should_cancel=…)` | 조회 + **상태 변경** |
| 지식그래프 | `SqliteGraphStore.{stats,neighbors,degree_ranking,nodes_of,iter_edges}()` | 조회 |
| 위키 탐색기 | `--out` 트리 순회 + 위키 마크다운 파싱 | 조회 |
| 지식 검색 | `search_index()` | 조회 |
| 설정 | `is_cloud_consent_granted()` · `grant/revoke_cloud_consent()` · `pii` 마스킹 | 조회 + 변경 |
| 폴더 선택 | 디렉터리 열람 (§4.5) | 조회 |

- 진행 스트림은 **SSE 1개**이며 `ProgressEvent.to_dict()`를 그대로 싣는다. 이벤트 11종(§4.7
  신설분 포함)은 전부 JSON 직렬화 가능하고 `StrEnum`이라 변환 계층이 필요 없다. [사용자 결정]
- **SSE 접속 즉시 현재 `StatusSnapshot`을 첫 이벤트로 한 번 보낸다** [T5 · 사용자 결정].
  그 뒤부터 실시간 `ProgressEvent`를 이어 보낸다.
  - 서버는 스캔이 도는 동안 `reduce(snapshot, event)`로 스냅샷을 접어 들고 있는다. 이미
    존재하는 순수 함수이며 `generated`·`skipped`·`skipped_by_reason`·`elapsed`·`rate`·`eta`가
    전부 들어 있어 진행바·통계·스킵 요약이 한 번에 복원된다.
  - **이벤트를 버퍼링해 리플레이하지 않는다.** 브라우저 `EventSource`는 연결이 끊기면 자동
    재연결하므로 재접속은 새로고침만의 사건이 아니라 정상 동작 중에도 일어난다. 버퍼 방식은
    스캔 1회분 이벤트(50문서면 수백 건)를 서버가 계속 쥐어야 하고 버퍼 상한·생애 정책이라는
    결정이 새로 늘어난다. 스냅샷 방식은 재연결이 몇 번이든 비용이 같고 메모리가 자라지 않는다.
  - **첫 프레임과 이후 프레임을 판별자로 가른다** [제안 후 승인 · 2026-08-27 추가]. 스냅샷은
    `StatusSnapshot`이고 이후는 `ProgressEvent.to_dict()`라 **모양이 다른데**, 후자에만 `kind`가
    있고(`_progress.py:51`) 전자에는 없어 프론트가 둘을 가를 근거가 초판에 없었다. 스냅샷도
    `{"kind": "snapshot", …}`으로 감싸 **모든 프레임이 `kind`를 갖게** 한다.
    - SSE `event:` 필드를 쓰지 않는 이유는 프레임 문법이 두 갈래가 되어 `format_sse()`의 계약과
      그 단위테스트(§3 항목4 ②)가 함께 갈라지기 때문이다. 판별자를 본문에 두면 프레임 문법은
      `data: …\n\n` 하나로 유지된다.
  - **스냅샷 확보와 구독 등록은 한 번의 락 안에서 한다** [제안 후 승인 · 2026-08-27 추가].
    스냅샷을 먼저 흘려보낸 뒤 구독하면 **그 사이에 방출된 이벤트가 어느 쪽에도 담기지 않아
    영구히 사라진다** — 스냅샷은 그 이전에 찍혔고 구독자는 아직 없었으며, 서버는 스냅샷을
    다시 보내지 않기 때문이다(위의 「리플레이하지 않는다」). 순서를 뒤집으면 이번엔 같은
    이벤트가 두 번 반영된다(스냅샷에 접힌 뒤 이벤트로 또 온다). 한 락 안에서 둘 다 하는 것만이
    정확히 한 번을 보장한다.
  - **유휴 연결에는 SSE 주석 프레임을 주기적으로 보낸다** [제안 후 승인 · 2026-08-27 추가 ·
    issue #57 · D4]. `: keepalive\n\n` 형태이며 주기는 15초다. `EventSource`가 주석을
    무시하므로 프론트엔드에 판별 부담이 없다. 끊겨도 자동 재연결되지만 그때마다 스냅샷을 다시
    주고받으므로, 브라우저·프록시의 기본 유휴 한계보다 넉넉히 짧게 잡는다.
  - **구독자 큐는 상한을 갖고, 차면 가장 오래된 것부터 버린다** [제안 후 승인 · 2026-08-27
    추가 · issue #57 · D5]. 상한은 1000이다. 화면 하나가 느리다고 스캔이 멈춰서는 안 되며,
    잃는 것은 줄 단위 로그이고 집계는 다음 스냅샷이 복원한다 — 아래 「알려진 한계」와 같은
    성질이다.
  - **알려진 한계**: 로그 스트림 화면은 「재접속 지점부터」만 보인다. 그때까지의 처리·스킵
    내역은 스냅샷의 집계로 대체되며 줄 단위 로그는 복원되지 않는다.
  - **화면은 라이브 이벤트를 접어 진행 카운터를 갱신한다** [제안 후 승인 · 2026-08-27 추가].
    스냅샷이 접속 때 한 번만 오므로, 접지 않으면 카운터가 접속 시점 값에 멈춘 채 파일 이름만
    바뀐다(실측: 문서 50개를 도는 내내 `0 / 0`). 프론트가 접는 것은 **화면이 그리는
    값**(생성·스킵·현재 파일·그래프 단계)뿐이며, rate·ETA 같은 파생값과 재동기화는 그대로
    서버 스냅샷이 소유한다 — 재접속 한 번이면 지역 집계가 서버 값으로 덮인다. 코어 `reduce()`를
    프론트로 옮겨 오는 것이 아니다.
  - **진행 카드는 이벤트 사이에도 시간을 흘린다** [제안 후 승인 · 2026-08-27 추가 · issue #62 ·
    D-8]. 마지막 프레임 이후 흐른 시간을 더해 `경과 mm:ss · ETA mm:ss · <단계>` 줄을 1초마다
    다시 그리고, 다음 프레임이 오면 그 값으로 덮인다.
    - 근거는 실측이다. 수동 스모크 실행 K 에서 **문서 1건의 요약이 도는 동안 이벤트가 하나도
      오지 않아 화면이 최대 47.1초 멈춘 것처럼 보였다**(그래프 구간은 T4 덕에 최대 0.4초로
      내려갔다). 코어에 토큰 단위 이벤트를 더하는 것은 §4.7이 이벤트 11종으로 못박은 범위 밖
      이므로, 화면 쪽에서 「살아 있다」를 보이는 것으로 푼다.
    - **서버 값을 재계산하지 않는다.** 이미 받은 값에서 **시간만 흘리는 표시**이며, 바로 위의
      「rate·ETA 같은 파생값은 서버 스냅샷이 소유한다」와 부딪치지 않는다.
    - **알려진 한계**: 그 구간에 **문서 단위 진행률은 여전히 움직이지 않는다.** 움직이는 것은
      경과·ETA·단계 줄뿐이고, 「N / M」 카운터는 다음 `FileGenerated`까지 그대로다.

  | 폴더 선택 | `GET /api/browse?path=…` (§4.5) | PR ② |

  - 실행과 상태를 **한 경로의 두 메서드**로 둔 것은 「스캔」이라는 자원 하나에 대한 조회·생성
    이기 때문이다.
  - `graph=false`는 JSON이 아니라 **쿼리 문자열**이라 문자열 비교로 가른다 — `"false"`가 그냥
    참이 되는 실수가 이 경로에서만 가능하다. `expand_edges`는 **주어졌을 때만** 코어에 넘긴다:
    빈 문자열을 `parse_expand_edges()`에 주면 `PreconditionError`인데(v0.7 §4.4가 「빈 목록을
    «확산 안 함»으로 받아 주지 않는다」로 정했다), 고급을 펼치지도 않은 요청이 그 오류를 받아서는
    안 된다. 확산을 끄는 길은 `graph=false` 하나로 유지된다.
  - `POST /api/settings`의 **`gui` 섹션은 통째로 교체하지 않고 병합한다**(`{**current,
    **payload}`). 화면이 값 하나만 보내도 나머지가 살아남는다 — 통째로 교체하면 §4.8이 막으려던
    「나중에 쓴 쪽이 상대를 날린다」가 **같은 섹션 안에서** 재현된다.
  - **성공 응답은 `error` 키를 갖지 않는다** — 프론트는 `"error" in body` 하나로 가른다.
    404·405·500도 같은 두 필드를 쓴다: 프로토콜 층 사건과 도메인 상태는 **상태코드**로 갈리므로
    본문 모양까지 두 벌로 둘 이유가 없다.
  - **정적 자산 경로는 한 층이며 하위 디렉터리를 두지 않는다.** 경로 조립을 하지 않으므로
    트래버설이 원천적으로 성립하지 않는다.
  - SSE의 `snapshot`이 `null`이면 이 프로세스에서 스캔이 한 번도 돌지 않은 것이다. 기본
    `StatusSnapshot()`을 대신 보내지 않는다 — 그 값의 `state`는 `"starting"`이라 화면이 「곧
    시작한다」로 읽는다.

- **한 응답이 여러 절을 담을 때 도메인 상태는 그 절 안에 담는다** [제안 후 승인 · 2026-08-27
  추가]. 대시보드의 `doctor`·`graph`는 각각 **성공 payload 또는 `{error, message}`** 둘 중
  하나이며, 한쪽이 선행 조건 실패여도 다른 카드는 실제 값으로 그려진다.
  - 이것이 §5의 「각 화면이 자기 빈 상태를 그린다」를 **카드가 둘인 화면**에서 성립시키는
    방식이다. 응답 전체를 오류 본문으로 바꾸면 첫 실행(그래프 DB 없음)에서 Doctor 카드까지
    사라져, 사용자가 「무엇을 먼저 해야 하는가」를 볼 곳이 없어진다.
  - 절 안의 도메인/버그 판정은 §4.3.2의 규칙을 그대로 쓴다 — 규칙이 코드에 한 번만 적힌다.

### 4.3.1 `GraphStore` 계약 확장 — `iter_edges()` [T7 · 사용자 결정]
지식그래프 화면은 **전체 노드와 엣지**를 그려야 한다. 기존 10멤버로는 절반만 얻어진다.

- **노드도 기존 계약으로 얻는다 — 다만 `degree_ranking()` 하나로는 아니다** [2026-08-27
  정정 · issue #62 · D-1]. 초판은 「`degree_ranking()`이 전 노드 id를 주고 `nodes_of()`가 그
  노드들을 준다」고 적었으나 **사실이 아니다.** 그 함수는 `Document` 노드만 돌려준다 — v0.6
  §4.7이 `graph --central`을 「연결 차수 내림차순 **문서** 목록」으로 정의했기 때문이다.
  문면대로 짜면 `Entity`·`Tag`가 통째로 빠진 그래프가 그려진다(실측: 노드 4개 중 2개만 응답에
  실렸고 `tests/unit/test_gui_graph_api.py::test_returns_all_nodes_and_edges`가 잡았다).
  - **전 노드 = `degree_ranking()`의 문서 ∪ `iter_edges()`의 끝점**이다. `Entity`·`Tag` 노드는
    문서가 그것을 가리켜야만 존재하므로 반드시 어떤 엣지의 끝점이고, 엣지가 하나도 없는 고립
    문서는 `degree_ranking()`이 담는다. 두 집합의 합이 전 노드이며 라벨은 `nodes_of()`가 준다.
  - **그래서 계약은 여전히 11멤버다.** 무너진 것은 노드를 얻는 **경로에 대한 설명**뿐이고,
    아래 「기존 10멤버로 짜내지 않는다」·「`iter_edges()` 하나만 더한다」는 결론은 그대로
    옳았다 — 12번째 멤버를 만들 이유가 없다.
- **화면이 쓰는 차수는 `degree_ranking()`이 아니라 엣지에서 센다** [2026-08-27 추가 · D-1].
  같은 이유다 — 그 함수는 문서만 담으므로 `Entity`·`Tag`의 차수가 전부 0이 되고, 화면은 노드
  크기를 차수로 정하므로 **문서 10개를 잇는 허브 태그가 가장 작게 그려진다.** 엣지에서 세면
  문서의 값은 어차피 같다(둘 다 그 노드에 닿는 엣지 수).
- **엣지를 통째로 주는 길이 없다.** `stats()`는 개수만, `neighbors()`는 한 노드 주변만 준다.
  따라서 `iter_edges() -> Iterator[GraphEdge]` **한 개**를 더해 **11멤버**로 넓힌다.
- **v0.7의 「계약을 넓히지 않는다」와 다른 결론이 나온 이유**: v0.7은 `search(top_k=전 문서)`로
  **이미 존재하는 메서드가 전 행을 돌려주게** 해서 목적을 달성했다. 여기엔 그런 메서드가 없다.
- **기존 10멤버로 짜내는 방식을 택하지 않는 근거**: 전 노드에 `neighbors()`를 돌리면 N+1
  쿼리가 나가고 대칭 엣지가 두 번 나와 **중복 제거 로직이 조회 어댑터에 생긴다.** v0.6.1이
  `nodes_of()`를 추가하며 낸 결론(라벨 선택 규칙을 조회 쪽에서 재구현하면 두 화면이 오류 없이
  어긋난다)과 같은 함정이며, 「대칭 엣지는 한 행으로 저장한다」는 v0.6 §4.1의 저장 규칙 지식이
  저장소 밖으로 새어 나간다.
- **새 테이블·새 저장 계층을 만들지 않는다.** `replace_graph()`가 이미 엣지를 통째로 **쓰는**
  쪽을 다루므로, `iter_edges()`는 그 읽기 대칭항일 뿐이다. 읽기 전용이며 `read_only=True`
  개봉에서도 동작해야 한다.
- `SqliteGraphStore`와 함께 파이프라인이 쓰는 무동작 구현에도 빈 이터레이터로 구현한다 —
  v0.6이 `iter_vectors()`를 `_NoIndexStore`에 더한 것과 같다.

### 4.3.2 코어 예외 → HTTP 매핑 [T8 · 사용자 결정]
HTTP 상태코드는 **프로토콜 층의 사건에만** 쓴다. 코어의 선행 조건 실패는 프로토콜 오류가
아니라 **환경의 상태**이므로 상태코드로 접지 않는다.

| 층 | 사건 | 응답 |
|---|---|---|
| 프로토콜 | 토큰 부재·불일치 | **401** |
| 프로토콜 | 허용되지 않은 `Origin`·`Host` | **403** |
| 프로토콜 | 스캔 진행 중 새 스캔 요청 | **409** |
| 프로토콜 | 없는 경로·허용되지 않은 메서드 | **404** · **405** |
| 프로토콜 | 요청 본문이 이 엔드포인트의 모양이 아님 | **400** |
| 도메인 | **`CorpBrainError` 전부** · `sqlite3.Error`(단 `ProgrammingError` 제외) | **200** + 구조화된 상태 본문 |
| 버그 | `sqlite3.ProgrammingError` · 위 어디에도 해당하지 않는 예외 | **500** |

- 도메인 응답 본문은 **예외 종류 식별자**와 **사용자 안내 문장**을 각각 필드로 담는다.
  프론트엔드가 문자열을 파싱해 분기하지 않는다. 식별자는 **예외 클래스명**을 그대로 쓴다.
- **열거가 아니라 기반 클래스로 가른다** [제안 후 승인 · 2026-08-27 정정]. 초판은 도메인 행에
  `PreconditionError`(+3종)·`TokenBudgetExceededError`·`sqlite3.Error`를 **이름으로 열거**했는데,
  코어의 `CorpBrainError` 계층에는 그 목록에 없는 것이 더 있다 — `GatewayError`·
  `NetworkGuardError`·`ExtractionError`·`EmbeddingError`·`LLMParseError`·`CloudApiError`·
  `CloudRateLimitedError`. 열거로 두면 그중 하나가 조회 경로로 새는 순간 **버그가 아닌데
  500**이 되어, 바로 아래 「로그의 500이 그대로 버그 신호」가 무너진다. 규칙은
  **「`CorpBrainError`면 도메인, 아니면 버그」** 한 줄이면 되고, 계층에 새 예외가 늘어도 규칙이
  자동으로 따라온다.
  - `PreconditionError` 계열(`GpuGateError`·`IndexNotFoundError`·`ConsentStoreError`·
    `OllamaNotAvailableError`·`ModelNotAvailableError`·`CloudAuthError`·`CloudUnavailableError`)과
    `TokenBudgetExceededError`는 전부 `CorpBrainError` 하위이므로 이 한 줄에 그대로 들어온다.
- **`sqlite3.ProgrammingError`만 도메인에서 빼 500으로 둔다** [제안 후 승인 · 2026-08-27 추가].
  `sqlite3.Error`를 통째로 접으면 **스레드를 넘겨 커넥션을 쓴 버그가 200으로 숨는다** — 이
  저장소의 sqlite 커넥션은 `check_same_thread` 기본값으로 열리고(`graphstore.py:345`·
  `vectorstore.py:84`), `ThreadingHTTPServer`는 요청마다 스레드가 다르므로 GUI에서 가장 나기
  쉬운 버그가 정확히 이 예외로 나타난다. 그것을 200 + 「DB를 지우고 다시 스캔하세요」로 안내하면
  사용자가 **멀쩡한 DB를 지운다.** 손상·스키마 불일치(`DatabaseError` 등)는 종전대로 도메인이다.
- **`BadRequest` → 400은 「`CorpBrainError`가 아니면 버그(500)」에 낸 유일한 예외다**
  [제안 후 승인 · 2026-08-27 추가 · issue #62 · D-3]. 초판 표에 400이 없었던 것은 PR ①에
  **요청 본문을 받는 엔드포인트가 하나도 없었기** 때문이며, 스캔·설정이 처음으로 본문을 받으면서
  생긴 자리다.
  - 대상은 **코어를 부를 인자를 만들 수조차 없는 경우**로 한정한다 — 본문이 JSON으로 읽히지
    않거나, 객체가 아니거나, 무엇을 스캔할지가 지정되지 않았거나, `max_files: "abc"`처럼 숫자
    자리에 숫자가 아닌 값이 온 경우다. 이들은 `CorpBrainError`가 아니라 표의 「그 밖의 예외」에
    걸리는데, 그러면 **사용자의 오타가 500이 되어 「로그의 500 = 버그 신호」가 오염된다.**
  - **값의 타당성은 여전히 코어가 판정하고 도메인(200)이다** (§4.3.3). 음수 `max_files`,
    범위 밖 `graph_decay`, 없는 폴더는 그대로 코어로 넘어가 `PreconditionError`로 돌아온다 —
    GUI는 검증을 두지 않는다. 400은 **그 앞 단계**다.
  - 규칙(「상태코드는 프로토콜 층 사건에만」)과 어긋나지 않는다 — 404·405와 같은 층이다.
  - 예외 클래스는 `corpbrain/gui/errors.py`에 둔다. `scan.py`가 이것을 올려야 하는데 `api.py`가
    이미 `scan.py`를 import하므로, `api.py`에 두면 순환 import가 된다.
- **도메인 식별자 4종을 GUI가 따로 둔다** [제안 후 승인 · 2026-08-27 추가 · issue #62 · D-4].
  전부 `PreconditionError` 하위여서 **매핑은 한 글자도 바뀌지 않고**(도메인 200), 갈라지는 것은
  **식별자**뿐이다. 같은 「아직 볼 것이 없다」가 화면마다 다른 식별자로 나가면 프론트가 결국
  안내 문자열을 파싱하게 되는데, 그것이 바로 이 절이 막으려던 것이다.

  | 이름 | 사실 |
  |---|---|
  | `GraphNotBuilt` | 그래프 DB 파일이 아직 없다 (대시보드 `graph` 절 · `/api/graph`) |
  | `NothingScanned` | `--out` 아래 위키가 **하나도** 없다 (`/api/wiki`) |
  | `WikiNotFound` | 지목한 `doc_id`의 위키가 없다 — 지목이 잘못됐거나 산출물이 사라졌다 |
  | `DirectoryUnreadable` | 열람하려는 디렉터리가 없거나·디렉터리가 아니거나·권한이 없다 (§4.5) |

  - **앞의 셋을 하나로 뭉치지 않는다.** 그래프가 없어도 위키가 있으면 트리는 파일명으로 그려지므로
    (§4.6.2 파생 결정) 「그래프가 없다」와 「스캔한 적이 없다」는 **다른 사실**이고, 화면이 낼
    안내도 다르다. `WikiNotFound`는 v0.6이 `graph --neighbors`에서 「존재를 전제한 식별자
    지목의 실패는 빈 결과가 아니라 잘못된 지목」이라고 가른 것과 같은 성격이다.
  - 코어는 그래프 DB의 **부재와 손상을 같은 `PreconditionError`**로 묶어 「파일을 지우고 다시
    scan 하세요」라고 안내한다. 그것은 `graph` **CLI**의 계약(부재도 exit 1)에 맞춰진 문구라,
    GUI 첫 실행에서 그대로 내보내면 **만든 적도 없는 파일을 지우라는 안내**가 된다.
    파일 존재 여부는 열기 전에 확인할 수 있으므로 GUI가 거기서 가른다.
- 근거: 「Ollama가 안 떠 있다」·「먼저 스캔해야 한다」·「DB를 지우고 다시 스캔하라」는 요청의
  잘못도 서버의 잘못도 아니고, 화면이 사용자에게 **다음에 할 일을 안내해야 하는 상태**다.
  4xx로 접으면 서로 다른 안내가 같은 코드(예: 412) 안에 뭉쳐 프론트가 본문을 다시 갈라야 하고,
  「호출자가 잘못했다」는 4xx의 의미와도 어긋난다.
- **부수 효과**: 5xx가 오직 버그일 때만 나므로 **로그의 500이 그대로 버그 신호**가 된다.
- CLI가 `report.py`의 순수 빌더로 사유를 문장으로 내는 관용구와 같은 결이다. 표시 문구는
  가능한 한 기존 `build_*_lines`를 재사용해 두 어댑터의 어휘가 갈리지 않게 한다.
- **CLI의 종료코드(1·3)를 응답 본문에 싣지 않는다.** 종료코드는 프로세스가 죽는 방식이지
  죽지 않는 서버의 어휘가 아니다.

### 4.3.3 화면이 노출하는 파라미터 [T9 · 사용자 결정]
`ScanConfig` 15필드와 `search_index` 파라미터 5종을 **전부 GUI에서 다룰 수 있게 하되**,
앞면과 「고급」 접기(`<details>`)로 나눈다. 프로토타입이 게이트 3종에 이미 쓰고 있는 관용구다.

| 화면 | 앞면 | 고급 (접힘) |
|---|---|---|
| 스캔 | 입력 폴더 · 출력 폴더 · 엔진 · `force` · `max_files` | `max_chars` · `max_file_size` · `max_total_tokens` · `force_gates` · `model` · `embed_model` · `cloud_model` · `similarity_threshold` · `related_top_k` · `ollama_url` |
| 검색 | 쿼리 · `top_k` | `graph`(끄기) · `graph_decay` · `expand_edges` · `ollama_url` |

- **전부 노출하는 근거**: `force` 없이는 재요약을 시킬 수 없고, `max_files` 기본 50을 넘는
  폴더는 GUI에서 아예 스캔이 막힌다. 「CLI로 돌아가야 하는 일」을 남기면 GUI를 만든 목적이
  줄어든다.
- **접는 근거**: `similarity_threshold`(0.5717…)와 `graph_decay`(0.5)는 **실측으로 확정된
  값**이다(#42 · v0.7 §0). 앞면에 두면 근거 없이 만지게 되고, 만지면 v0.6·v0.7이 실측으로
  세운 성질이 조용히 무너진다.
- **평면 노출을 택하지 않는 근거**: 입력란 15개짜리 폼은 minimalist가 세운 절제된 벤토
  레이아웃과 부딪친다.
- **`ollama_url`을 빠뜨리지 않는다** [제안 후 승인 · 2026-08-27 정정]. 초판 표는 스캔 14개·검색
  4개만 담아 「15필드·5종 전부」라는 첫 문장과 어긋나 있었고, 양쪽에서 빠진 것이 같은 필드였다.
  기본 포트가 아닌 Ollama를 쓰는 사용자가 GUI에서 아예 막히면 이 절의 근거가 성립하지 않으므로
  고급에 넣는다.
  - 값이 localhost가 아니면 관문(`gateway`)이 `NetworkGuardError`로 거른다. 이는 사용자의 입력
    실수이지 버그가 아니며, §4.3.2가 규칙을 기반 클래스로 바꾼 덕에 **200 + 안내 문장**으로
    자동으로 들어온다 — 표에 예외를 따로 더할 필요가 없다.
- 검증은 종전대로 **코어가 소유한다.** GUI는 값을 그대로 코어에 넘기고 자체 파서·검증을 두지
  않는다 — `validate_graph_decay()`·`parse_expand_edges()`가 이미 코어에 있으며, v0.7 §4.4가
  「규칙이 한 곳에만 있어야 코어를 직접 부르는 후속 어댑터도 같은 보호를 받는다」고 정한
  그 후속 어댑터가 이번 GUI다.

### 4.3.4 스캔 화면의 2단계 흐름 [IX6 · 사용자 결정]
스캔은 **계량 → 확인 → 실행** 2단계다. 버튼 하나로 바로 시작되지 않는다.

1. **계량하기** — `plan_scan()`을 불러 파일 수·예상 토큰·소요시간 추정·게이트 판정과 파일별
   테이블(경로·확장자·크기·예상 토큰·중요도)을 보여 준다. 이 단계는 LLM을 부르지 않는다.
2. **스캔 시작** — 계량 결과 화면에서 눌러야 `run_scan()`이 시작된다.

- 게이트(GPU 미탑재·총 토큰 예산 초과)가 걸리면 **2단계에서 이유와 강행 토글(`force_gates`)을
  함께 보여 준다.** CLI가 exit 3으로 막는 자리와 같다.
- 근거: 게이트를 둔 이유가 「비용이 큰 작업을 무심코 시작하지 않게」이므로, 버튼 하나로
  시작되면 그 취지가 약해진다. CLI도 `plan`을 **별도 명령으로 분리해** 같은 판단 순간을 만들어
  두었다.
- **폴더를 고르는 즉시 자동 계량하지 않는다** — `plan_scan()`은 `nvidia-smi` subprocess와 전체
  stat 패스를 돌리므로, 폴더를 둘러보는 동안 그것이 반복되면 탐색이 느려진다.
- 계량 결과는 `run_scan(plan=…, findings=…)`으로 **재사용해** 같은 작업을 두 번 하지 않는다 —
  CLI가 `_emit_scan_banner`에서 하는 것과 같다.
- **재사용은 「계량에 쓰인 `ScanConfig`와 완전히 같을 때」로 한정한다** [제안 후 승인 ·
  2026-08-27 추가]. 다르면 서버가 **조용히 다시 계량하고** 그 결과로 실행한다.
  - 막으려는 것: 게이트에 막힌 사용자가 고급을 펼쳐 `max_total_tokens`를 20만 → 50만으로 올리고
    「스캔 시작」을 눌러도 **여전히 막히는** 상황이다. `ScanPlan.gate`는 계량 시점의 임계값으로
    이미 판정된 값(`GateVerdict`)을 담고 있고, `run_scan`의 방어는 `plan.file_count !=
    len(findings.targets)` 하나뿐이라(`pipeline.py:200`) 파일 수가 같으면 **낡은 판정을 그대로
    쓴다.** 엔진을 local → cloud로 바꾼 경우도 같다 — `gate.gpu_enforced`가 낡은 채 따라온다.
  - 이는 **GUI가 새로 만드는 요구**다. CLI는 한 프로세스 안에서 계량과 실행이 연달아 돌아
    사이에 설정이 바뀔 틈이 없었고, 두 HTTP 요청으로 쪼개면서 비로소 생겼다.
  - 판정을 코어에 넣지 않는다 — `run_scan`의 기존 방어는 「이 findings로 계산된 plan인가」라는
    **다른 질문**에 답하며, 「사용자가 폼을 만졌는가」는 어댑터가 아는 사실이다.

### 4.4 스캔 동시성 [사용자 결정]
- **한 번에 하나.** 서버는 스캔 워커 스레드를 하나만 둔다. 진행 중에 들어온 새 스캔 요청은
  **409**로 거절한다.
- 새로고침·다른 탭에서 열면 **진행 중인 스캔에 다시 붙는다** — 스캔 상태는 서버가 소유하고
  브라우저 세션이 소유하지 않는다.
- 근거: sqlite 커넥션이 생성 스레드에 묶여 있어 병렬 스캔이 애초에 성립하지 않는다.
  `run_scan` 전체가 하나의 워커 스레드 안에서 돈다.
- **같은 이유가 조회 경로에도 적용된다** [제안 후 승인 · 2026-08-27 추가]. 조회 엔드포인트
  (그래프·검색·위키 트리)는 **요청마다 저장소를 열고 `finally`에서 닫는다.** 커넥션을 요청
  사이에 캐시하지 않는다.
  - `ThreadingHTTPServer`는 요청마다 다른 스레드에서 핸들러를 돌리고 코어의 커넥션은
    `check_same_thread` 기본값으로 열리므로(`graphstore.py:345`·`vectorstore.py:84`), 저장소를
    프로세스 수명으로 캐시하면 **두 번째 요청부터 실패**한다.
  - 비용은 sqlite 파일 개봉 한 번이고, 조회는 `read_only=True` 개봉이라 파일에 쓰지도 않는다
    (v0.6.1 결정 계승).

### 4.5 디렉터리 열람 [사용자 결정]
- 나열 범위에 **제한을 두지 않는다** — 임의 절대경로를 열람할 수 있다.
- 근거: CLI가 이미 `corpbrain scan /any/path`를 제한 없이 수행한다. GUI만 좁히면 같은 코어의
  두 어댑터가 다른 권한을 갖게 된다. 인가되지 않은 호출은 §4.2가 이미 거절하며, 서버는
  사용자 자신의 파일 권한으로 돌아간다.
- **숨김 항목을 서버가 거르지 않는다** [제안 후 승인 · 2026-08-27 추가 · issue #62 · D-4].
  `hidden` 플래그만 실어 보내고 접을지는 화면이 정한다 — 「제한을 두지 않는다」는 위 결정이
  거르는 쪽으로 조용히 새지 않게 한다.
- **그 폴더의 지원 포맷 파일 개수를 함께 낸다.** 스캔 대상을 고르는 화면이므로 「여기에 스캔할
  것이 있는가」가 곧 필요한 정보다. 판정은 코어 `is_supported()`를 그대로 쓴다 — 확장자 목록을
  어댑터가 다시 적으면 `SUPPORTED_EXTENSIONS`와 갈린다.
- **읽지 못한 디렉터리는 `DirectoryUnreadable`(도메인 200)로 낸다** [제안 후 승인 · 2026-08-27
  추가 · issue #62 · D-4]. 이것이 §5의 「열람 API가 접근할 수 없는 디렉터리: 권한 거부를
  **그대로 보고하고 서버를 죽이지 않는다**」를 성립시키는 장치다.
  - `PermissionError`·`FileNotFoundError`는 `CorpBrainError`가 아니라 §4.3.2의 규칙대로면
    **500**(버그)인데, 사용자가 남의 폴더를 눌러 본 것은 버그가 아니다. `PreconditionError`
    하위로 옮겨 화면이 「읽을 수 없습니다」를 그리고 탐색을 계속하게 한다.
  - 나열 도중 **개별 항목** 하나를 판정하지 못한 경우(깨진 심볼릭 링크 등)는 그 항목만 건너뛰고
    나열을 계속한다 — v0.1 §5의 「개별 파일 실패는 전체 실패로 위장하지 않는다」와 같은 결이다.

### 4.6 위키 상세 [사용자 결정]
- **서버가 위키 마크다운을 구조화해 JSON으로 내려준다.** front-matter **5키**(`source_path`·
  `generated_at`·`model`·`engine`·`source_bytes`)와 7섹션(제목·한 줄 요약·핵심 포인트·요약·
  태그·원문·관련 문서)을 각각 필드로 나눈다.
  - **`engine`을 빠뜨리지 않는다** [제안 후 승인 · 2026-08-27 정정]. 초판은 4키로 적었으나
    `render.py:69`가 실제로 쓰는 키는 다섯이다. 빠져 있던 `engine`은 v0.5가 「생성물만 보고도
    이 문서가 외부로 나갔는지 구별할 수 있게」 넣은 값이므로(v0.5 §4.6), 상세 화면에서
    **가장 먼저 보여야 할 값**에 가깝다.
  - **여기에 `wiki_path`·`wiki_relative` 두 필드가 더 실린다** [제안 후 승인 · 2026-08-27 추가 ·
    issue #62 · D-5]. 각각 위키 파일의 절대경로와 `--out` 기준 상대경로이며, 화면이 「이 위키가
    어디에 있는가」를 보이는 데 쓴다. 제거하지 않는다 — 상세 화면은 `doc_id`(원문 경로)와 위키
    파일 경로 **둘 다** 보여야 하고, 프론트가 `out_dir`와 `doc_id`로 그 값을 조립하면 MVP 스펙
    §4.4의 파일명 규칙(`<원본이름.확장자>.md`)이 프론트로 새어 나간다. 서버는 이미 그 경로를 손에
    쥐고 있으므로(§4.6.2의 인벤토리로 찾았다) 실어 보내는 비용이 0이다.
  - **front-matter 5키 + 7섹션이 계약이고, 이 둘은 그 위에 얹힌 어댑터 값이다.** 파싱이 낳는
    값(`WikiDocument`)에는 들어가지 않는다 — 코어는 경로 해석 책임을 지지 않으므로 「이 마크다운이
    어느 파일에서 왔는가」를 알지 못한다.
- 프론트엔드에 **마크다운 파서를 두지 않으며**, 따라서 마크다운 렌더 경로의 XSS 방어도
  프론트엔드 책임이 아니다.
- **파싱은 `embedding_text` 모듈이 소유한 섹션 지식을 재사용하되, 기존 함수를 그대로 쓰지는
  못한다** [제안 후 승인 · 2026-08-27 정정]. 마크다운 구조 지식이 두 곳으로 갈라지지 않게
  한다는 취지는 그대로다(v0.6 §4.4 결정 계승).
  - **초판은 `parse_wiki_markdown`을 재사용한다고 적었으나 그 함수로는 이 절을 만들 수 없다.**
    임베딩 입력을 만들려고 쓰인 함수라, ① 첫 줄의 `_strip_front_matter()`가 front-matter를
    통째로 버리고 ② 반환이 `(제목, 임베딩용 합본 텍스트, 태그)` 3-튜플이라 섹션별 원문이 남지
    않으며(「원문」·「관련 문서」는 내부적으로 읽되 돌려주지 않는다) ③ 불릿 기호 제거·태그
    분해·빈 줄 제거로 구조가 **되돌릴 수 없게** 정규화된다.
  - **같은 모듈에 `parse_wiki_document(markdown) -> WikiDocument`를 추가하고,
    `parse_wiki_markdown`은 그것을 부르는 얇은 래퍼로 남긴다.** `WikiDocument`는 front-matter
    5키와 7섹션을 각각 필드로 담는 frozen 값 객체이며, 「관련 문서」 항목은 아래 IX3의
    `{title, doc_id, 근거}` 모양을 그대로 쓴다.
  - 래퍼로 남기는 이유는 **기존 호출부를 하나도 건드리지 않기 위해서다** —
    `_backfill_embedding`·`_restore_facts`(그래프 재료 복원)·단위테스트가 3-튜플 언패킹에
    의존한다. v0.6이 이 함수를 넓힐 때 **고쳐야 할 언패킹 지점 네 곳을 스펙에 직접 적어 둔**
    전례가 있고, 이번에는 반환을 바꾸지 않는 쪽으로 그 비용 자체를 없앤다.
  - 새 모듈로 분리하지 않는다 — 「마크다운 구조 지식이 한 파일에 모인다」가 이 결정의
    출발점이다.
- 서버측 마크다운→HTML 변환을 하지 않으므로 파이썬 마크다운 라이브러리 의존성도 생기지 않는다.
- **「관련 문서」 항목은 `doc_id`를 함께 실어 내린다** [IX3 · 사용자 결정]. 각 항목을
  `{title, doc_id, 근거}` 필드로 담고, 프론트엔드는 `#/wiki?doc=<doc_id>`를 조립하기만 한다.
  - `render.py`가 위키에 쓰는 링크는 **그 위키 파일 기준 상대경로**(`../개발/설계.md.md`)라
    브라우저에서 그대로 쓰면 404이거나 원시 마크다운이 다운로드된다.
  - **서버는 그 `doc_id`를 상대 링크를 풀어서 얻는다** [제안 후 승인 · 2026-08-27 추가].
    위키 본문에는 `doc_id`가 **적혀 있지 않다** — 적혀 있는 것은 제목·상대경로·근거 문구뿐이다
    (`render.py:120`). 서버가 링크의 상대경로를 그 위키 파일 기준으로 풀어 대상 위키를 찾고,
    그 front-matter의 `source_path`를 읽는다. `rerun.read_source_path()`가 이미 그 일을 한다.
    - 비용은 **상세 1건당 최대 `related_top_k`개(기본 5)의 파일 열기**다. §4.6.2가 배제한
      「매 요청 `rglob` + 전 문서 열기」와는 규모가 다르다.
    - 초판은 「서버가 `doc_id`를 실으면 링크를 만들었다가 다시 파싱해 되돌리는 왕복이
      사라진다」고 적었으나, **서버도 그 값을 갖고 있지 않다.** 왕복은 사라지는 것이 아니라
      프론트에서 서버로 **옮겨지는** 것이며, 이 항목이 그 옮겨진 자리를 정한다. 프론트가 하지
      않아야 하는 이유(경로 해석이 프론트로 넘어간다 · 마크다운 파서가 생긴다)는 그대로다.
    - **그래프에서 다시 계산하지 않는다.** `rank_related()`는 동점 정렬 5번 키로 「출력
      상대경로」를 쓰는데 그 값을 얻으려면 결국 위키 전체를 열어야 하고, 그 인자를 생략하면
      **화면의 순서가 파일에 적힌 순서와 어긋난다.** 「조회 시점에 파생값을 다시 계산하지
      않는다」는 v0.6 불변식과도 부딪친다.
    - **위키에 `doc_id`를 적어 넣는 방식도 택하지 않는다** — §2의 「위키 산출물은 한 글자도
      바뀌지 않는다」를 지킨다.
  - **프론트엔드가 링크 문자열을 파싱해 되돌리는 방식은 택하지 않는다.** 경로 해석이
    프론트로 넘어가 「상대경로 해석은 어댑터의 책임이며 코어로 넘기지 않는다」는 불변식의
    취지를 벗어나고, §4.6이 정한 「프론트엔드에 마크다운 파서를 두지 않는다」와도 부딪친다.
  - 서버가 `doc_id`를 실으면 **프론트엔드에는 그 왕복이 남지 않는다** — 한 번 풀린 값을 필드로
    받으므로 화면 코드에 경로 조립 규칙이 생기지 않는다. 서버 쪽 해석 비용은 위 항목이 다룬다.
  - 링크 없이 제목만 내는 방식도 택하지 않는다 — v0.6이 「문서 사이의 섬을 잇는다」고 만든
    기능이 GUI에서만 탐색 불가능해져, 파일 탐색기보다 못한 경험이 된다.
- **「원문」은 링크가 아니라 「경로 표시 + 복사 버튼」으로 낸다** [IX2 · 사용자 결정].
  - `render.py:91`이 위키에 넣는 `[원본 파일 열기](file://<절대경로>)`는 `http://127.0.0.1`로
    서빙된 페이지에서 **브라우저가 차단**해 클릭해도 아무 일도 일어나지 않는다. 죽은 링크를
    그대로 그리지 않는다.
  - GUI는 `source_path` 필드를 mono 글꼴로 표시하고 클립보드 복사 버튼을 붙인다.
  - **`os.startfile`/`open`/`xdg-open`을 부르는 엔드포인트를 두지 않는다.** MVP 스펙 §2가
    「`os.startfile` 딥링크 브릿지」를 명시적 비목표로 정했고, 그것을 되살리면 「서버가 임의
    파일을 OS 기본 앱으로 실행한다」는 새 능력이 생긴다. 토큰이 있어도 이는 §4.2가 다루는
    범위를 넘는 별개의 결정이다. 플랫폼 분기도 함께 들어온다.
  - **원문 바이트를 내려주는 방식도 택하지 않는다** — 같은 파일이 둘로 늘어나 사용자가 받은
    사본을 고쳐도 원본은 그대로이고, `.docx`·`.xlsx`는 결국 다운로드 후 수동으로 열어야 한다.
  - **위키 산출물은 바꾸지 않는다.** `render.py`의 `file://` 링크는 그대로 둔다 — 파일 탐색기·
    에디터에서 위키를 직접 볼 때는 여전히 동작하며, §2가 정한 「위키 산출물 불변」을 지킨다.
    GUI는 마크다운을 그리지 않고 **필드로 받으므로**(위) 이 결정은 GUI 표시에만 적용된다.

### 4.6.2 위키 탐색기 트리 [IX5 · 사용자 결정]
- 트리의 **제목은 그래프 DB의 `nodes.label`에서 얻는다.** `degree_ranking()`으로 전 노드 id를
  받아 `nodes_of()`로 `Document` 노드의 라벨을 가져온다 — sqlite 조회 2번이고 위키 파일을
  하나도 열지 않는다.
- 트리의 키는 `doc_id`이며 IX3의 「관련 문서」 링크·그래프 화면·검색과 **같은 키**를 쓴다.
- 근거: v0.6.1이 정한 「라벨 선택 규칙은 `build_graph()` 한 곳에만 있고 조회는 저장된
  `nodes.label`을 읽는다」를 그대로 계승한다. 같은 문서가 화면마다 다른 제목으로 불리지 않는다.
- **매 요청 `rglob` + 파일 열기 방식은 택하지 않는다** — 문서 수만큼 파일을 여는 일이 화면을
  열 때마다 반복되고, 제목 파싱 경로가 서버 안에 둘(그래프용·트리용)이 된다.
- **파일명만 내는 방식도 택하지 않는다** — `채용계획.docx.md`가 그래프·검색이 보여 주는 제목과
  달라, 같은 문서가 화면마다 다르게 불린다.
- **파생 결정**: 그래프 DB가 없거나(v0.5 이하 산출물·DB만 삭제) 뒤처진 상태면 트리도 그렇다.
  이 경우 §5의 기존 방침대로 다루며, 라벨을 얻지 못한 항목은 파일명으로 대체하고 화면이
  「다시 스캔하면 채워집니다」를 안내한다.

### 4.6.1 검색 결과의 응답 모양 [IX4 · 사용자 결정]
- `doc_id` · `score` · `title` · `source_path`는 **필드로 내린다.** 검색 화면은 점수 배지·
  스니펫·태그 칩·「지식그래프에서 보기」 버튼이 있는 카드이므로 줄 문자열로는 그릴 수 없다.
- **확산 문서의 근거 줄만 `report.py`의 기존 빌더 결과 문자열을 그대로 싣는다.** v0.7 §4.6이
  정확 문자열까지 못박고 `tests/unit/test_search_report.py`가 단언하는 계약이므로, 이 한 줄이
  CLI와 GUI에서 한 글자도 갈리지 않는다.
  - **그 빌더를 공개 이름으로 승격한다** [제안 후 승인 · 2026-08-27 추가]. 현재 이름은
    `_expansion_evidence`(밑줄, `report.py:318`)인데 이 모듈의 공개 관용구는 `build_*`이므로,
    다른 어댑터가 밑줄 함수를 import하는 상태로 두지 않는다. `build_expansion_evidence()`로
    옮기고 `build_search_lines()`가 그것을 부른다 — 표시 로직의 소유자는 종전대로 `report.py`
    한 곳이다.
  - 이는 v0.7 계약의 변경이 **아니다.** 반환 문자열은 한 글자도 바뀌지 않으며 기존 단위테스트가
    그대로 그 성질을 지킨다.
- **`build_search_lines()` 전체를 그대로 내리지 않는다** — 결과 하나가
  `"  1. [0.710] 온보딩 — /Users/…"` 한 문자열로 뭉쳐 있어 프론트가 정규식으로 다시 갈라야
  하고, 그러면 출력 문구를 다듬는 순간 조용히 깨진다.
- **근거까지 전부 구조화하지도 않는다** — 참조 방향 3종 문구(「시드를 참조함」·「시드가
  참조함」·「서로 참조함」)를 프론트가 다시 구현하게 되어 v0.7이 못박은 어휘가 둘로 갈린다.
- 원칙: **갈라지면 안 되는 것은 「어휘」이지 「줄 조립」이 아니다.** §4.3.2의 「기존 빌더를
  재사용한다」는 이 뜻으로 읽는다.
- **그래서 「줄 목록을 그대로 싣는 것」이 금지되는 것은 아니다 — 경계는 「프론트가 그 줄을
  다시 갈라야 하는가」다** [제안 후 승인 · 2026-08-27 추가 · issue #62 · D-6].

  | 값 | 처분 | 이유 |
  |---|---|---|
  | 검색 결과 (`build_search_lines()`) | **싣지 않는다** | 한 줄에 점수·제목·경로가 뭉쳐 있어 카드로 그리려면 프론트가 정규식으로 갈라야 한다 |
  | 확산 근거 (`build_expansion_evidence()`) | **문자열 그대로** | 줄 전체가 하나의 표시 단위이고 v0.7이 정확 문자열로 못박았다 |
  | 스캔 종료 요약 (`build_summary_lines()`) | **줄 목록 그대로**(`summary_lines`) | 이미 **독립된 줄의 목록**이라 프론트가 순서대로 출력하면 끝이다 |

  - 종료 요약을 프론트가 다시 조립하면 스킵 사유 라벨과 「그래프 미반영 — 다시 스캔하면
    반영됩니다」 같은 문구가 두 벌이 되어, **CLI와 GUI가 같은 결과를 다른 말로 설명한다.**
    그것이 이 절이 막으려는 것이고, 줄 목록을 싣는 것은 그것을 막는 쪽이다.
  - 카드가 필요로 하는 **숫자**(생성·스킵·취소 여부·그래프 지표)는 구조화된 필드가 따로 낸다 —
    줄에서 뽑아 쓰지 않는다. 두 표현이 한 응답에 함께 있는 것이 이 결정의 모양이다.

### 4.7 코어 변경 [사용자 결정]
둘 다 **가산적 변경**이며 기존 시그니처를 깨지 않는다.

- **협조적 취소 훅** [T1]: `run_scan()`에 `should_cancel: Callable[[], bool] | None = None`을
  더한다. 파일 루프 경계에서 호출해 `True`면 멈추며, 계약은 **「진행 중인 문서를 마친 뒤
  멈춘다」**다.
  - **`threading.Event`를 받지 않는다.** 코어에는 현재 `threading`·`asyncio`·`signal` import가
    하나도 없고, 순수 술어로 두면 그 성질이 유지된다. 동시성 자료형을 코어 시그니처에 박으면
    「단일 프로세스 안의 스레드」를 전제하게 되어 후속 어댑터(프로세스·비동기)가 변환층을
    지게 된다. 단위테스트도 스레드 없이 카운터 하나로 짤 수 있다.
  - **`on_event`의 반환값으로 취소를 표현하지 않는다.** 이벤트 sink와 실행 제어가 한 콜백에
    섞이고, `_emit`이 반환값을 버리고 예외까지 삼키는 현재 구조에서는 「sink 버그로 스캔이
    조용히 멈춘다」는 새 실패 모드가 생긴다.
  - **`should_cancel`의 예외는 삼키지 않는다.** `_emit`이 `on_event` 예외를 흡수하는 것과
    의도적으로 다르다 — sink는 표시 장치라 죽어도 스캔이 계속되는 것이 옳지만, 취소 술어는
    제어 입력이라 조용히 무시하면 사용자의 중단 요청이 사라진다.
  - 취소되어도 **부분 `ScanResult`를 정상 반환**한다. `finally`의 저장소 정리가 그대로 돌아
    인덱스·그래프 DB가 깨끗하게 닫히고, 그때까지 쓰인 `.md`는 디스크에 남아 다음 실행에서
    `up_to_date`로 재사용된다.
  - **취소되면 그래프 단계(패스2 빌드 · 패스3 「관련 문서」 주입)를 건너뛰고 즉시 반환한다**
    [T2 · 사용자 결정]. 취소가 가장 빨리 듣는 쪽을 택한다.
    - **다음 `scan`이 자동으로 회복한다.** `doc_facts` upsert는 패스2가 아니라 **패스1의 파일
      루프 안에서 문서마다** 일어나므로(`pipeline.py:537`), 취소된 실행에서도 완료된 문서의
      재료가 엔티티까지 온전히 남는다. 다음 실행은 전 문서가 `up_to_date`로 스킵되더라도
      패스2·3을 돌려 그래프를 전체 재빌드하고 「관련 문서」를 주입한다 — **`--force`도
      재요약도 필요 없고 엔티티 손실도 없다.**
    - 남는 대가는 **다음 `scan`까지의 창(window)** 뿐이다. 그동안 새로 만들어진 위키의
      「관련 문서」 마커 블록은 비어 있고(`관련 문서 없음`), 그래프 화면·`graph` 조회·검색
      확산은 그 문서들을 알지 못한다.
    - 이 창을 조용히 두지 않는다 — 취소된 스캔의 종료 보고에 **「그래프 미반영 — 다시 스캔하면
      반영됩니다」**를 낸다.
  - **취소되면 고아 벡터 정리도 함께 건너뛴다** [제안 후 승인 · 2026-08-27 추가]. 패스2·3과
    같은 자리에서 건너뛰지만 이유가 다르다 — 이쪽은 속도가 아니라 **데이터 손실 방지**다.
    - `run_scan()`의 고아 벡터 정리는 파일 루프가 **방문한 문서만** 담은 집합(`valid_ids`)으로
      「위키가 사라진 문서」를 판정한다(`pipeline.py:244`·`:252`). 취소로 루프가 일찍 끊기면
      **아직 방문하지 않은 문서 전부**가 그 판정에 걸린다 — 문서 50개 중 3번째에서 취소하면
      나머지 47건의 벡터가 인덱스에서 지워지고, 화면에는 아무 말도 나오지 않는다.
    - 다음 실행이 `_backfill_embedding`으로 되채우므로 영구 손실은 아니다. 그러나 문서마다
      임베딩 호출을 한 번씩 다시 치르고 그 사실이 어디에도 보고되지 않으므로, 「취소는 아무것도
      망가뜨리지 않는다」는 이 절의 계약이 조용히 깨진다.
    - **새 규칙이 아니다.** v0.6 §5가 「위키를 하나라도 읽지 못하면 재료 정리를 통째로
      건너뛴다」로 이미 같은 잣대를 세웠고(`_WikiInventory.complete`), 그 근거는 **「목록이
      불완전한 채로 «없는 문서»를 판정하면 일시적 조건이 삭제로 번진다」**였다. 취소는 그 목록을
      불완전하게 만드는 **또 하나의 경로**이며, 초판은 그것을 세지 못했다.
  - **`ScanResult`에 `cancelled: bool = False`를 더한다** [T3 · 사용자 결정]. 9필드 → 10필드다.
    - 취소는 **실행 전체의 상태**이지 그래프 축의 속성이 아니다. 이미 최상위에 있는
      `limit_exceeded: bool`·`discovered_count`와 같은 성격이며 모양도 `limit_exceeded`와
      정확히 같아 새 관용구를 만들지 않는다.
    - `GraphSkipReason`에 `CANCELLED`를 더하는 방식은 택하지 않는다 — 「스캔이 중단됐다」가
      그래프 하위 객체 안에 숨어, 그래프를 보지 않는 호출자가 취소를 알 길이 없어진다.
    - 코어가 모르게 두는 방식도 택하지 않는다 — 「이 실행이 왜 일찍 끝났는가」의 판정 로직이
      어댑터마다 복제된다. `cancelled=True`면 그래프 미반영도 함께 참이므로 판정은 한 곳이다.
    - v0.6이 세운 「`ScanResult`는 9필드를 유지한다」는 **여기서 한 번 깨진다.** 그 결정의
      근거는 「그래프 지표가 늘어날 때 평면 필드로 흩뿌리지 않는다」였고 취소는 그래프 지표가
      아니므로, 근거가 겨냥한 대상이 아니다. 그래프 관련 값은 종전대로 `GraphOutcome` 안에서만
      늘어난다.
  - **알려진 지연**: 요약 1건의 소켓 타임아웃이 300초이므로 취소 요청이 최대 그만큼 대기할 수
    있다. 진행 중인 HTTP 호출을 끊지 않는다.
  - 프로세스를 kill하는 방식은 택하지 않는다 — sqlite 정리가 보장되지 않고 부분 결과를 회수할
    길이 없다.
- **그래프 단계 진행 이벤트** [T4]: `_progress.py`에 **3종**을 더하고 `reduce()`를 확장한다.
  기존 8종 → 11종이 된다.

  | 이벤트 | 필드 | 시점 |
  |---|---|---|
  | `GraphStarted` | `at` | 패스2 진입 |
  | `RelatedInjected` | `at, index, total, path` | 패스3에서 위키 1개를 처리할 때마다 |
  | `GraphFinished` | `at, stats: GraphStats \| None` | 패스3 종료 **및 빌드 실패** |

  - **`stats`는 `None`일 수 있고, 그때도 이벤트를 낸다** [제안 후 승인 · 2026-08-27 추가].
    그래프 재빌드가 실패하면 단일 트랜잭션이라 이전 그래프가 그대로 보존되고 스캔은 계속되는데
    (v0.6 §5), 그 경로에서 이벤트를 내지 않으면 `GraphStarted`가 연 구간이 **닫히지 않은 채**
    끝나 화면이 「그래프 빌드 중」에 멈춘 것처럼 보인다. 실패는 `GraphOutcome.build_failure`가
    이미 결과 축으로 보고하므로, 이벤트 축은 **구간을 닫는 일**만 한다.
    - 초판 표는 `at, stats` 로만 적어 **스펙대로 읽으면 구현이 틀린 것처럼 보였다.**
      문면을 구현에 맞춰 되적는다 (issue #57 · D2).
  - 근거: 현재 `_run_graph_stage`는 이벤트를 하나도 내지 않아 마지막 파일 이후 `RunFinished`
    까지 진행 표시가 멈춘 것처럼 보인다. 대형 `--out`에서 이 구간이 길다.
  - **진행률은 패스3에만 싣는다.** 패스2(그래프 재빌드)는 쪼갤 수 없는 단일 작업이고, 패스3은
    `--out` 아래 위키 수를 알아 쪼갤 수 있다. 「쪼갤 수 있는 것만 쪼갠다」가 타입에 드러나게
    두며, 없는 진행률을 지어내지 않는다.
  - `index, total, path` 세 필드는 기존 `FileStarted`·`FileStage`·`FileGenerated`와 같은
    이름·같은 의미를 쓴다. 진행 이벤트의 어휘가 갈리지 않게 한다.
  - **기존 `FileStage`의 `Stage` enum에 값을 더하는 방식은 택하지 않는다.** `FileStage`는
    「문서 1개를 처리하는 중」을 뜻하는 타입이라 의미가 달라지고, `reduce()`의 `generated`
    카운트와 rate·ETA 계산이 오염된다.
  - 패스3의 개별 실패(`InjectionFailure`)는 종전대로 `GraphOutcome`에 모아 보고한다 — 이벤트
    축과 결과 축을 겸하게 하지 않는다.
  - **`reduce()`는 `StatusSnapshot`에 필드 3개를 더한다** [제안 후 승인 · 2026-08-27 추가].
    파일 루프의 축(`stage`·`index`·`total`·`generated`)과 **별도 축**이며, 같은 필드에 담으면
    바로 위에서 `Stage` enum 재사용을 거부한 것과 같은 오염이 일어난다.

    | 필드 | 값 |
    |---|---|
    | `graph_stage` | `None`(진입 전) · `building`(패스2) · `injecting`(패스3) · `done`(패스3 종료) |
    | `graph_index` · `graph_total` | 패스3의 진행률. 패스2는 쪼갤 수 없으므로 `building` 동안 0 |

    - `RelatedInjected`는 `current_file`도 갱신한다 — CLI stderr 라이브 라인이 그대로 살아
      움직인다(§2의 「공짜 이득으로 받되 목표로 삼지 않는다」). `render_status_line()`은 한
      글자도 바뀌지 않는다.
    - **진행 이벤트는 「고쳐 쓴 위키」가 아니라 「처리한 위키」를 센다.** 내용이 바뀌지 않아
      파일을 다시 쓰지 않은 위키에도 `RelatedInjected`를 낸다 — 후자만 세면 아무것도 바뀌지
      않은 재실행에서 진행바가 0에 멈춘 것처럼 보인다. `GraphOutcome.related_updated_count`
      (실제로 고쳐 쓴 수)와는 **다른 축**이다.
    - 초판은 「`reduce()`를 확장한다」까지만 적고 필드를 명명하지 않았다 (issue #57 · D3).
- **`collect_wiki_documents()`·`WikiInventory` 를 공개 이름으로 승격한다** [제안 후 승인 ·
  2026-08-27 추가 · issue #62 · D-7]. `pipeline.py`의 사설 함수였다. **동작은 한 글자도 바뀌지
  않으며**, U1의 `build_expansion_evidence()` 승격과 같은 성격이다 — 이로써 이 슬라이스의 공개
  승격은 **3종**이 된다(`build_expansion_evidence()` · `parse_wiki_document()` · 이것).
  - 위키 상세는 `doc_id`로 위키 **파일**을 찾아야 하는데 트리는 그래프 라벨만 준다(§4.6.2).
    그 함수가 이미 `--out`을 훑어 `doc_id → 위키 경로`를 만들고, 그 안에 **「같은 원문을 가리키는
    위키는 마지막 것이 이긴다」**(v0.6 §5)와 **「읽지 못한 위키가 있으면 목록이 불완전하다」**
    (v0.6 §5)는 규칙이 들어 있다. GUI가 다시 구현하면 한쪽만 고쳐지는 순간 **두 경로가 같은
    `--out`을 다르게 본다.**
  - **§4.6.2가 배제한 방식으로 되돌아가는 것이 아니다.** 그 절이 거부한 것은 트리의 **제목**을
    매 요청 파일에서 파싱하는 일이고, 제목은 여전히 그래프 `nodes.label`에서만 온다.
  - **비용**: 인벤토리는 `--out` 아래 `.md`를 전부 훑어 각 파일의 **앞부분만** 읽는다
    (`read_source_path()`가 front-matter를 담을 만큼만 peek한다). 즉 **상세 1건당 문서 수 N회의
    head 읽기**이며, §4.6 IX3이 「상세 1건당 최대 `related_top_k`개」로 적은 것은 「관련 문서」
    해석 몫만 센 값이다. 두 비용이 겹치지만 `--max` 기본 50 규모에서 셋 다 작고, 자주 열리는
    **트리는 이 경로를 타지 않는다**(sqlite 조회 2번). 캐시를 두지 않는다 — 스캔이 돌면 곧바로
    낡고 「언제 무효화하는가」라는 결정이 새로 생긴다.
- **`_progress`는 밑줄 모듈인 채로 둔다** [제안 후 승인]. GUI도 CLI와 같은 방식으로 직접
  import한다. 공개 API로 승격하지 않으며,
  `static/docs/specs/features/corpbrain-run-status-observability.md` §2의 「이벤트 계약을 공개
  API로 노출하지 않는다」를 유지한다.

### 4.8 설정 영속화 [사용자 결정]
- GUI 설정(최근 폴더·모델명·게이트 값 등)은 **`~/.corpbrain/config.json`의 `gui` 섹션**에
  저장한다. 클라우드 동의 섹션과 나란히 둔다.
- 새 설정 파일을 만들지 않는다 — 사용자가 어디를 봐야 하는지 헷갈리지 않게 하고, 코어의 기존
  읽기·쓰기 관용구를 그대로 쓴다.
- 브라우저 `localStorage`를 설정 저장소로 쓰지 않는다 — 브라우저를 바꾸거나 시크릿 창에서 열면
  사라지고 CLI와 값을 공유할 길이 없다.
- **쓰기는 「직전 재읽기 → 자기 섹션만 교체 → 임시파일 후 `rename`」 순으로 한다**
  [T13 · 사용자 결정]. 이 규칙은 `gui` 섹션과 기존 `cloud_consent` 섹션 **양쪽에 적용한다.**
  - 막으려는 것: GUI 서버가 떠 있는 동안 사용자가 다른 터미널에서 동의를 승인·철회했을 때
    **나중에 쓴 쪽이 상대 섹션을 통째로 날리는** 것이다. 동의가 조용히 철회되면 클라우드 스캔이
    막히고 원인이 드러나지 않는다.
  - **`consent.py`는 이미 이 관용구로 돼 있다** [제안 후 승인 · 2026-08-27 정정]. 초판은
    「양쪽이 «읽기 → 수정 → 통째로 쓰기»를 한다」고 적었으나 그 전제는 사실이 아니다 —
    `_read_document_for_update()`가 갱신 직전에 다시 읽고, `_with_provider()`가 자기 provider
    항목만 교체하며, `_write_document()`가 mkstemp + fsync + `os.replace`로 원자적으로 기록한다
    (`consent.py:130`·`:158`·`:189`). 막으려던 사고는 **한쪽에서는 이미 막혀 있다.**
  - 따라서 이 결정의 실질은 **「GUI가 같은 관용구를 쓴다」**이며, 구현은 그 쓰기 절차를
    `gui`·`cloud_consent` 두 섹션이 **공유하는 헬퍼 하나로 뽑아** 쓴다. 복사해 두 벌로 두지
    않는다 — 한쪽만 고쳐지는 순간 위 성질이 한쪽에서만 성립하고, 그 어긋남은 설정이 사라진
    한참 뒤에야 드러난다.
  - `rename`은 같은 파일시스템 안에서 원자적이라 **반쯤 쓰인 설정 파일**이 남지 않는다.
  - **파일 락을 두지 않는다** — POSIX `fcntl`과 Windows `msvcrt` 분기를 코어에 들이게 되는데,
    현재 코어의 플랫폼 분기는 파일 숨김 처리 한 곳뿐이고 설정 저장 빈도에 비해 과하다.
  - **남는 이론적 레이스**(재읽기와 `rename` 사이)는 알려진 한계로 둔다. 단일 사용자가 설정을
    바꾸는 드문 순간에만 성립한다.
  - **GUI 설정을 별도 파일로 분리하지 않는다** — 위의 「설정 파일이 하나로 유지된다」를 뒤집게
    된다.

### 4.9 클라우드 엔진 [사용자 결정]
- 엔진 선택(local/cloud)과 클라우드 **동의 토글**은 GUI에 둔다. 토글은 기존 `consent.py`를
  그대로 호출한다.
- **API 키는 `ANTHROPIC_API_KEY` 환경변수로만 읽는다.** GUI에서 입력받지 않고 저장하지 않는다.
  키가 없으면 대시보드 Doctor 카드가 「미설정」으로 뜨고 클라우드 스캔을 시작할 수 없다.
- 근거: 지금까지 키를 다루는 지점은 `anthropic_client.resolve_api_key()` 한 곳뿐이다. GUI가
  키를 받으면 그 값이 HTTP 바디로 오가고 서버 프로세스가 키를 쥐게 되어 경계가 넓어진다.

### 4.10 스택 [사용자 결정]
- **서버: 표준 라이브러리 `http.server`**(`ThreadingHTTPServer`). FastAPI·Starlette·uvicorn을
  도입하지 않는다. 신규 런타임 의존성 0이며 `uv.lock`이 늘지 않는다.
  - 근거: 필요한 것은 정적 파일 서빙 + JSON 엔드포인트 + SSE 1개뿐이다. 의존성 4개(전부 문서
    파서)로 운영해 온 「100% 로컬」 제품에 uvicorn·pydantic 스택을 들이는 것은 비율이 맞지
    않는다. 대가는 라우팅·직렬화·오류 처리를 직접 쓰는 것이다.
- **프론트: 바닐라 JS/CSS를 새로 작성한다.** 빌드 스텝을 두지 않으므로 정적 파일이 그대로
  wheel에 들어가고 CI 구조가 바뀌지 않는다.
  - 프로토타입(`gui_preview/variants/minimalist`)에서 가져오는 것은 **디자인 토큰과 관용구뿐**
    이다 — 웜 화이트 모노크롬 팔레트(`--canvas: #FBFBFA` / `--surface: #FFFFFF` /
    `--ink: #111111`), 채도를 뺀 악센트 6종, 파스텔 배지 5쌍, sans/serif/mono **3계열 대비**
    (세리프는 「값」에만, 작은 라벨은 UPPERCASE + letter-spacing), 플랫 벤토 카드
    (`1px solid --border` + `--radius-lg` + 거의 안 보이는 그림자 2종), 사이드바 264px /
    2줄 헤더 114px.
  - 마크업·상태 관리·데이터 바인딩은 **실제 코어 타입에 맞춰 새로 쓴다.** 프로토타입의 목업
    데이터 구조를 이식하지 않는다.
  - 프로토타입을 포크하지 않는 근거: 뷰 6개가 한 HTML에 동시 존재하고 `.active` 토글로
    전환되어 라우팅이 없으며, 디자인 리뷰가 미해결로 기록한 결함(프로젝트 전환 시 스캔 상태
    미리셋, 위키 트리 검색창 미배선)과 목업 타입 불일치(§4.11)를 함께 상속한다.
- **Zero External CDN을 유지한다** [제안 후 승인]. 폰트·스크립트·스타일·그래프 엔진을 전부
  로컬 자산으로 번들한다. 프로토타입이 이미 지킨 제약이며 「100% 로컬」 원칙의 일부다.
- **서버는 CLI와 동급의 얇은 어댑터다** [제안 후 승인]. 비즈니스 로직을 두지 않고 코어 호출·
  JSON 직렬화·경로 해석·상태코드 매핑만 한다. 코어/CLI 이음새(MVP 스펙 §4.5)를 그대로 계승하며,
  코어는 GUI의 존재를 알지 못한다.

### 4.10.3 서버의 테스트 가능한 이음새 [TH1 · 사용자 결정]
요청 처리를 **순수 함수**로 뽑고, `http.server` 핸들러는 그 함수를 부르기만 한다.

```python
def handle(
    method: str,
    path: str,
    headers: Mapping[str, str] | None = None,
    body: bytes = b"",
) -> Response: ...
```

- **`headers`·`body`는 기본값을 갖는다** [제안 후 승인 · 2026-08-27 추가]. 초판은 넷을 전부
  필수로 적었으나, 본문 없는 조회를 단언하는 테스트가 매번 `b""`를 손으로 넘기게 되어 요지와
  무관한 잡음이 늘었다. 계약(무엇을 받아 무엇을 돌려주는가)은 바뀌지 않는다 (issue #57 · D1).
- `path`는 **쿼리를 포함한 요청 대상**이다(`/api/dashboard?token=…`). 쿼리 분리와 헤더 이름
  소문자 정규화는 이 함수 안에서 한다 — 호출자가 전처리를 나눠 갖지 않는다.
- `Response`는 상태코드·헤더·본문을 담는 값 객체다. 함수는 소켓을 모르고 전역 상태를 읽지
  않으며, 필요한 것(스캔 상태·`out_dir`·토큰)은 인자나 생성자로 주입받는다.
- **인증·Origin 검증·라우팅·직렬화·상태코드는 전부 이 함수 안에** 있다. 따라서 §3 항목1·2가
  요구하는 단언이 소켓 없이 결정적으로 성립한다.
- 실제 소켓은 **「정말로 뜨고 붙는다」만 최소로** 확인한다(§3 항목9의 wheel 기동 스모크가 그
  자리를 겸한다).
- **그 기동 스모크는 `watch_sockets` fixture를 쓰지 않는다** [TH3 · 사용자 결정].
  `_fake_connect`는 기록 후 `ConnectionRefusedError`를 던지는 **보안 도구**여서 실제 연결과
  양립하지 않는다. 이는 결함이 아니라 「감시를 우회한 연결은 실패해야 한다」는 의도다.
  - 두 테스트는 목적이 다르다 — 보안 테스트는 「우회한 연결은 실패해야 한다」를, 기동 스모크는
    「서버가 정말 뜨는가」를 본다. 목적이 다른 테스트가 fixture를 공유할 이유가 없다.
  - **watcher에 「허용 목록」 예외를 두지 않는다.** 예외가 하나 생기면 늘어나고, 그때마다
    불변식 테스트가 스스로 약해지는데 그걸 막는 것은 코드리뷰뿐이다.
- 근거: 이 저장소가 이미 세운 관용구 — 표시 로직은 `report.py`의 순수 빌더가 소유하고 정확
  문자열은 단위테스트가 단언하며, 어댑터 테스트는 종료코드와 배선만 본다. 서버는 CLI와 동급
  어댑터이므로 같은 잣대를 댄다.
- `BaseHTTPRequestHandler`를 가짜 소켓으로 돌리는 방식은 택하지 않는다 — 테스트가 `http.server`
  내부 구현에 묶여 서버 계층을 바꾸면 재사용되지 않는다.

### 4.10.5 접근성 기준 [IX7 · 사용자 결정]
- **색은 계승한 토큰만 쓴다.** 새 회색을 임의로 만들지 않는다. minimalist의
  `--text-secondary`·`--text-muted`는 각각 `#787774`(4.3:1, AA 실패)·`#A6A29A`(2.3~2.5:1)에서
  **이미 한 번 재서 올린 값**이며(그 이력이 `style.css` 주석에 남아 있다), 토큰을 벗어나면 그
  비용이 무효가 된다. 본문 대비비는 AA(4.5:1) 이상을 유지한다.
- **클릭 가능한 요소는 전부 키보드로 닿고 포커스 링이 보인다.** 프로토타입이
  `makeActivatable()`로 이미 잡은 문제이며, 새로 쓰는 마크업에서 되살리지 않는다.
- **자동 접근성 검사(axe-core 등)를 도입하지 않는다** — §2가 배제한 Node 툴체인과 CI 브라우저
  구동이 다시 들어온다(Playwright를 배제한 것과 같은 비용).
- 대신 §3 항목12의 **수동 스모크 항목**으로 사람이 확인한다.

### 4.10.1 정적 자산의 배치와 탐색 [T10 · 사용자 결정]
- 자산은 **`corpbrain/gui/static/`** 아래, 즉 **파이썬 패키지 안**에 둔다.
- 런타임 탐색은 **`importlib.resources`** 로 한다. 설치 위치를 계산하거나 `__file__` 상대
  경로를 조립하지 않는다.
- 근거: hatchling의 `packages = ["corpbrain"]` 설정이 그대로 자산까지 거두므로 빌드 설정
  특례가 필요 없고, **`-e` 개발 설치와 wheel 설치가 같은 코드 경로**를 쓴다.
- 저장소 루트에 두고 `force-include`로 끌어오는 방식은 택하지 않는다 — 경로 해석이 개발
  설치와 wheel 설치에서 갈려 분기가 생긴다.
- DoD 9번(wheel에 자산이 들어가고 그 wheel로 기동)이 이 배치를 실제로 검증한다.

### 4.10.2 `gui_preview/` 자산의 처분 [T12 · 사용자 결정]
- **전부 그대로 둔다.** 설계문서 5종도, HTML/CSS/JS 프로토타입 4벌(원본 + 변종 3개)도 이번
  슬라이스에서 삭제·이동하지 않는다.
- **위상은 이 스펙이 가른다**: 실제 구현의 정본은 `corpbrain/gui/`이고, `gui_preview/`는
  **디자인 토큰의 참조원이자 설계 이력**이다(§4.10). 두 곳이 어긋나면 `corpbrain/gui/`가 옳다.
- **수용하는 알려진 대가**: 동작하는 프로토타입 4벌이 실제 GUI 옆에 남아, 시간이 지나며
  실제 구현과 어긋난다. 설계문서 02가 확정한 다크 테마를 minimalist 변종이 이미 뒤집은 전례가
  있으므로 이 어긋남은 실제로 일어난다.
- 삭제하지 않는 이득: 설계문서 03~05가 담은 **멀티 워크스페이스·2-Axis 레이아웃·프로젝트 카드
  IA** 결정은 §2가 비목표로 미룬 것이라 다음 버전에서 다시 쓰인다.

### 4.10.4 화면 상태와 라우팅 [IX1 · 사용자 결정]
- **URL 해시가 화면 상태의 단일 출처다.** `#/graph?node=…` · `#/wiki?doc=…` · `#/search?q=…`
  형식으로 「어느 뷰인가」와 「무엇을 보고 있는가」를 함께 담는다.
- 프론트엔드는 `hashchange`를 듣고 해시에서 화면을 복원한다. 화면 전환은 해시를 바꾸는
  것으로만 일어나며, 뷰 전환 함수를 직접 부르지 않는다 — 그래야 해시와 화면이 어긋나지 않는다.
- 이로써 **새로고침·뒤로가기·링크 공유**가 모두 동작한다. T5가 SSE 재접속을 정상 사건으로
  정의해 새로고침이 흔해지므로 이 성질이 필요하다.
- **해시는 서버로 전송되지 않는다.** `http.server` 라우팅을 한 줄도 건드리지 않는다.
- `history.pushState` 방식은 택하지 않는다 — 서버가 모르는 경로 전부에서 `index`를 내주는
  SPA fallback 규칙이 필요한데, 그러면 §4.3.2가 정한 404 처리와 규칙이 섞인다.
- T6의 부트스트랩 토큰 제거(`history.replaceState`로 **쿼리**를 지움)와 층이 다르므로
  충돌하지 않는다.

### 4.11 프로토타입 ↔ 코어 정합 [제안 후 승인]
목업이 실제 코어와 어긋나 있는 지점을 **코어 값 쪽으로** 맞춘다.

| 지점 | 목업 | 채택 |
|---|---|---|
| 엣지 타입 | `ref` / `entity` / `tag` 3종 | 코어 `EdgeType` 4종 값 그대로. `SEMANTICALLY_SIMILAR`를 더한다 |
| PII 종류 | 6종 (제목은 "7종") | 코어 `PiiType` **7종** — 목업에 빠진 `IP` 포함 |
| PII 라벨 | 「휴대전화번호」 | 코어 값 「전화번호」 |
| PII 플레이스홀더 | `[PII: 휴대전화번호:001]` | 코어 `PiiType.placeholder` 형식 (`[REDACTED_PHONE]`) |
| 지표 | 노드/엣지 `170 / 342` 등 하드코딩 | 전부 실제 값 |

- 근거: `EdgeType` 값은 코드·저장소·출력에서 갈리지 않도록 한 곳이 소유한다는 v0.6 결정이 이미
  있다. 프론트가 자기 리터럴을 갖는 순간 `graph --stats` 출력·DB `type` 컬럼·`--expand-edges`
  플래그와 어휘가 갈린다.

## 5. 엣지 케이스와 실패 시나리오
- **인가되지 않은 요청**: 토큰 부재·불일치는 **401**, 허용되지 않은 `Origin`·`Host`는 **403**.
  이유를 자세히 적지 않는다. 「헤더가 없을 때」의 판정은 §4.2의 표를 따른다 — `Host`는 항상
  필수, `Origin`은 상태를 바꾸는 메서드에서만 필수다. [사용자 결정]
- **스캔 중 새 스캔 요청**: **409**. 진행 중인 스캔은 영향받지 않는다(§4.4). [사용자 결정]
- **스캔 중 브라우저를 닫거나 새로고침**: 스캔은 계속된다. 다시 열면 진행 중인 스캔에 붙는다
  — 스캔 상태는 서버가 소유한다. [사용자 결정]
- **취소 요청**: 진행 중인 문서를 마친 뒤 멈추고 부분 `ScanResult`를 반환한다. 진행 중인 HTTP
  호출은 끊지 않으므로 최대 300초 대기할 수 있다(§4.7). [사용자 결정]
- **첫 실행 — `--out`이 아직 없음** [T11 · 사용자 결정]: 각 화면이 §4.3.2의 구조화된 상태
  본문을 받아 **자기 빈 상태를 그리고** 「먼저 스캔하세요」로 스캔 화면에 보낸다. 탭을 잠그거나
  스캔 화면으로 강제 이동시키지 않는다.
  - 새 규칙이 아니다 — §4.3.2가 이미 「선행 조건 실패는 200 + 안내 문장」으로 정해 뒀고,
    첫 실행은 그 규칙이 자연히 적용되는 경우다. 화면마다 다른 규칙을 만들지 않는다.
  - 강제 이동을 택하지 않는 근거: 「비었지만 유효한 상태」(스캔했으나 전 파일이 스킵된 폴더)와
    「첫 실행」을 가르는 판정이 하나 늘고, 탭 잠금이라는 새 상태가 생긴다.
  - 프로토타입은 그래프 화면에만 빈 상태 문구를 갖고 있다. 나머지 다섯 화면으로 넓힌다.
- **그래프 DB·벡터 인덱스 부재**: 기존 코어 방침을 그대로 노출한다 — 검색은 인덱스가 없으면
  선행 조건 실패, 그래프 DB가 없으면 코사인 단독 + 안내(v0.7 §5). GUI가 새 판정을 만들지
  않는다. [제안 후 승인]
- **그래프 렌더 규모**: 4종 노드를 제한 없이 전부 그린다. `--max` 기본 50문서에서 노드 수백
  개·엣지 수백~천 개가 나오며(실측: 24문서에 `CONTAINS_ENTITY` 엣지만 130개), 프로토타입의
  자작 canvas 물리는 17노드로만 검증됐다. **대규모에서 느려지는 것을 알려진 한계로 수용하고
  후속 이슈로 넘긴다.** 상한·필터·차수 추림을 이번에 만들지 않는다. [사용자 결정]
  - **v0.9.1에서 «읽히는가» 쪽만 손봤다** [2026-08-28 · 문면 정정]. 이 항목이 「느려진다」로
    적어 둔 한계와 별개로, 실제 규모에서 **읽을 수가 없다**는 것이 크리틱(20/40)에서
    드러났다 — 캔버스에 `fillText` 호출이 0회라 노드 식별이 전부 옆 목록에서만 일어났고,
    반지름 식 `min(6, 3 + 차수 × 0.35)`이 **연결 9개에서 상한에 닿아** 허브와 잎이 같은
    크기로 보였다(태그 77개 규모에서는 대다수가 그 구간이다).
    - 세 가지를 바꿨다: 반지름을 제곱근 스케일로(넓이 ∝ 차수) · 엣지 불투명도 0.08 → 0.18
      (선택 시 0.7 / 0.05로 분기) · 차수 상위 12개에 라벨. 범례에 「크기 = 연결 수」를 더했다.
    - **색은 한 값도 바꾸지 않았다.** 라벨 글꼴·색은 `--font-sans`·`--text-secondary`,
      겹친 원을 가르는 테두리는 `--surface` — 전부 기존 토큰이다(§4.10.5).
    - **상한·필터·차수 추림은 여전히 만들지 않았고 issue #58 그대로다.** 노드는 제한 없이
      전부 그린다. 이번 변경은 「무엇을 그리는가」가 아니라 「그린 것이 읽히는가」다.
    - 결정적 배치·전환 없음·포커스 링 단일 소유는 그대로다.
- **API 키 미설정 상태의 클라우드 스캔**: Doctor 카드가 「미설정」으로 뜨고 스캔을 시작할 수
  없다. GUI가 키를 받아 해결해 주지 않는다(§4.9). [사용자 결정]
- **`~/.corpbrain/config.json` 손상**: 코어의 기존 방침을 따른다 — 자동 복구하지 않는다.
  [제안 후 승인]
- **열람 API가 접근할 수 없는 디렉터리**: 권한 거부를 그대로 보고하고 서버를 죽이지 않는다.
  [제안 후 승인]
- 기존 스펙들의 실패 방침(개별 파일 실패를 전체 실패로 위장하지 않음, 선행 조건 실패는 비-0,
  저장소 손상은 자동 복구하지 않음)은 그대로 유지된다.
