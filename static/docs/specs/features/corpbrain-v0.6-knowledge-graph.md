# 스펙: CorpBrain v0.6 — 지식그래프 (문서 중심 4종 엣지 · 관련 문서 상호연결)

- 상태: 완료
- 최종 갱신: 2026-08-23

## 1. 목표
v0.1~v0.5로 완성된 스캔→요약→위키 렌더→벡터 인덱싱 파이프라인 위에, 문서 사이의 관계를
결정적으로 계산해 저장하는 지식그래프 계층을 얹는다. 지금까지 각 위키 문서는 서로 단절된
섬이었다. v0.6은 문서·엔티티·태그를 노드로, 태그 소속·엔티티 포함·시맨틱 유사도·명시적
참조를 엣지로 하는 그래프를 `scan` 과정에서 함께 만들고, 그 결과를 ① 각 위키 마크다운의
「관련 문서」 섹션과 ② `corpbrain graph` 조회 명령 두 경로로 드러낸다. 로컬 우선 원칙과
단일 게이트웨이 불변식은 그대로 유지하며, 그래프 계산 자체는 추가 LLM 호출과 추가 네트워크
연결을 발생시키지 않는다. [사용자 결정]

## 2. 비목표
이번 슬라이스에서 다음은 하지 않는다.

- **GUI 일체** — FastAPI/Starlette 로컬 서버, SSE 이벤트 브리지, `corpbrain gui` 명령,
  6대 화면 프론트엔드, 멀티 워크스페이스(프로젝트 전환), 상단 탭 기반 레이아웃. `gui_preview/`
  아래 설계 문서 5종과 HTML 프로토타입은 v0.7 이후의 참고 자료일 뿐이며 이 스펙의 구현
  대상이 아니다. [사용자 결정]
- **`RELATES_TO` 엣지(엔티티 ↔ 엔티티)** — 문서에 적혀 있지 않은 관계를 LLM이 추론해야 해
  문서당 추가 호출이 들고 같은 입력에도 결과가 달라진다. 기계 판정 가능한 완료의 정의를
  세울 수 없어 제외한다. [사용자 결정]
- **LLM 기반 엔티티 동의어 병합** (`인사팀` = `HR팀` 판정). 위와 같은 이유. [제안 후 승인]
- **엔티티 → 태그 엣지.** `gui_preview` 프로토타입 목업 데이터에는 존재하나 이번 범위 밖.
  [제안 후 승인]
- **그래프 가중치를 결합한 하이브리드 검색.** `corpbrain search`는 v0.4의 코사인 top-k
  그대로 둔다. [제안 후 승인]
- **별도 `graph build` 명령.** 그래프 빌드는 `scan`에 통합되며 독립 빌드 명령을 두지 않는다.
  [사용자 결정]
- **매개 중심성 등 고급 그래프 지표.** `--central`은 연결 차수만 다룬다. [제안 후 승인]
- **그래프 DB 스키마 마이그레이션** — 손상되거나 구버전 스키마면 자동 복구하지 않고 에러 +
  재생성 안내만 한다(§5). v0.4가 벡터 인덱스에 대해 정한 것과 같은 방침이다. [사용자 결정]

## 3. 완료의 정의
픽스처 코퍼스를 **태그 공유 쌍 · 엔티티 공유 쌍 · 명시적 파일명 참조 · 고유사도 쌍 ·
고립 문서**가 각각 최소 1개씩 존재하도록 구성하고, `corpbrain scan <fixture> --out <tmp>`
실행 시 아래를 모두 만족한다. [제안 후 승인]

1. `<out>/.corpbrain_graph.sqlite`가 생성되고, 저장된 노드·엣지의 `(type, src, dst)` 튜플
   집합이 기대 집합과 정확히 일치한다.
   - 검증: 통합테스트가 DB를 직접 읽어 튜플 집합을 단언.
2. 생성된 모든 `.md`가 「관련 문서」 섹션을 포함하고, 항목 순서가 §4.5의 계층적 정렬 규칙과
   일치하며 항목 수가 `--related-top-k` 이하다. 고립 문서는 `관련 문서 없음`으로 렌더된다.
   - 검증: 생성물 파싱으로 섹션 존재·항목 순서·개수 확인.
3. `corpbrain graph --out <tmp> --stats` 출력의 노드·엣지 종류별 개수가 DB 실측과 일치하고,
   `--neighbors <상대경로>`가 해당 문서의 4종 엣지를 모두 출력하며, `--central`이 연결 차수
   내림차순을 출력한다.
   - 검증: CLI 통합테스트로 stdout 단언.
4. **결정성**: 동일 입력으로 두 번 실행하면 그래프 DB 내용과 모든 `.md`가 동일하다.
   두 번째 실행은 재요약도 하지 않고(§4.2 mtime 규칙) 관련 문서도 달라지지 않아 파일을
   다시 쓰지 않으므로(§4.5) `generated_at`까지 바이트 동일하다. `--force`를 준 2회 실행을
   비교할 때만 `generated_at`을 제외한다.
   - 검증: 2회 실행 후 DB 튜플 집합과 파일 내용을 비교(무옵션·`--force` 두 경우 모두).
5. 벡터 인덱스가 없는 상태에서 `SEMANTICALLY_SIMILAR` 엣지가 0개이고 나머지 3종은 정상
   생성되며, 종료 코드 0과 함께 종료 요약에 생략 사유가 1줄 나온다.
   - 검증: 게이트웨이 스텁으로 Ollama 부재를 만든 통합테스트.
6. 엔티티가 없는 v0.5 산출물이 이미 있는 `out_dir`에 대해 `scan` 실행 시 재요약이 발생하지
   않고(mtime 규칙대로 스킵), 안내 문구가 출력되며 종료 코드 0이다.
   - 검증: v0.5 형식 위키를 미리 배치한 뒤 실행해 LLM 호출 횟수 0과 안내 문구를 단언.
7. 정규화에 의해 `인사팀`과 `인사 팀`이 단일 `Entity` 노드로 병합된다.
   - 검증: 정규화 함수 단위테스트 + 그래프 빌드 통합테스트.
8. **네트워크 불변식 유지** — 그래프 빌드 단계에서 로컬 Ollama 외 소켓 연결이 0건이고,
   `corpbrain graph`는 소켓을 **하나도** 열지 않는다.
   - 검증: `tests/security/test_network_invariant.py`에 케이스 2개를 추가한다 [사용자 결정] —
     ① 그래프까지 도는 `scan`의 목적지 집합이 localhost뿐 ② `graph` 단독 실행은 소켓 0건
     (§4.7에서 순수 조회로 확정했으므로 네트워크가 아예 없어야 한다. `plan_scan`에 대해 이미
     세워 둔 "소켓 0건" 단언과 같은 종류다).
   - 새 파일로 분리하지 않는다 — 소켓 패치 관용구가 복제되고, 감시장치가 공허하게 통과하지
     않음을 증명하는 기존 `test_watcher_flags_a_gateway_bypass`의 보호를 받지 못한다.

검증 방식(전반): 그래프 빌더·엔티티 정규화·관련 문서 정렬은 단위테스트, 파이프라인 통합은
`gateway.request_json`을 스텁한 채 코어 API를 직접 호출하는 통합테스트로 검증하고, 마무리로
실제 모델 1회 수동 스모크를 실행해 `docs/SMOKE.md`에 시나리오와 실행 기록을 추가한다.
[제안 후 승인]

픽스처 구성 [사용자 결정]: 자동 테스트와 수동 스모크의 요구가 달라 픽스처를 분리한다.
- **자동 테스트**는 `tmp_path`에 코퍼스를 인라인 생성한다(`tests/integration/test_cloud_engine.py`·
  `test_indexing.py`가 이미 쓰는 방식). 통합테스트에서 태그·엔티티·벡터는 파일 내용이 아니라
  `gateway.request_json` 스텁이 결정하므로, 4종 엣지 중 실제 파일 텍스트에 의존하는 것은
  `REFERENCES`뿐이다. 인라인으로 두면 스텁 값과 기대 엣지가 같은 파일에 나란히 놓여
  "이 문서 쌍이 왜 유사한가"가 코드에 드러난다.
- **기존 테스트 영향** [사용자 결정]: `parse_wiki_markdown`의 반환이 3-튜플로 바뀌므로
  언패킹 지점 네 곳(`tests/unit/test_embedding_text.py:52`·`:70`·`:92`,
  `corpbrain/core/pipeline.py`의 `_backfill_embedding`)을 한 줄씩 고친다. `SECTION_HEADERS`를
  순회하는 네 지점은 위 렌더러 결정에 따라 수정이 필요 없다.
- **인라인 코퍼스 구성** [사용자 결정]: 문서 6개짜리 **단일 코퍼스** 하나로 아래 11가지를
  모두 덮는다. DoD 항목1이 "튜플 집합이 기대 집합과 정확히 일치"라는 전체 그래프 단언이므로
  코퍼스가 하나여야 성립한다. 비교 연산자·정규화·정렬 같은 순수 로직은 단위테스트가 따로
  덮으므로 코퍼스는 end-to-end만 증명한다.

  ```
  인사/채용계획.docx   A      개발/아키텍처.md   C      개발/README.md   E
  인사/온보딩.md       B      개발/벡터설계.md   D      기타/메모.txt    F
  ```

  | 쌍·문서 | 심는 것 | 덮는 대상 |
  |---|---|---|
  | A ↔ B | 태그 `인사` 공유 · 엔티티 `인사팀` 공유 · 유사도 0.81 · 양방향 참조 | 태그 공유 · 엔티티 공유 · 고유사도 · 양방향(§4.1) |
  | C ↔ D | 유사도 **정확히 0.75** · 태그 `설계` 공유 | 임계치 경계 포함(§4.1 `>=`) |
  | C → E | 단방향 참조 | 명시적 파일명 참조 |
  | A ↔ C | 유사도 0.30 | 임계치 미만 제외 |
  | E | 본문에 자기 파일명 `README.md` 등장 | 자기 루프 제외(§4.1) |
  | E | 스텁 응답에서 `entities` 키를 뺌 | 선택 필드 처리(§4.2) |
  | F | 고유 태그·고유 엔티티·저유사도·참조 없음 | 고립 문서 → `관련 문서 없음` |
  | `인사/` `개발/` `기타/` | 하위 폴더 3개 | 출력 트리 미러링(v0.1) |
- **임베딩 스텁의 벡터 설계** [사용자 결정]: 스텁은 코사인이 아니라 벡터를 돌려주므로,
  의도한 유사도를 결정적으로 얻는 방법을 고정한다.
  - 벡터는 **짧은 직교 기저 조합**으로 만든다(실제 768차원이 아니라 3~4차원이면 충분하다 —
    코사인만 의도대로 나오면 되고 짧을수록 테스트가 읽힌다).
  - **임계치 경계 케이스는 `--similarity-threshold`를 실측 코사인 값으로 준다.** 벡터에서
    코사인을 역산하면 `0.7499999999999999`처럼 부동소수 오차가 남아 `>=` 판정이 뒤집힐 수
    있다. 계산된 그 값을 그대로 임계치로 주면 왕복 오차 없이 "같은 값을 포함하는가"만
    정확히 검증된다.
    ```python
    THRESHOLD = _cosine_similarity(VECTORS["개발/아키텍처.md"], VECTORS["개발/벡터설계.md"])
    # C~D 는 `>=` 이므로 이 임계치에서 반드시 엣지를 가져야 한다
    ```
  - 코사인 계산 자체의 정확성은 `tests/unit/test_vectorstore.py`가 이미 덮으므로 여기서
    다시 검증하지 않는다.
- **수동 스모크 시나리오** [사용자 결정]: `docs/SMOKE.md`에 **실행 H** 하나를 추가한다.
  스텁이 원리적으로 증명할 수 없는 것만 겨냥하고, 자동 테스트를 복창하지 않는다.
  1. **실제 모델이 `entities`를 채워 주는가** — §4.2에서 선택 필드로 뒀으므로, 모델이 늘
     비워 보내도 통합테스트는 전부 통과하지만 실사용 그래프에는 `CONTAINS_ENTITY` 엣지가
     하나도 생기지 않는다.
  2. **실제 `nomic-embed-text` 분포에서 기본 임계치 `0.75`가 합리적인가** — 너무 낮으면 모든
     문서가 서로 연결되어 「관련 문서」가 무의미해지고, 너무 높으면 엣지가 0개다. 스텁 벡터로는
     알 수 없으며, **기본값을 바꿔야 할지 판단할 유일한 근거**다.
  3. **「관련 문서」 목록이 사람이 보기에 납득되는가** — 순위 규칙(§4.5)이 실제 문서에서
     쓸 만한 순서를 내는지.
  - 온디스크 코퍼스는 위 인라인 코퍼스와 같은 6문서 구조를 실제 파일로 만들되, 내용은 실제
     모델이 엔티티를 뽑을 만한 한국어 문서로 채운다.
  - 부분 그래프(Ollama 없이 cloud)는 §3 항목5가 스텁으로 이미 덮으므로 수동 절차로 옮기지
     않는다.
- **수동 스모크**용으로만 관계를 갖춘 온디스크 코퍼스를 새로 추가한다. 기존
  `tests/fixtures/sample_corpus/`는 세 테스트 파일이 공유하고 있고, 2026-08-22에 스모크
  산출물이 그 폴더를 오염시켜 통합테스트 3건을 깨뜨린 사고가 있었으므로 확장하지 않는다.

## 4. 인터페이스 계약

### 4.1 그래프 모델 [사용자 결정]
- 노드 3종: `Document`, `Entity`, `Tag`.
- 엣지 4종:

| 엣지 | 방향 | 가중치 | 재료 |
|---|---|---|---|
| `TAGGED_WITH` | 문서 → 태그 | 없음 | `doc_facts.tags_json` (← `SummaryResult.tags`) |
| `CONTAINS_ENTITY` | 문서 → 엔티티 | 없음 | `doc_facts.entities_json` (← `SummaryResult.entities`, 신규 필드) |
| `SEMANTICALLY_SIMILAR` | 대칭 | 코사인 유사도 | v0.4 벡터 인덱스 |
| `REFERENCES` | 방향 있음 | 없음 | `doc_facts.refs_json` (← 요약 입력 텍스트, §5) |

엣지는 `SummaryResult`가 아니라 **`doc_facts`에서 파생한다**(§4.4). 스킵된 문서는 이번 실행에
`SummaryResult`가 없지만 `doc_facts`에는 재료가 남아 있어 그래프에 계속 참여한다.

- **노드 ID 체계** [사용자 결정]
  - `Document` 노드 id = **원문 절대경로 문자열**. v0.4 벡터스토어의 `doc_id`와 같은 키를
    쓰므로 `SEMANTICALLY_SIMILAR` 조인에 좌표 변환이 필요 없고, 고아 정리(`is_relative_to`)
    선례를 그대로 계승한다.
  - `Entity` 노드 id = `entity:<정규화키>`, `Tag` 노드 id = `tag:<정규화키>` — 타입 접두사로
    문서 경로와 충돌하지 않는다. 정규화 키는 §4.3을 따른다.
  - `graph --neighbors`가 받는 상대경로는 **CLI 어댑터가 절대경로로 해석해** 코어에 넘긴다.
    코어는 경로 해석 책임을 지지 않는다(코어 no-I/O 불변식).
- **자기 자신을 향하는 엣지는 종류를 불문하고 만들지 않는다** [사용자 결정]. 판정은 `doc_id`
  동일성으로 한다. 자기 루프는 어느 엣지 종류에서도 정보가 없고, 있으면 순위 규칙 ①에 걸려
  모든 문서의 「관련 문서」 1순위가 자기 자신이 된다. 자기 파일명을 본문에서 언급하는 문서
  (`README.md`가 "이 파일(README.md)은…"이라고 쓰는 경우)는 실제로 흔하다.
- **`REFERENCES` 방향 처리** [사용자 결정]: 두 문서가 서로를 언급하면 **엣지 두 행**(A→B,
  B→A)을 그대로 둔다. `REFERENCES`는 4종 중 유일하게 방향이 작성자의 의도를 담은 엣지이므로
  병합하면 이 엣지를 따로 둔 목적이 사라진다. `SEMANTICALLY_SIMILAR`가 대칭이라 한 행인 것과는
  엣지 성격의 차이이지 세는 방식의 불일치가 아니다.
- **`SEMANTICALLY_SIMILAR` 생성 규칙** [사용자 결정 · 제안 승인]
  - **비교는 `>=`(이상)** 이다. 코사인이 임계치와 정확히 같은 쌍은 엣지를 만든다.
    `gui_preview/02` View 3의 "유사도 75% 이상"과 같은 해석이다. 테스트는 정확히 임계치인
    쌍을 일부러 만들어 이 경계를 고정한다.
  - **자기 자신 쌍은 제외**하되 판정 기준은 유사도 값이 아니라 **`doc_id` 동일성**이다.
    내용이 같은 별개 파일(`보고서.txt`와 `보고서_사본.txt`)은 코사인이 `1.0`이어도 서로 다른
    문서이므로 정상적으로 엣지를 가져야 한다.
  - **대칭 엣지는 `edges`에 한 행만 저장한다.** `src < dst`로 정렬된 `doc_id` 조합을 쓰고,
    `neighbors(node_id)`가 `src`·`dst` 양쪽을 조회한다.
    - 이렇게 해야 `--stats`의 유사도 엣지 수가 사람이 세는 관계 수와 일치하고, 방향이 있는
      나머지 3종과 세는 방식이 갈리지 않는다. 두 행으로 저장하면 같은 그래프의 유사도
      엣지만 2배로 보고된다.
    - 전 쌍 계산도 `i < j` 조합으로 한 번씩만 수행해 같은 쌍을 두 방향으로 계산하는 일이
      없게 한다.
- 네 종류 모두 추가 LLM 호출이 0이고 결과가 결정적이다. [제안 후 승인]
- 그래프의 대상은 이번 실행에서 처리한 문서가 아니라 **`--out`에 존재하는 위키 전체**다.
  [제안 후 승인]

### 4.2 요약 JSON 스키마 확장 [제안 후 승인]
기존 고정 필드(`title`, `one_line_summary`, `key_points`, `summary`, `tags`)에 `entities`
배열을 추가한다. 별도 LLM 호출을 만들지 않고 같은 요약 호출의 반환 필드만 늘린다.

- **`entities`는 선택 필드다** [사용자 결정]. 응답에 없으면 `LLMParseError`가 아니라 빈
  배열로 본다. 그 문서는 위키가 정상 생성되고 `CONTAINS_ENTITY` 엣지만 갖지 않는다.
  - 근거: `entities`는 §4.5 위키 템플릿의 어느 섹션에도 렌더되지 않는 **그래프 전용
    재료**다(§4.4 — 엔티티는 그래프 DB에만 영속). 위키 생성의 선행 조건으로 삼을 근거가
    없고, 재료가 없으면 그 엣지만 빠지는 것이 §5의 다른 «재료 부재» 처리와 일관된다.
  - 기존 5필드는 전부 템플릿에 직접 렌더되므로 **종전대로 필수**다.
  - 필수로 두면 프롬프트로만 요청받는 로컬 모델이 필드를 빠뜨렸을 때 제목·요약·태그를
    모두 정상 수신했음에도 그 문서의 위키가 통째로 생성되지 않고, 같은 모델이면 재실행에서도
    반복된다.
- **두 엔진에 같은 규칙을 적용한다** [사용자 결정]. `validate_summary_fields` 공유를 그대로
  유지해 엔진에 따라 위키 품질 기준이 갈리지 않게 한다(v0.5 §4.3). 엔진별로 필수 여부를
  달리하면 같은 폴더를 `--engine local`로 돌렸을 때와 `cloud`로 돌렸을 때 생성되는 위키
  개수가 달라진다.
- 요청 자체는 양쪽에서 한다:
  - `llm/summarize.py`의 `PROMPT_TEMPLATE` JSON 스키마에
    `"entities": ["문서에 등장하는 인물·부서·시스템·프로젝트명 (문자열 배열)"]`을 추가한다.
  - `llm/anthropic_client.py`의 `SUMMARY_TOOL_SCHEMA` `properties`에 `entities`를 추가하되
    **`required`에는 넣지 않는다**.

### 4.3 엔티티 정규화 [사용자 결정]
- 정규화 키 = 유니코드 NFC + 소문자화 + **모든 공백 제거**. 같은 키를 갖는 엔티티는 단일
  노드로 병합한다.
- 표시 라벨은 최다 등장 형태를 쓰고, 동점이면 사전순으로 결정한다.

### 4.4 저장 [제안 후 승인]
- 그래프는 `<out_dir>/.corpbrain_graph.sqlite`에 저장한다. v0.4의 `.corpbrain_index.sqlite`와
  별도 파일로 두며, 한쪽만 삭제해 재구축할 수 있다.
- **`VectorStore` Protocol 확장** [사용자 결정]: 유사도 엣지 계산을 위해
  `iter_vectors() -> Iterator[tuple[str, list[float]]]`를 `VectorStore` Protocol에 추가하고
  `SqliteVectorStore`와 `_NoIndexStore`(빈 이터레이터)에 구현한다. 그래프 빌더는 sqlite를
  직접 열지 않고 이 인터페이스로만 벡터에 접근한다 — v0.4가 세운 저장소 어댑터 이음새를
  유지해 후속 저장소 교체가 그래프까지 자동으로 따라오게 한다.
  - 전 쌍 코사인은 O(n²)이며, **규모 가드는 기존 `--max`(기본 50)가 겸한다**(50개 → 1,225쌍).
    별도 상한을 두지 않으며, `--max`를 크게 올리면 비용이 함께 커지는 것은 알려진 특성이다.
- v0.4 `VectorStore` Protocol 패턴을 따라 `GraphStore` Protocol + `SqliteGraphStore` 구현을
  둔다. 파이프라인과 `graph` CLI는 이 인터페이스 타입에만 의존하고 구체 구현(`sqlite3` 기반)을
  직접 참조하지 않는다.
- **`GraphStore` 어댑터 인터페이스 계약** [사용자 결정]: 8메서드로 구성한다. v0.4가 최초
  3메서드로 적었다가 코드리뷰에서 누락이 드러나 6메서드로 넓힌 전례가 있어(v0.4 스펙 §4)
  이번에는 스펙이 요구하는 사용처에서 역산해 처음부터 전부 적는다.

  | 메서드 | 요구 근거 |
  |---|---|
  | `upsert_facts(doc_id: str, facts: DocFacts) -> None` | `doc_facts` 증분 upsert |
  | `get_facts(doc_id: str) -> DocFacts \| None` | 재료 복원 fallback 판정(행 존재 여부) |
  | `iter_facts() -> Iterator[DocFacts]` | `nodes`·`edges` 파생의 입력 |
  | `delete_facts(doc_id: str) -> None` | 위키가 사라진 문서의 유령 노드 제거 (v0.4 고아 벡터 정리 계승) |
  | `replace_graph(nodes, edges) -> None` | §5의 단일 트랜잭션 재빌드 |
  | `stats() -> GraphStats` | §4.7 `--stats` |
  | `neighbors(node_id: str) -> list[Edge]` | §4.7 `--neighbors` |
  | `degree_ranking() -> list[tuple[str, int]]` | §4.7 `--central` |
  | `close() -> None` | 저장소가 쥔 자원 정리 (v0.4 계약 계승) |

  「관련 문서」 계산은 패스2가 방금 만든 그래프를 메모리에서 그대로 쓰므로 별도 조회
  메서드를 두지 않는다.
- **재빌드 전략** [사용자 결정]: 재료는 증분 보존, 파생물은 매 실행 전체 재생성한다.
  - `doc_facts`(문서에서 추출한 사실 — 태그·엔티티·참조 목록)는 재요약된 문서만 upsert하고
    나머지는 그대로 둔다. 스킵된 문서의 엔티티가 이 테이블에 남아 그래프에 계속 참여한다.
  - `nodes`·`edges`는 매 실행 통째로 비우고 `doc_facts`와 벡터 인덱스로부터 다시 파생한다.
    임계치나 문서 집합이 바뀌어도 옛 엣지가 남지 않아 §3 항목4(결정성)를 만족한다.
- **스키마** [제안 후 승인]:
  ```sql
  doc_facts(doc_id TEXT PRIMARY KEY, title TEXT, tags_json TEXT,
            entities_json TEXT, refs_json TEXT, updated_at TEXT)   -- 증분 upsert
  nodes(id TEXT PRIMARY KEY, type TEXT, label TEXT, props_json TEXT)  -- 매 실행 재빌드
  edges(src TEXT, dst TEXT, type TEXT, weight REAL,
        PRIMARY KEY(src, dst, type))                                  -- 매 실행 재빌드
  meta(key TEXT PRIMARY KEY, value TEXT)                              -- schema_version 등
  ```
- **재료 복원 fallback** [사용자 결정]: `doc_facts`에 행이 없는데 위키가 존재하는 문서
  (v0.5 이하 산출물, 그래프 DB만 삭제, 위키 폴더만 복사 등)는 위키 마크다운을 파싱해
  `# 제목`과 「태그·키워드」 섹션에서 복원 가능한 재료를 채워 `doc_facts`에 upsert한다.
  엔티티는 위키에 남지 않으므로 빈 배열이 된다. 파싱 비용은 문서당 1회뿐이며 이후 실행은
  정상 경로를 탄다. 이로써 v0.5 산출물에서도 태그·참조·유사도 3종이 동작하는 부분 그래프를
  얻는다(§5 「엔티티가 없는 기존 위키」와 같은 취지).
- **`embedding_text.parse_wiki_markdown` 확장** [사용자 결정]: 「관련 문서」를 파서가 알되
  임베딩 입력에서는 제외한다는 것을 코드에 명시한다.
  - `_ALL_SECTIONS`에 `"## 관련 문서"`를 추가한다. 추가하지 않으면 이 섹션과 마커·불릿이
    직전 `## 원문` 섹션의 내용으로 흡수된다. 현재는 `## 원문`이 `_EMBEDDABLE_SECTIONS`에
    없어 결과적으로 무해하지만 그것은 우연이며, 언젠가 `## 원문`을 임베딩에 포함시키면
    **유사도 → 관련 문서 → 임베딩 → 유사도의 피드백 루프**가 생겨 §3 항목4(결정성)가
    무너진다. 동시에 갓 생성된 문서와 백필된 문서의 임베딩 텍스트가 어긋나 이 함수의
    독스트링이 경계한 랭킹 불안정이 발생한다.
  - 반환값을 `(제목, 임베딩 입력 텍스트, 태그)`로 확장해 §4.4의 재료 복원 fallback이 같은
    파서를 쓴다. 마크다운 구조 지식이 한 파일에 모이고, 호출부는 `_backfill_embedding`
    한 곳뿐이라 수정 비용이 작다.
- 문서별 엔티티 목록은 **그래프 DB에만** 영속한다. 위키 front-matter와 본문에는 남기지
  않는다. [사용자 결정]

### 4.5 위키 출력 템플릿 변경 [사용자 결정]
기존 필수 섹션 뒤에 「관련 문서」를 추가한다. v0.1 스펙 §3 항목2가 세는 방식(`# 제목` 포함)
으로는 **7번째 필수 섹션**이고, `render.py`의 `SECTION_HEADERS` 튜플(`## ` 헤더만 담는다)
기준으로는 **6번째 원소**다. 두 셈이 다르므로 아래에서는 튜플 기준으로 말한다.

```markdown
<!-- corpbrain:related:start -->
## 관련 문서
- [<제목>](<--out 기준 상대경로>) — 유사도 0.81 · 공유 태그 `인사` · 공유 엔티티 `인사팀`
- [<제목>](<--out 기준 상대경로>) — 이 문서를 참조함
<!-- corpbrain:related:end -->
```

- **기계 관리 마커 블록** [사용자 결정]: 「관련 문서」는 `<!-- corpbrain:related:start -->` 와
  `<!-- corpbrain:related:end -->` 사이의 블록으로 정의한다. 패스3은 **마커 사이만** 교체하고,
  마커가 없으면 탐색하지 않고 파일 끝에 블록 전체를 추가한다. 기존 본문은 건드리지 않는다.
  - 이 규칙 없이 `## 관련 문서` 헤딩을 탐색하면, 요약문 안에 그 문자열이 들어간 문서
    (CorpBrain 자신이나 이 스펙을 스캔한 경우 실제로 발생한다)에서 뒤따르는 「태그·키워드」·
    「원문」 섹션이 조용히 잘려 나간다. `rerun.py`가 front-matter 블록을 먼저 잘라내도록
    고친 것과 같은 종류의 사고다.
  - 마커는 CommonMark 주석이므로 렌더된 화면에는 나타나지 않는다.
  - 사용자가 마커를 지우면 다음 실행에 블록이 하나 더 추가되어 섹션이 중복될 수 있다.
    가시적이고 복구가 쉬운 실패이므로 데이터 손실보다 낫다고 보고 수용한다.
- **렌더러가 빈 블록을 소유한다** [사용자 결정]: `render_markdown()`이 처음부터 마커와
  `관련 문서 없음`을 함께 렌더하고, `render.py`의 `SECTION_HEADERS`에 `"## 관련 문서"`를
  추가한다. 패스3은 그 블록을 채우기만 한다.
  - "코드가 템플릿을 소유하므로 섹션 누락이 불가능하다"는 `render.py`의 성질이 7번째
    섹션까지 그대로 확장되고, §3 항목2(모든 `.md`에 섹션 존재)가 렌더 단계에서 이미
    보장된다.
  - `SECTION_HEADERS`를 순회해 단언하는 기존 네 지점(`tests/unit/test_render.py:60`·`:90`,
    `tests/integration/test_pipeline.py:96`, `tests/integration/test_pdf_pipeline.py:109`)이
    수정 없이 새 섹션까지 커버한다.
  - 갓 생성된 위키에는 마커가 항상 있으므로, 위의 "마커가 없으면 파일 끝에 추가" 경로는
    §4.4로 복원하는 v0.5 이하 산출물에서만 쓰인다.
  - 이 방식은 재요약된 문서·스킵된 문서·§4.4로 복원한 v0.5 산출물 **세 경로를 모두 같은
    코드로 처리한다** — `SummaryResult`를 필요로 하지 않으므로 전면 재렌더 방식과 달리
    구현 경로가 하나로 유지된다.
- **내용이 달라졌을 때만 기록한다** [사용자 결정]: 마커 교체를 위해 어차피 파일 전체를
  읽으므로, 교체 결과 문자열을 기존 내용과 비교해 다를 때만 쓴다. 재실행 시 관련 문서가
  바뀌지 않은 대다수 위키는 mtime이 그대로 유지되어, 동기화 도구가 매 실행마다 위키
  전체를 변경으로 보고 다시 전송하는 일이 없다. 비교 비용은 이미 손에 든 두 문자열의
  비교 한 번뿐이다.
- 단일 목록으로 최대 `--related-top-k`개를 내고, 각 줄 끝에 관련 근거를 표기한다.
- **`REFERENCES` 근거 문구** [제안 후 승인]: 방향에 따라 셋으로 구분한다.

  | 상황 | 문구 |
  |---|---|
  | 이 문서 → 상대 | `이 문서가 참조함` |
  | 상대 → 이 문서 | `이 문서를 참조함` |
  | 양방향 | `서로 참조함` |
- **링크는 그 위키 파일 기준 상대경로를 쓴다** [사용자 결정 · 2026-08-23 정정]. 이 결정이
  링크에 요구한 것은 "파일 탐색기·에디터에서 그대로 동작"이고, `--out` 루트 기준 문자열을
  그대로 넣으면 하위 폴더 문서에서 링크가 깨진다 — `인사/채용계획.docx.md` 안의
  `개발/설계.md.md`는 `인사/개발/설계.md.md`를 가리킨다. 올바른 값은 `../개발/설계.md.md`다.
  최상위 문서에서는 두 값이 같다.
  - 아래 순위 규칙 ⑤의 tie-break는 **문서 사이의 비교**라 종전대로 `--out` 기준 상대경로를
    쓴다. 링크(파일마다 다름)와 정렬 키(전역에서 하나여야 함)의 요구가 다르기 때문이다.
- 관련 문서가 하나도 없으면 섹션을 생략하지 않고 `관련 문서 없음`이라고 쓴다.
- **순위 = 계층적 정렬** (가중합을 쓰지 않는다):
  1. `REFERENCES` 관계가 있는 문서
  2. 유사도 내림차순
  3. 공유 엔티티 수 내림차순
  4. 공유 태그 수 내림차순
  5. 동점은 출력 상대경로 사전순 (tie-break)

### 4.6 결과 타입과 종료 요약 [사용자 결정]
그래프 단계의 결과 넷(통계·유사도 생략 사유·재료 없는 위키 건수·빌드/주입 실패)은 평면
필드로 흩뿌리지 않고 **단일 `GraphOutcome` 객체**에 묶어 `ScanResult.graph`(기본 `None`)로
담는다. `ScanResult`는 9필드를 유지하며, 후속 버전이 그래프 지표를 더해도 `GraphOutcome`
안에서만 늘어난다.

```python
class GraphSkipReason(StrEnum):
    VECTORS_UNAVAILABLE = "vectors_unavailable"   # 벡터 인덱스 부재 (§5)
    BUILD_FAILED = "build_failed"                 # 트랜잭션 롤백 (§5)

@dataclass(frozen=True)
class GraphStats:
    documents: int
    entities: int
    tags: int
    edges_by_type: dict[str, int]

@dataclass(frozen=True)
class InjectionFailure:
    """「관련 문서」 주입에 실패한 위키 — v0.4 `EmbeddingFailure`와 같은 모양이다."""
    path: Path
    detail: str

@dataclass(frozen=True)
class GraphOutcome:
    stats: GraphStats | None = None               # 빌드 실패면 None
    similarity_skipped: GraphSkipReason | None = None
    build_failure: str = ""
    facts_missing_count: int = 0                  # 엔티티 없는 기존 위키 건수 (§5)
    related_updated_count: int = 0                # 「관련 문서」가 실제로 갱신된 위키 건수
    injection_failures: list[InjectionFailure] = field(default_factory=list)
    duplicate_sources: list[Path] = field(default_factory=list)   # 같은 원문을 가리킨 위키
```

`related_updated_count`는 요약 파이프라인의 «생성/스킵» 축과 **별개 축**이다 [사용자 결정].
`up_to_date`로 스킵된 문서라도 다른 문서의 변경 때문에 관련 문서 목록이 바뀌면 그 파일은
패스3에서 수정된다. 이 건수를 그래프 축에 따로 내지 않으면 "스킵 9건"이라고 보고해 놓고
파일 몇 개의 타임스탬프가 바뀌는 상황이 설명되지 않는다. `SkipReason`을 세분화해 같은 축에
담지는 않는다 — 스킵 사유가 요약과 그래프 두 시스템의 상태를 함께 표현하게 되기 때문이다.

`scan` 종료 요약 출력 형태:
```
처리 6건 / 스킵 1건
  - 미지원 확장자: 1건
그래프: 노드 23개(문서 6 · 엔티티 11 · 태그 6) / 엣지 41개
  - 관련 문서 갱신 4건
  - 유사도 엣지 생략 — 로컬 Ollama 데몬이 응답하지 않아 벡터 인덱스가 비어 있습니다.
  - 엔티티 없는 기존 위키 2건 — `--force` 로 재스캔하면 엔티티까지 채워집니다.
출력 경로: ./corpbrain_wiki
```

### 4.7 CLI [사용자 결정]
```
corpbrain graph
  --out DIR                    위키·그래프 DB 위치 (기본 ./corpbrain_wiki)
  --stats                      노드·엣지 종류별 개수
  --neighbors <상대경로>        해당 문서의 4종 엣지 이웃
  --central                    연결 차수 내림차순 문서 목록
```
- `--stats` / `--neighbors` / `--central`은 상호배타이며, 중첩 서브커맨드를 두지 않는다.
- **`graph`는 순수 조회 명령이다** [사용자 결정]. `--similarity-threshold`·`--related-top-k`는
  `graph`에 두지 않는다. 엣지는 `scan`이 §4.4의 재빌드 전략으로 이미 만들어 둔 것이고,
  조회 시점에 다시 계산하면 `--stats` 출력이 DB·위키와 어긋나 §3 항목3을 위반한다.
  - 임계치를 바꿔 보려면 `corpbrain scan … --similarity-threshold 0.85` 를 다시 돌린다.
    `should_regenerate()`는 임계치를 보지 않으므로 문서가 그대로면 전부 `up_to_date`로
    스킵되어 **LLM 호출이 0회**이고, 그래프 재빌드와 「관련 문서」 주입만 일어난다.
  - 이 경로는 `scan` 프리플라이트 때문에 Ollama가 떠 있어야 한다는 마찰이 있다. 그 대가로
    §2의 "독립 빌드 명령을 두지 않는다"를 지키고 DB·조회·위키가 항상 한 값을 가리킨다.
- `--central`의 중심성은 **연결 차수(degree)** 내림차순으로 정의하고, 동점은 사전순으로
  정렬한다. [제안 후 승인]
- `corpbrain scan`에 `--similarity-threshold`(기본 0.75)와 `--related-top-k`(기본 5)를
  추가한다. 기본값을 보존하므로 하위 호환이다.
- **`--neighbors` 경로 해석** [제안 후 승인]: `--out` 기준 **위키 상대경로**(`개발/설계.md.md`)를
  우선 매칭하고, 실패하면 **원문 상대경로**(`개발/설계.md`)로 한 번 더 시도한다. 절대경로도
  허용한다. 「관련 문서」 링크와 `--stats` 출력이 위키 상대경로를 쓰므로 복붙 경로가 우선이다.
- **오류 계약** [사용자 결정]:
  - 그래프 DB 부재(`scan` 이전 실행) → **exit 1**. `search`가 인덱스 부재를 선행 조건 실패로
    다루는 선례와 같다.
  - `--neighbors`가 지목한 문서가 그래프에 없음 → **exit 1** + 안내. `search`의 "결과 0건은
    exit 0"과 갈라지는데, 자유 텍스트 쿼리와 달리 `--neighbors`는 존재를 전제한 **식별자
    지목**이므로 매칭 실패는 빈 결과가 아니라 잘못된 지목이다.
  - `--stats`·`--central`이 빈 그래프를 만난 경우(문서 0건) → exit 0. 빈 결과는 정상 응답이다.

### 4.8 파이프라인 통합 [사용자 결정]
- 그래프 빌드와 「관련 문서」 주입은 `corpbrain scan` 한 명령 안에서 수행한다.
- 「관련 문서」는 전 문서를 처리한 뒤에야 계산 가능하므로 `run_scan()`은 2-패스가 된다:
  ① 전 문서 요약·렌더 → ② 그래프 빌드 → ③ 각 `.md`에 「관련 문서」 섹션 반영.
- **`VectorStore` 수명** [사용자 결정]: 패스2가 `iter_vectors()`로 유사도를 계산해야 하므로,
  `run_scan()`의 `finally: store.close()`는 그대로 두되 **패스2·패스3을 그 `try` 블록 안으로
  넣어** 저장소 개방 구간을 실행 끝까지 늘린다. 그래프 빌더가 인덱스를 따로 여는 방식은
  택하지 않는다 — `_NoIndexStore`가 없애 둔 `if indexing` 분기를 되살리게 되기 때문이다.
  `indexing=False`면 `_NoIndexStore.iter_vectors()`가 빈 이터레이터를 돌려주어 §5의
  부분 그래프가 분기 없이 성립한다.
- 코어/CLI 이음새와 단일 외부호출 관문 불변식은 그대로 유지한다. 그래프 계층은 네트워크
  라이브러리를 직접 호출하지 않는다. [제안 후 승인]

## 5. 엣지 케이스와 실패 시나리오
- **벡터 인덱스 부재 또는 비어 있음** (`--engine cloud` + Ollama 미구동 등): `SEMANTICALLY_SIMILAR`
  만 생략하고 나머지 3종으로 **부분 그래프**를 만든다. 종료 코드 0, 종료 요약에 생략 사유를
  한 줄 보고한다. [사용자 결정]
- **엔티티가 없는 기존 위키** (v0.5 이하 산출물): 재요약을 강제하지 않는다. mtime 규칙대로
  스킵하고 엔티티 없이 부분 그래프를 만들며, 종료 요약에 `--force`로 재스캔하면 엔티티까지
  채워진다는 안내를 낸다. 종료 코드 0. **BREAKING이 아니다.** [사용자 결정]
- **개별 문서 임베딩 실패**: 그 문서만 유사도 엣지를 갖지 않고 나머지는 정상 처리한다.
  [제안 후 승인]
- **`REFERENCES` 오탐 억제**: 스캔 대상 안의 파일명(확장자 포함)이 대상 텍스트에 정확히
  등장할 때만 엣지를 만든다. 확장자 없는 부분 일치, 또는 동명 파일이 여럿이라 대상이
  모호한 경우에는 엣지를 만들지 않는다 — 모호하면 만들지 않는다. [제안 후 승인]
- **`REFERENCES` 대상 텍스트 확보** [사용자 결정]: 재요약되는 문서는 이미 읽어 둔 요약 입력
  텍스트를 그대로 재사용해 추가 파일 I/O를 만들지 않는다. `doc_facts` 복원 경로(§4.4)에서만
  원문을 `--max-chars`까지 1회 다시 읽어 `refs`를 계산하고 캐시하며, 이후 실행은 캐시를 쓴다.
  원문이 이미 없거나 접근 불가하면 `refs`는 빈 배열로 둔다.
  - **알려진 한계**: 요약 입력과 같은 절단을 쓰므로 `--max-chars` 이후에 등장하는 참조는
    잡히지 않는다. 요약 자체가 같은 범위만 보므로 일관된 한계로 수용한다.
- **그래프 빌드·주입 단계의 실패** [사용자 결정]: 패스1이 끝난 시점에 위키는 이미 정상
  생성돼 있고 LLM 비용도 지불된 상태다. 이 뒤의 실패는 스캔 전체를 무효화하지 않는다.
  - `nodes`·`edges` 재빌드는 **단일 트랜잭션**으로 커밋한다. 비운 직후 중단되어 그래프가
    사라지거나, 절반만 채워진 그래프가 정상처럼 보이는 상태를 원천 차단한다. 실패하면
    이전 그래프가 그대로 보존된다.
  - 「관련 문서」 주입은 **파일별 베스트 에포트**다. 한 파일이 실패해도(권한 거부·잠금 등)
    나머지 파일 처리를 계속하고, 실패한 경로와 사유를 종료 요약에 보고한다.
  - 두 경우 모두 **종료 코드 0**이며 실패 사유를 종료 요약에 낸다 — v0.1 §5의 "개별 파일
    실패는 전체 실패로 위장하지 않는다"와 v0.4 고아 벡터 정리의 베스트 에포트 방침을
    그대로 계승한다.
- **그래프 DB 스키마 불일치·손상** [사용자 결정]: `meta`의 `schema_version`(초깃값 `"1"`)이
  이번 버전과 다르거나 sqlite 계층 오류가 나면 자동 복구하지 않고 `PreconditionError`로
  **exit 1**을 내며, `.corpbrain_graph.sqlite`를 지우고 다시 `scan` 하라고 안내한다.
  v0.4가 벡터 인덱스에 대해 세운 "자동 마이그레이션하지 않고 에러 + 재생성 안내" 방침과
  동형이며(v0.4 스펙 §2·§5), 저장소가 둘로 늘어도 같은 정책을 유지한다.
  - 그래프 DB를 지우면 `doc_facts`의 엔티티가 함께 사라지지만 §4.4의 재료 복원 fallback이
    위키에서 제목·태그를 되살리므로, 다음 `scan`은 엔티티만 빈 부분 그래프를 만든다 —
    아래 「엔티티가 없는 기존 위키」와 같은 상태다. 엔티티를 되찾으려면 `--force` 재스캔이
    필요하다.
  - 조용히 폐기하고 재생성하지 않는다. 데이터 손실이 「관련 문서」에서 엣지 근거가 사라진
    뒤에야 드러나기 때문이며, §4.5 마커 결정과 같은 잣대다.
- **위키를 읽지 못한 경우** [사용자 결정 · 2026-08-23 추가]: `--out` 아래 위키 하나라도
  읽지 못하면(권한 거부·잠금) 그 실행에서는 **재료 정리를 통째로 건너뛴다**. 목록이 불완전한
  채로 "위키 없는 문서"를 판정하면 파일이 잠긴 일시적 조건이 `doc_facts` 삭제(엔티티 영구
  소실)로 번진다. 그래프 자체는 읽어낸 문서들로 정상 생성된다.
- **같은 원문을 가리키는 위키가 둘 이상** [사용자 결정 · 2026-08-23 추가]: 서로 다른 스캔
  루트가 같은 `--out`을 공유하면 생길 수 있다. 마지막에 발견된 위키가 그래프에 참여하고,
  밀려난 위키의 경로를 종료 요약에 한 줄로 알린다 — 조용히 사라지게 두지 않는다.
- **고립 문서**: 「관련 문서」 섹션에 `관련 문서 없음`을 렌더한다. [사용자 결정]
