## 0. 구현 결과 (완료의 정의 13 반영)

**`DEFAULT_GRAPH_DECAY = 0.5`.** §4.8의 절차대로 24문서 코퍼스·한국어 쿼리 15개로 α를
0.5~0.95(0.05 간격) 스윕하고 §4.8 4번 규칙을 적용해 나온 값이다. 원시 출력은
`docs/smoke/graph_decay_results.{json,csv}`, 절차와 해석은 `docs/SMOKE.md` 실행 J.

```
설정            top-1 적중률      MRR     Recall@3
no-graph            0.00%     0.2056     0.4000   ← 기준선
α=0.50 ~ 0.65       0.00%     0.2056     0.4000   ← 기준선과 완전히 동일
α=0.70 ~ 0.85       0.00%     0.2056     0.3667
α=0.90              0.00%     0.1900     0.2333
α=0.95              0.00%     0.2022     0.3000
```

규칙 적용: top-1 전부 동률(0.00%) → MRR 최고 0.2056이 α 0.50~0.85 8개 동률 → Recall@3
최고 0.4000이 α 0.50~0.65 4개 동률 → 마지막 키(α가 작은 쪽) → **α = 0.5**.

**규칙은 정상 작동했지만 그 답의 의미는 「0.5가 최적」이 아니다** [2026-08-26 실측].
α=0.5에서는 **확산 문서가 결과에 한 건도 들어오지 않는다** — 코사인 단독과 완전히 같은
출력이다. 확산이 결과를 바꾸기 시작하는 것은 α=0.6부터이고, 개입이 커질수록 지표는
단조 하락한다. 즉 실측이 고른 것은 개입 강도가 아니라 **「이 코퍼스에서는 개입하지 않는
것이 최선」**이다.

| α | 코사인 단독과 결과가 달라진 쿼리 | 결과에 들어온 확산 문서 |
|---|---|---|
| 0.50 · 0.55 | 0/15 | 0건 |
| 0.60 · 0.65 | 1/15 | 2건 |
| 0.70 | 2/15 | 5건 |
| 0.85 | 7/15 | 13건 |
| 0.90 | 9/15 | 23건 |
| 0.95 | 13/15 | 34건 |

(α 0.60·0.65에서 결과 순서가 바뀌는데도 위 지표표에서 α≤0.65가 기준선과 같은 것은, 그
쿼리에서 순서가 바뀐 구간이 정답을 포함하지 않아 MRR·Recall@3에 잡히지 않기 때문이다.)

**원인 — 고차수 엔티티 노드** [2026-08-26 실측]. 엣지 종류를 갈라 같은 스윕을 돌리면
`CONTAINS_ENTITY` 단독이 기본 3종과 소수점까지 같은 값을 낸다 — 손해 전부가 엔티티에서
나온다. 요약 모델이 뽑는 엔티티가 대부분 부서명이라 선택성이 없기 때문이다: `인사팀`
하나가 23문서 중 10개를 잇고, 시드가 그 엔티티를 가지면 문서 10개가 한꺼번에 `시드 × α`
동점으로 후보에 들어와 코사인 2~5위의 정답을 밀어낸다. §5가 「흔한 태그로 인한 동점 다발」로
적어 둔 현상이 태그가 아니라 엔티티에서 일어났다(태그는 2개 이상 문서를 잇는 노드가 77개 중
7개뿐이라 후보를 거의 만들지 않는다).

**구조적 사실 — top-1 적중률은 α를 판별할 수 없다** [2026-08-26 실측]. 확산 문서의 점수는
`max(자기 코사인, 시드 × α)`이고 확산 문서는 정의상 코사인 top-k 밖이라 항상 1위 코사인
미만이다. 따라서 **어떤 쿼리 세트를 써도 top-1(α) = top-1(no-graph)** 이며, §4.8 4번의
1순위 키는 α 선택에 기여할 수 없다. 규칙 자체는 그대로 성립하므로(2·3순위 키가 받는다)
고치지 않고 사실만 기록한다.

**기본 `--expand-edges`를 바꾸지 않는다.** 진단된 원인은 `CONTAINS_ENTITY`지만 근거가
코퍼스 1개·쿼리 15개이고, 기본값 변경은 §4.2의 결정을 뒤집는 일이라 후속 이슈로 넘긴다.
사용자 안내(`docs/USAGE.md` §6.3)에 우회법으로 적는다.

## 1. 목표
`corpbrain search`는 v0.4의 코사인 top-k 그대로 머물러 있어 v0.6이 만든 지식그래프를 순위에
전혀 반영하지 못한다. 코사인 상위 문서를 **시드**로 삼아 그래프로 연결된 문서를 후보에
끌어올리고, 감쇠 계수 하나로 재순위화한다. 태그·엔티티·명시적 참조는 임베딩이 포착하지
못하는 신호이며, 이 신호를 더하는 것이 이번 슬라이스의 전부다. 추가 LLM 호출과 추가 네트워크
연결은 발생하지 않으며(쿼리 임베딩 1회는 v0.4와 동일), 신규 저장 계층을 만들지 않는다.

  저장 가능한 것(노드·엣지)은 v0.6이 이미 저장했고 이번 슬라이스는 그것을 읽기만 한다.

  "이 문서 다음에 무엇을 볼까"에, 검색은 "이 쿼리에 답하는 문서가 무엇인가"에 답하며,
  「관련 문서」에는 쿼리가 없어 코사인을 곱할 대상 자체가 없다. **이번 슬라이스에서 위키
  산출물은 한 글자도 바뀌지 않는다.**
- **인터뷰에서 검토 후 배제한 대안 3종.**
  - **문서 2홉 이상 확산** — 흔한 태그를 두 번 경유하면 코퍼스 대부분이 후보가 된다.
    (`온보딩` → `인사` 태그 → `채용계획` → `경영` 태그 → `이사회의사록`)
  - **정적 중심성(degree) 가산** — 쿼리와 무관한 가산이라 어떤 쿼리에도 같은 허브 문서가
    올라오고, "이 쿼리와 관련되어 순위가 올랐다"는 설명이 성립하지 않는다.
  - **쿼리 문자열 ↔ 태그·엔티티 라벨 직접 매칭** — 쿼리에 고유명사가 글자 그대로 있을
    때만 작동한다. 자연어 문장 쿼리에서는 그래프 기여가 0이 된다.

## 3. 완료의 정의
자동 테스트는 `tmp_path`에 코퍼스를 **인라인 생성**하고 `gateway.request_json`을 스텁해
벡터를 고정한다(v0.6 관용구 계승). 아래를 모두 만족한다. [제안 후 승인]

1. 코사인 단독으로는 `--top-k` 밖이던 문서가 하이브리드에서 기대 순위에 나타난다.
   - 검증: 결과의 `(순위, doc_id)` 시퀀스를 기대 시퀀스와 정확히 일치 단언.
2. `--no-graph` 실행의 **stdout이 그래프 DB를 삭제한 뒤의 stdout과 바이트 동일**하다.
   - 검증: 두 실행의 stdout 비교. (stderr는 §5의 안내 한 줄만큼 다르다.)
3. 결과 개수가 항상 `--top-k` 이하다.
   - 검증: 확산으로 후보가 `--top-k`를 초과하는 코퍼스에서 반환 길이 단언.
4. 확산 문서의 점수가 그 시드의 점수를 넘지 않는다.
   - 검증: 전 결과에 대해 `expansion is None or score <= seed_score` 단언.
5. 동점 그룹 내 순서가 §4.3의 정렬 키와 일치한다.
   - 검증: 같은 시드의 여러 이웃이 동일 점수를 받는 코퍼스로 순서 단언.
6. `--expand-edges`에서 `REFERENCES`를 빼면 참조로만 이어진 문서가 결과에서 사라진다.
   - 검증: 같은 코퍼스·쿼리로 두 번 호출해 결과 집합 차이 단언.
7. 그래프 DB 부재 시 exit 0, 코사인 단독 결과, stderr 안내 1줄.
   - 검증: 그래프 DB 없이 CLI 실행해 종료 코드·stdout·stderr 단언.
8. `--graph-decay`가 `0 < α < 1` 밖이면 exit 1 + 사유. 코어 API를 직접 호출해도 같은 예외가
   난다.
   - 검증: 코어 단위테스트(경계값 0.0·1.0 포함)와 CLI 종료 코드 단언.
9. 그래프 DB 손상·스키마 불일치 시 exit 1 + 재생성 안내.
   - 검증: `schema_version`을 어긋나게 한 DB로 CLI 실행해 종료 코드 단언.
10. 동일 입력 2회 실행 시 stdout이 바이트 동일하다.
   - 검증: 2회 실행 결과 비교.
11. **네트워크 불변식** — `search` 1회 실행의 소켓 목적지가 localhost뿐이고 연결이 쿼리

## 4. 인터페이스 계약

### 4.1 결합 모델 [사용자 결정]
- **시드 확산**으로 결합한다. 코사인 상위 `--top-k` 문서 전부를 시드로 삼고, 각 시드의
  그래프 이웃 문서를 후보에 추가한다.
- 확산 문서의 점수:

  ```
  d = 확산으로 후보가 된 문서 (시드가 아니다)
  score(d) = max( cosine(query, d),  max over seeds s of ( score(s) × α ) )
  ```

  **시드의 점수는 자기 코사인 그대로이며 이 식의 적용 대상이 아니다** [사용자 결정 ·
  2026-08-26 리뷰 확인]. 식 안의 `d`를 모든 문서로 읽으면 상위 시드와 태그를 공유한 시드가
  `시드 × α`로 올라가 사실상 밀려나지 않게 되고, 아래 「코사인 하위 시드가 밀려나는 것은
  재순위화의 의도된 동작」이 성립하지 않는다. 실제로 코드리뷰 준비 중 이 오독이 한 번
  발생했으므로 `d`의 범위를 식 안에 못박는다.

- **상수는 감쇠 계수 α 하나뿐이다.** v0.6 `rank_related`가 가중합을 거부한 이유("가중치를
  임의로 정해야 하고 부동소수 비교가 생긴다")를 계승해, 엣지 종류별 가중치를 두지 않는다.
- **확산은 문서 1홉만** 한다. 태그·엔티티 노드 경유는 홉으로 세지 않는다 — 그래프는
  문서 → Tag/Entity → 문서 구조이므로 「문서 1홉」이 이웃 문서 한 단계를 뜻한다.
- α는 **열린 구간 `0 < α < 1`** 로 제한한다 [사용자 결정 · grill-it T5]. 이 범위 안에서만
  「확산 문서는 자기 시드를 추월하지 못한다」가 성립하며, §3 항목4는 그 성질을 단언한다.
  범위 밖 입력은 §4.5의 코어 API가 `PreconditionError`로 거부한다(exit 1) — 검증을 CLI
  파서가 아니라 코어에 두어 규칙이 한 곳에만 있고, 코어를 직접 부르는 후속 어댑터(GUI 등)도
  같은 보호를 받는다.
  - α ≥ 1은 확산 문서가 시드를 추월하거나 시드와 전부 동점이 되어 `--top-k`가 한 시드의
    이웃으로 채워진다. α ≤ 0은 확산 기여가 사라져 플래그가 무의미해진다.
  - 클램프하지 않는다. α를 스윕해 효과를 보는 §4.8 측정 절차에서, 조용히 다른 값으로 바뀐
    α는 결과를 설명 불가능하게 만든다.
- 재순위화 후 **`--top-k`로 자른다.** 확산 문서가 들어온 만큼 코사인 하위 시드가 밀려나는
  것은 재순위화의 의도된 동작이다.

**「조회 시점에 파생값을 재계산하지 않는다」 불변식과의 관계** [제안 후 승인]: 그 불변식이
막으려던 것은 저장된 엣지를 다른 임계치로 다시 만들어 DB·산출물과 출력이 어긋나는 것이다.
확산은 저장된 노드·엣지를 **읽기만** 하며 아무것도 다시 만들지 않는다. 쿼리는 조회 시점에만
존재해 애초에 저장할 수 없고, 코사인 top-k도 이미 조회 시점 계산이다. 위반이 아니다.

### 4.2 확산 대상 엣지 [사용자 결정]
- 기본은 `TAGGED_WITH` · `CONTAINS_ENTITY` · `REFERENCES` **3종**이다. 임베딩이 포착하지
  못하는 신호만 더한다.
- `SEMANTICALLY_SIMILAR`는 기본에서 제외한다 — 임베딩 코사인 그 자체라 같은 신호를 두 번
  세게 되고, #42가 실측한 임베딩 모델 종속성이 순위에서 증폭된다. `--expand-edges`로 켤 수
  있다.
- 확산 방향은 따지지 않는다. `REFERENCES`가 방향 있는 엣지라도 어느 방향이든 이웃으로 본다.
  방향은 근거 문구에만 반영한다(§4.6).
- 자기 자신은 이웃이 아니다. v0.6이 자기 루프 엣지를 만들지 않으므로 추가 처리가 필요 없다.

### 4.3 순위와 동점 처리 [사용자 결정]
1차 키는 §4.1의 `score` 내림차순이다. **동점은 v0.6 `rank_related`의 계층 정렬 키를
그대로 계승해** 가른다. 새 상수를 도입하지 않는다.

0. **시드가 확산 문서보다 앞선다** [사용자 결정 · 2026-08-26 추가]
1. `REFERENCES` 관계가 있는 문서
2. 시드와의 공유 엔티티 수 내림차순
3. 시드와의 공유 태그 수 내림차순
4. 자기 코사인 내림차순 (벡터가 없어 코사인이 없으면 최하위로 본다)
5. `doc_id`(원문 절대경로) 사전순

**0번 키를 두는 이유** [사용자 결정 · 2026-08-26 · PR #46 코드리뷰]: 1~4번은 전부
「**시드와의** 공유 엔티티 수」처럼 기준 시드를 전제해 쓰여 있어 **시드 자신에게는 적용할
대상이 없다.** 초기 구현은 시드에 관계 축을 임의값으로 매겼고, 그 결과 `REFERENCES` 관계를
가진 확산 문서가 정확한 동점에서 시드를 이겨 **코사인 top-k 안에 정말로 들어온 문서가 잘려
나갔다**(실측 재현). §4.1이 「코사인 하위 시드가 밀려나는 것은 재순위화의 의도된 동작」이라고
한 것은 확산 문서의 점수가 더 **높을 때**를 말하며, 같을 때까지 허용한 것이 아니다.
- **따름정리** [2026-08-26]: 확산 문서의 코사인은 정의상 최하위 시드의 코사인 이하이므로,
  자기 코사인이 `max()`를 이긴 확산 문서는 잘해야 최하위 시드와 동점이고 그 동점은 이제
  시드가 가져간다. 따라서 **결과에 남은 확산 문서는 언제나 «자기 코사인 < 점수»** 이며,
  §4.5 표의 「`max()`가 자기 코사인으로 결정돼도 채운다」는 경계 규칙으로는 그대로 살아 있되
  실제 출력에서는 나타나지 않는다. 근거 줄이 코사인을 따로 적는 목적(대괄호 숫자가 그 문서의
  코사인이 아님을 알린다)은 그대로 성립한다.

한 문서가 여러 시드의 이웃이면 **가장 높은 점수를 준 시드**를 기준 시드로 삼고 그 시드와의
관계를 근거·정렬에 쓴다. 점수까지 같으면 시드의 `doc_id` 사전순으로 기준 시드를 정한다.

**tie-break 키가 v0.6 `rank_related`와 다른 이유** [사용자 결정 · grill-it T3]: `rank_related`는
「출력 상대경로 사전순」을 쓰지만, 그 값은 파이프라인이 스캔 루트를 알기에 만들어 넘겨 준
것(`relative_paths` 인자)이다. `search_index`는 `out_dir`와 `doc_id`만 알고 스캔 루트를 모르며,
코어는 경로 해석 책임을 지지 않는다(CLAUDE.md 불변식). 상대경로를 얻으려면 검색 1회마다
`out_dir` 아래 위키를 전부 열어 front-matter를 읽어야 하는데, 이는 동점 처리 하나를 위해 조회
명령의 비용 성격을 바꾸는 일이다.
- tie-break의 목적은 «실행마다 순서가 흔들리지 않게»이고 `doc_id`는 코어가 이미 손에 쥔
  전역 유일 키라 그 목적을 그대로 달성한다.
- 같은 스캔 루트의 문서들은 공통 접두사 뒤를 비교하므로 **상대경로 사전순과 같은 순서**가
  나온다. 루트가 섞인 `out_dir`에서만 갈리며, 그때도 결정적이다.

### 4.4 CLI [사용자 결정]
```
corpbrain search <query>
  --out DIR              위키·인덱스·그래프 DB 위치 (기본 ./corpbrain_wiki)
  --top-k N              기본 5 (시드 개수이자 최종 결과 개수)
  --ollama-url URL       기본 http://127.0.0.1:11434
  --no-graph             그래프 확산 없이 코사인 단독 (v0.4 동작)
  --graph-decay FLOAT    확산 감쇠 계수 α (기본값은 §4.8의 실측으로 확정)
  --expand-edges LIST    확산에 쓸 엣지 종류. 쉼표 구분.
                         기본 TAGGED_WITH,CONTAINS_ENTITY,REFERENCES
```
- **하이브리드가 기본 동작이다.** 되돌리는 플래그(`--no-graph`)를 두어 하위 호환을 확보한다.
- `--expand-edges`는 **`EdgeType` StrEnum 값을 그대로** 받는다. 짧은 별칭을 새로 만들지
  않는다 — `graph --stats` 출력·DB의 `type` 컬럼·이 플래그가 한 문자열이어야 어휘가 갈리지
  않는다. 목록에 없는 값은 즉시 오류로 거른다.
- **입력 처리 규칙** [사용자 결정 · grill-it T10 · 2026-08-26 문면 정정]. 파싱과 검증을
  **코어가 소유한다**(T5와 같은 이유) — 규칙이 한 곳에만 있어야 코어를 직접 부르는 후속
  어댑터(GUI 등)도 같은 보호를 받는다. CLI는 자체 파서를 두지 않고 코어가 공개한
  `parse_expand_edges(raw: str) -> frozenset[EdgeType]`를 호출해 그 결과를 §4.5의
  `expand_edges` 인자로 넘긴다.
  - **초판은 「CLI는 문자열을 그대로 넘긴다」고 적었으나 §4.5의 시그니처와 모순이었다** —
    `expand_edges: frozenset[EdgeType]`는 문자열을 받을 수 없다. T10이 지키려던 것은
    «문자열이 코어까지 간다»가 아니라 «파싱 규칙의 구현이 하나뿐이다»이며, 후자는 파서가
    코어에 있는 것으로 이미 성립한다. 문면만 구현에 맞춰 고친다.

  | 입력 | 처리 |
  |---|---|
  | `TAGGED_WITH, REFERENCES` (쉼표 주변 공백) | 각 항목을 trim해 정상 처리 |
  | `TAGGED_WITH,TAGGED_WITH` (중복) | `frozenset`이 흡수 — 정상 처리 |
  | `tagged_with` (소문자) | `PreconditionError` (exit 1) |
  | `` (빈 목록) · `TAGGED_WITH,` (빈 항목) | `PreconditionError` (exit 1) |

  - 빈 목록을 «확산 안 함»으로 받아 주지 않는다. 확산을 끄는 길은 `--no-graph` 하나여야
    §3 항목2·7이 다루는 경로가 갈라지지 않는다.
  - 소문자를 받아 주지 않는 것은 위의 «한 문자열» 근거를 그대로 지키기 위함이다.
- 플래그 이름에 «hybrid»를 쓰지 않는다. §2 비목표①에 적은 대로 그 단어는 업계에서 BM25
  결합을 뜻한다.

### 4.5 코어 API와 결과 타입 [사용자 결정]
```python
def search_index(
    out_dir: Path,
    query: str,
    *,
    top_k: int = 5,
    ollama_url: str = DEFAULT_OLLAMA_URL,
    graph: bool = True,
    graph_decay: float = DEFAULT_GRAPH_DECAY,
    expand_edges: frozenset[EdgeType] = DEFAULT_EXPAND_EDGES,
) -> list[SearchResult]: ...
```

`graph_decay`가 `0 < α < 1` 밖이면 `PreconditionError`를 낸다(§4.1 · grill-it T5). CLI는 이
예외를 exit 1로 매핑할 뿐 자체 검증을 두지 않는다.

`SearchResult`에 **선택 필드 1개**를 더한다. v0.6이 `ScanResult`를 9필드로 유지하고 그래프
결과 넷을 `GraphOutcome` 한 객체로 묶은 것과 같은 형태다. 코사인 단독 경로와 타입이 갈리지
않는다.

```python
@dataclass(frozen=True)
class GraphExpansion:
    """그래프 확산으로 후보에 올라온 문서의 근거. 코사인 단독 결과는 이 값이 None이다."""
    seed_doc_id: str
    seed_title: str
    seed_score: float
    cosine: float | None            # 확산 문서 자신의 코사인. 벡터가 없으면 None
    shared_tags: list[str]          # 표시 라벨 (노드 id가 아니다)
    shared_entities: list[str]      # 표시 라벨
    reference: ReferenceDirection   # v0.6 정의를 재사용

@dataclass(frozen=True)
class SearchResult:
    doc_id: str
    score: float
    metadata: dict[str, Any]
    expansion: GraphExpansion | None = None   # 신규
```

`shared_tags`·`shared_entities`가 노드 id가 아니라 표시 라벨을 담는 것은 v0.6
`RelatedDocument`와 같다 — 렌더러가 재변환하지 않는다.

**`expansion`의 경계는 «후보 진입 경로»다** [사용자 결정 · grill-it T2]. 점수의 출처가 아니라
**그 문서가 어떻게 후보가 되었는가**로 가른다.

| 문서 | `expansion` |
|---|---|
| 코사인 top-k로 들어온 시드 | `None` (다른 시드의 그래프 이웃이기도 해도 마찬가지) |
| 확산으로 처음 후보가 된 문서 | 값 있음 — `max()`가 자기 코사인으로 결정돼도 채운다 |

두 번째 행의 단서는 **경계를 진입 경로로 정의한다는 규칙**이며, §4.3 0번 키가 더해진 뒤로는
실제 출력에 나타나지 않는다(§4.3 「따름정리」). 규칙을 점수 출처로 바꾸지 않는 이유는
그대로다 — 그렇게 가르면 코사인 top-k 밖인데 결과에 나타난 문서가 설명 없이 놓인다.

- 점수 출처로 가르면 «코사인 top-k 밖인데 결과에 나타난 문서»가 근거 없이 놓인다. 진입
  경로로 가르면 **전 결과에서 «이 문서가 왜 여기 있는가»가 설명된다** — 시드는 코사인 상위라
  이유가 자명하고, 나머지는 전부 근거 줄을 갖는다.
- 이 경계에서도 §3 항목4(`score <= seed_score`)는 성립한다. 비시드 문서의 코사인은 정의상
  최하위 시드의 코사인 이하이고, 기준 시드의 점수는 그 값 이상이기 때문이다.

### 4.6 출력 형식 [제안 후 승인]
`report.py`의 `build_search_lines()`를 확장한다. CLI는 이 순수 함수의 반환을 출력만 한다.
**근거 줄은 확산된 문서에만** 붙인다.

```
검색 결과 5건
  1. [0.710] 온보딩 — /Users/me/docs/인사/온보딩.md
  2. [0.568] 채용계획 — /Users/me/docs/인사/채용계획.docx
       └ 코사인 0.380 · 시드 «온보딩» · 공유 태그 `인사` · 공유 엔티티 `인사팀` · 서로 참조함
  3. [0.550] 메모 — /Users/me/docs/기타/메모.txt
```

- **경로는 v0.4 그대로 `metadata["source_path"]`(원문 절대경로)를 적는다** [사용자 결정 ·
  grill-it T4]. 상대 표기로 바꾸면 T3이 비용을 이유로 배제한 «검색 1회마다 위키 전체 읽기»가
  다시 필요하고 v0.4 출력이 바뀐다. 보이는 문자열과 §4.3 정렬 키 5번이 같은 값이 되는 이점도
  있다. 확산 문서 중 벡터가 없어 `metadata`가 없는 경우는 v0.4의 기존 대체 규칙대로
  `doc_id`를 적는다(같은 값이다).

- 대괄호 안 점수는 §4.1의 최종 점수다. 확산 문서에서는 코사인이 아니므로, 근거 줄이 원
  코사인을 함께 적어 성격이 다른 두 숫자가 구분되게 한다.
- 확산 문서에 벡터가 없어 `cosine`이 `None`이면 `코사인 …` 항목을 생략한다.
- **최종 점수가 자기 코사인과 같으면(=`max()`를 코사인이 이겼으면) `코사인 …` 항목도
  생략한다** [사용자 결정 · grill-it T2]. 대괄호 안 숫자와 같은 값을 한 줄에서 두 번 적지
  않는다. 코사인 표기의 목적은 «대괄호 숫자가 코사인이 아니다»를 알리는 것이므로, 두 값이
  같은 문서에서는 알릴 것이 없다.
- 근거 항목의 나열 관용구(`·` 구분, 태그·엔티티를 백틱으로 감쌈)는 v0.6 `render.py:_evidence()`
  와 같은 결로 맞춘다. 조사로 문장을 잇지 않는다 — 항목을 기계적으로 `·`로 잇는 그 관용구가
  라벨 받침에 따라 조사가 갈리는 문제를 애초에 만들지 않는다.
- **참조 방향 문구는 «시드»를 글자로 박아 3종으로 쓴다** [사용자 결정 · grill-it T9]. 근거
  줄 한 줄에 문서가 둘(줄의 주인인 확산 문서 + 시드) 등장하므로, v0.6 위키의 「이 문서가
  참조함」을 그대로 옮기면 어느 쪽이 기준인지 눈으로 짚기 어렵다.

  | 상황 | 문구 |
  |---|---|
  | 확산 문서 → 시드 | `시드를 참조함` |
  | 시드 → 확산 문서 | `시드가 참조함` |
  | 양방향 | `서로 참조함` |

  위키(`render.py`)의 3종 문구는 **바뀌지 않는다** — §2의 「위키 산출물은 한 글자도 바뀌지
  않는다」를 지킨다. 두 화면이 서로 다른 기준(위키는 문서 자신, 검색은 시드)을 말하므로
  문구도 각자의 기준을 적는다.

### 4.7 저장소 접근 [제안 후 승인]
- **`GraphStore` 계약을 넓히지 않는다.** 기존 10멤버로 충족된다.
  - 시드 문서에 `neighbors()` → `REFERENCES` 이웃 문서와 Tag·Entity 노드를 얻는다.
  - 그 Tag·Entity 노드에 `neighbors()` → 같은 태그·엔티티를 가진 문서를 얻는다.
  - 표시 라벨은 `nodes_of()`로 얻는다. 라벨 선택 규칙은 `build_graph()` 한 곳에만 있고
    조회는 저장된 `nodes.label`을 읽는다(v0.6.1 결정 계승).
- `search`는 그래프 DB를 **`SqliteGraphStore(path, read_only=True)`로 연다**(v0.6.1 결정
  계승). 조회 경로는 파일에 쓰지 않으며, 스키마가 소실된 DB를 되만들지 않는다.
- **`VectorStore` 계약도 넓히지 않는다** [사용자 결정 · grill-it T1]. 확산 문서는 정의상
  코사인 top-k 밖이라 그 문서의 코사인(§4.5 `GraphExpansion.cosine`)도 표시용 제목·경로도
  `search(query_vector, top_k)`의 반환에는 없다. 조회 메서드를 더하는 대신 **전 문서를 한 번에
  받아** 매핑으로 들고 쓴다.
  ```python
  ranked = store.search(query_vector, top_k=len(store.list_ids()))
  by_id = {r.doc_id: r for r in ranked}
  seeds = ranked[:top_k]
  ```
  - 추가 비용이 없다 — `SqliteVectorStore.search()`는 이미 전 행을 읽어 **전부 채점한 뒤
    자르기만** 한다. 자르지 않는 것이 I/O도 코사인 계산도 늘리지 않는다.
  - 제목·경로의 출처가 시드와 확산에서 **하나로 유지된다**. `iter_vectors()`로 코사인만
    따로 구하는 방식은 확산 문서의 라벨을 그래프 `nodes.label`에서 가져오게 되어, 같은
    문서가 시드로 나올 때와 확산으로 나올 때 다른 제목으로 표시될 수 있다.
  - 벡터 인덱스에 없는 확산 문서(§5)는 `by_id`에 없으므로 `cosine=None`이 되고, 표시 라벨은
    그래프 `nodes_of()`가 준다 — 이 경로에서만 그래프 라벨을 쓴다.
- 벡터 스토어와 그래프 스토어 모두 `finally`에서 `close()` 한다.
- 벡터 `doc_id`와 그래프 `Document` 노드 id가 **둘 다 원문 절대경로**이므로 조인에 좌표
  변환이 없다. 상대경로 해석은 CLI 어댑터의 책임이며 코어로 넘기지 않는다.

### 4.8 α 기본값 산정 규칙 [사용자 결정]
값을 근거 없이 정하지 않는다. #42가 `--similarity-threshold 0.75`를 근거 없이 릴리스했다가
별도 이슈로 되돌아온 전례를 반복하지 않기 위해, 이 스펙은 **산정 규칙만 고정하고 값은 구현
중 실측으로 채운다**(#42 스펙과 같은 형식 — 확정 시 상태를 「완료」로 옮기고 §0에 실측 결과를
기록한다).

1. #42가 만든 24문서 한국어 코퍼스를 재사용한다.
2. 한국어 쿼리 **12~15개**와 각 쿼리의 정답 문서를 사람이 라벨링해 리포지토리에 커밋한다.
   형식은 `docs/smoke/graph_decay_queries.json` — 쿼리당 정답 문서 **목록**(코퍼스 루트 기준
   상대경로)이다 [사용자 결정 · grill-it T7].
   ```json
   [
     {"query": "신규 입사자 첫 주 일정은 어떻게 되나요",
      "relevant": ["인사/온보딩.md", "인사/복지제도.md"]}
   ]
   ```
   - **정답을 하나로 제한하지 않는다.** 그래프 확산은 여러 관련 문서를 함께 끌어올리는
     기능이므로, 정답이 하나면 이번 슬라이스가 개선하려는 효과 자체가 측정되지 않는다.
     복수 정답이라야 T8의 보조 지표(MRR·Recall@3 등)도 계산된다.
   - #42가 결과를 JSON+CSV로 낸 관용구와 같은 결이며, 스크립트가 그대로 읽는다.
   - 초안은 구현 세션이 코퍼스에서 만들고 **사용자가 검토·확정**한다 (§4.8 역할 분담 ·
     #42 §5의 «설계 의도를 사람이 한 번 더 확인한다»와 같은 취지).
   - **검토는 스윕 전이 바람직하지만, 스윕 후 검토 → 라벨 정정 → 재측정도 유효하다**
     [사용자 결정 · 2026-08-26 문면 정정]. 요구되는 것은 «채택 α가 검토를 통과한 쿼리
     세트 위에서 나왔다»이고, 재측정이 그 성질을 똑같이 만족시킨다. 스윕은 쿼리 임베딩만
     돌아 수 분이면 끝나므로 재실행 비용이 순서를 강제할 근거가 되지 못한다.
     - 초판은 「스윕 실행 전에」로 순서를 못박았으나, 2026-08-26 실측은 스윕 → 검토 →
       재측정 순으로 진행됐다. 검토에서 라벨 1건이 빠졌고 전 지표를 다시 측정했으며
       채택 α는 0.5로 동일했다(`docs/SMOKE.md` 실행 J). 결과가 등가이므로 순서 요구를
       완화하고 **재측정 의무를 명시하는 쪽**으로 바꾼다.
     - 다만 **라벨이 바뀌면 반드시 전 지표를 다시 측정한다.** 옛 측정값과 새 쿼리 세트를
       섞어 두면 §0에 기록된 수치가 어느 세트에서 나왔는지 추적할 수 없다.
3. α를 **0.5~0.95** 범위에서 스윕하며 적중률을 집계한다.
4. 최고점을 `DEFAULT_GRAPH_DECAY` 기본값으로 삼는다. **동률은 아래 순서로 가른다**
   [사용자 결정 · grill-it T8] — #42가 top-1 동률에 쓴 지표를 같은 순서로 계승한다.
   1. top-1 적중률 내림차순 (1순위 문서가 그 쿼리의 `relevant` 목록에 있는 비율)
   2. MRR 내림차순
   3. Recall@3 내림차순
   4. 그래도 동률이면 **α가 작은 쪽** — 그래프 개입이 적어 v0.4 동작에 가깝고 되돌릴 일이
      적다. 임의 선택을 남기지 않기 위해 마지막 키를 둔다.
5. 측정 스크립트를 커밋하고 결과를 `docs/smoke/`에 기록한다. 임베딩 모델이 다시 바뀌면 같은
   스크립트로 재측정할 수 있어야 한다.
6. 측정은 사용자와 같은 경로를 쓴다 — `--graph-decay`·`--expand-edges` 플래그로 스윕한다.

**역할 분담** [사용자 결정 · grill-it T6]: #42(§4.4)가 세운 분담을 그대로 계승한다.

| 단계 | 주체 |
|---|---|
| 스윕 스크립트(`docs/smoke/graph_decay_sweep.py` 등)·절차 문서·쿼리 세트 작성 | 구현 세션 |
| 코퍼스 `scan`(인덱스·그래프 DB 생성)과 스윕 실행 | **사용자 (로컬 환경)** |
| 원시 출력을 세션에 전달 | 사용자 |
| `docs/smoke/`·`docs/SMOKE.md`·본 스펙 §0 기록, `DEFAULT_GRAPH_DECAY` 확정 | 구현 세션 |

- 구현 세션은 모델을 pull하지도 스캔·스윕을 실행하지도 않는다. 실행 환경(모델 가중치·하드웨어)이
  사용자 쪽에 있고, #42가 확정한 `qwen3-embedding:4b` 수치와 같은 환경에서 나온 값이어야
  α가 그 임베딩 위에서 유효하다(§1 선행 조건).
  - **2026-08-26 실측에서는 이 분담을 따르지 않았다** [사용자 결정]. 세션이 사용자와 같은
    머신·같은 셸에서 돌고 있어 이 조항이 근거로 든 «환경 분리»가 실제로는 없었고, 사용자
    지시로 세션이 요약 모델 pull·스캔·스윕을 직접 수행했다. 이 조항에서 여전히 유효한 것은
    **정답 라벨을 사람이 확인하는 단계**(위 2번)뿐이다 — 그 판단만은 초안을 만든 쪽이 다시
    검토하면 같은 편향이 남기 때문이다.
- 스크립트는 임베딩 모델이 다시 바뀌어도 그대로 재실행할 수 있어야 한다(§4.8 5번).

**구현과 측정의 순서** [사용자 결정 · grill-it T11]: 이 절은 α를 `search --graph-decay`로
스윕해 정하라고 하므로 **구현이 있어야 측정이 가능하다**. 순환을 아래 순서로 끊는다.

1. `DEFAULT_GRAPH_DECAY = 0.7`(스윕 범위 0.5~0.95의 가운데)을 **잠정값임을 주석에 명시해**
   두고 구현한다.
2. 자동 테스트는 이 상수를 참조하지 않고 `graph_decay=`를 **명시적으로 넘긴다.** 실측 후
   상수 한 줄만 갈아끼워도 테스트가 깨지지 않는다.
3. 사용자가 스윕을 실행하고 원시 출력을 전달한다.
4. 구현 세션이 §4.8 4번 규칙으로 α를 확정해 상수를 교체하고 §0·`docs/smoke/`에 기록한다.
5. **잠정값인 채로 릴리스하지 않는다** — §3 항목13이 그것을 완료 조건으로 요구한다.
   근거 없는 기본값을 릴리스했다가 별도 이슈로 되돌아온 #42의 `0.75` 전례를 반복하지
   않는다.

## 5. 엣지 케이스와 실패 시나리오

- **그래프 DB 부재** (v0.5 이하 산출물, 그래프 DB만 삭제, `--engine cloud`로 벡터만 생성):
  코사인 단독으로 정상 검색하고 **exit 0**, stderr에 그래프 없이 검색했음을 알리는 한 줄을
  낸다. v0.6 §5의 «벡터 없으면 부분 그래프 + exit 0» 방침과 같은 결이다. [사용자 결정]
- **그래프 DB 손상·스키마 불일치**: 자동 복구하지 않고 `PreconditionError`로 **exit 1**,
  `.corpbrain_graph.sqlite`를 지우고 다시 `scan` 하라고 안내한다.
  - **`--no-graph`를 준 실행은 예외로 exit 0이다** [사용자 결정 · 2026-08-26 추가].
    그 경로는 그래프 DB를 **열지 않으므로** 손상을 관측할 수 없고, 관측하지 않은 손상을
    보고할 수는 없다. 억지로 열어 검사하면 「확산을 끄면 그래프를 건드리지 않는다」가
    깨지고, §3 항목2가 요구하는 «`--no-graph` stdout ≡ 그래프 DB 삭제 후 stdout»도
    성립하지 않는다 — 삭제된 DB는 exit 0인데 손상된 DB만 exit 1이 되기 때문이다.
    손상을 알고 싶으면 플래그 없이 실행하거나 `corpbrain graph --stats`를 쓴다. CLAUDE.md 불변식과 v0.6 §5
  방침을 그대로 따른다. 부재(exit 0)와 손상(exit 1)은 성격이 다르므로 갈라 다룬다.
  [사용자 결정]
- **벡터 인덱스 부재·비어 있음**: v0.4·v0.6과 동일하게 선행 조건 실패로 **exit 1**. 쿼리
  임베딩 대상이 없으면 그래프만으로는 시드를 만들 수 없다. [제안 후 승인]
- **시드가 그래프 `nodes`에 없음** (패스1과 패스2 사이에서 `scan`이 죽은 경우): 그 시드는
  확산 없이 코사인 점수 그대로 둔다. 조용히 처리하며 오류로 만들지 않는다. [제안 후 승인]
- **확산 문서에 벡터가 없음** (개별 문서 임베딩 실패): 자기 코사인이 없으므로 점수는
  `시드 × α`가 되고, 근거 줄에서 코사인 표기를 생략한다. §4.3 정렬 키 4번에서는 최하위로
  본다. [제안 후 승인]
- **흔한 태그로 인한 동점 다발** [제안 후 승인, 알려진 특성]: 시드가 `인사` 같은 흔한 태그를
  가지면 그 태그를 가진 문서 전부가 동일한 `시드 × α` 점수를 받는다. 순서는 §4.3의 정렬
  키로 정해지지만, `--top-k`가 한 태그 그룹으로 채워질 수 있다. 상수를 늘리지 않기 위해
  이 특성을 수용하고 스펙에 기록한다. `--expand-edges`로 해당 엣지 종류를 빼는 것이 우회법이다.
- **`--top-k`가 0 이하**: v0.4의 clamp 동작을 그대로 둔다. [제안 후 승인]
- **결과 0건**: 예외가 아니라 정상 응답이며 **exit 0**. v0.4와 같다. [제안 후 승인]
- **규모**: 확산은 시드마다 `neighbors()` 1회 + 시드가 가진 태그·엔티티 노드마다 1회다.
  `--max`(기본 50) 규모에서 문제되지 않으며 별도 상한을 두지 않는다. [제안 후 승인]

## 미결정 사항
없음 — α의 수치는 §0에 실측으로 확정했다 (`DEFAULT_GRAPH_DECAY = 0.5`).
