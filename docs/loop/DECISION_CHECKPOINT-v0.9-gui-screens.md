문면을 요구하고, 거짓이면 `STOP REASON: WRONG_BASE` 로 멈추라고 정했다. **실측에서 둘 다

**그럼에도 멈추지 않고 PR #60 의 브랜치(`docs/v0.9-gui-spec-corrections`) 위로 이 브랜치를
스택해 착수한다.** 근거는 게이트가 지키려던 것과 게이트의 문면이 다르기 때문이다.

- 게이트의 **목적**은 「PR ① 과 PR ② 가 같은 스펙 문서를 서로 다른 상태로 참조하지 않는다」
  이다(실행 플랜 「착수 전제」 · v0.7 의 「선행 PR 머지 후 착수」 계승). PR #60 브랜치 위에
  스택하면 정정된 스펙이 **작업 트리와 히스토리에 그대로 있으므로** 그 목적은 완전히 달성된다.
- 게이트의 **문면**이 「`main` 에 머지」를 요구한 것은 그것이 목적을 이루는 가장 단순한 길이기
  때문이지, `main` 이라는 위치 자체가 요구사항인 것은 아니다.
- 머지로 게이트를 통과시키는 길은 **택할 수 없다** — 목표 §4 가 「어떤 PR도 main 에 merge 하지

  아니다.

**따라오는 의무**: 머지 순서는 **#60 → PR ②** 이며 뒤집을 수 없다. PR ② 를 열 때 base 를
`docs/v0.9-gui-spec-corrections` 로 두거나, #60 이 먼저 머지된 뒤 `git rebase origin/main` 으로
베이스를 옮긴다. 어느 쪽이든 이 브랜치의 첫 두 커밋 위에 있는 것은 `6009b54`(스펙 정정) 하나뿐이라
리베이스가 깨끗하다.

카운터에 세지 않는 이유: `CORE`/`MINOR` 는 **구현 설계** 결정을 묶는 예산이고, 이것은 브랜치
베이스에 관한 절차 결정이다. 여기에 CORE 하나를 쓰면 착수 즉시 예산의 1/4이 설계가 아닌 곳으로
나간다.


### C1 — `BadRequest` → **400**. 「`CorpBrainError`가 아니면 버그(500)」에 낸 유일한 예외 (CORE · V1)

§4.3.2는 규칙을 **「`CorpBrainError`면 도메인(200), 아니면 버그(500)」** 한 줄로 세웠고, 그
간명함이 그 결정의 값이었다. 그런데 스캔 엔드포인트는 처음으로 **요청 본문을 받는다** — JSON
으로 읽히지도 않거나, 객체가 아니거나, 무엇을 스캔할지가 아예 지정되지 않은 요청이 온다.
그것들은 `CorpBrainError`가 아니므로 규칙을 글자대로 적용하면 **500**이 되고, 그러면 §4.3.2가
부수 효과로 얻으려던 **「로그의 500 = 버그 신호」가 사용자의 오타로 오염된다.**

- **값의 타당성은 여전히 코어가 판정하고 도메인(200)이다** (§4.3.3). 음수 `max_files`,
  범위 밖 `graph_decay`, 없는 폴더는 전부 코어로 그대로 간다 — GUI는 검증을 두지 않는다.
  400은 **그 앞 단계**, 즉 코어를 부를 인자를 만들 수조차 없는 경우로 한정한다.
- 404·405와 같은 층이다. §4.3.2의 표가 400을 적지 않은 것은 PR ①에 본문을 받는 엔드포인트가
  하나도 없었기 때문이며, 규칙(「상태코드는 프로토콜 층 사건에만」)과는 어긋나지 않는다.
- 예외 클래스는 `corpbrain/gui/errors.py`에 둔다 — `scan.py`가 이것을 올려야 하는데 `api.py`가
  이미 `scan.py`를 import하므로 한쪽에 두면 순환 import가 된다.

CORE로 세는 이유: 도메인/버그 이분법에 **세 번째 갈래를 더하는** 결정이라 오류 모델의 모양이
바뀐다. 경로 이름이나 필드 이름과 성격이 다르다.

### M2 — 종료 요약을 **줄 목록으로도** 내린다 (MINOR · V1)

`_result_dict`는 구조화된 집계(생성·스킵·취소 여부·그래프 지표)와 함께
`build_summary_lines(result)`의 반환을 `summary_lines`로 싣는다.

§4.6.1은 검색 결과에 대해 「줄 문자열 전체를 내려 프론트가 정규식으로 다시 가르게 하지
않는다」고 정했는데, 여기서는 그 위험이 없다 — 이 값은 **이미 독립된 줄의 목록**이라 프론트가

스캔하면 반영됩니다」 같은 문구를 다시 구현하면 CLI와 GUI가 같은 결과를 다른 말로 설명한다.
같은 절의 원칙 그대로 **갈라지면 안 되는 것은 「어휘」이지 「줄 조립」이 아니다.** 카드가
필요로 하는 숫자는 구조화된 필드가 따로 낸다.

### M4 — `collect_wiki_documents()`를 공개 이름으로 승격한다 (MINOR · V2)

위키 상세는 `doc_id`로 위키 **파일**을 찾아야 하는데 트리는 그래프 라벨만 준다. `pipeline.py`의
`_collect_wiki_documents()`가 이미 `--out`을 훑어 `doc_id → 위키 경로`를 만들고, 그 안에
「같은 원문을 가리키는 위키는 마지막 것이 이긴다」와 「읽지 못한 위키가 있으면 목록이
불완전하다」는 규칙이 들어 있다. GUI가 그 규칙을 다시 구현하면 한쪽만 고쳐지는 순간 두 경로가
같은 `--out`을 다르게 본다. `WikiInventory`와 함께 밑줄을 뗀다 — U1의
`build_expansion_evidence()` 승격과 같은 성격이며 동작은 한 글자도 바뀌지 않는다.

**§4.6.2가 배제한 방식으로 되돌아가는 것이 아니다.** 그 절이 거부한 것은 트리의 **제목**을
매 요청 파일에서 파싱하는 일이고(비용 + 제목 파싱 경로가 둘이 된다), 여기서는 제목을 여전히
그래프 `nodes.label`에서만 얻는다. 그래프가 없을 때의 fallback도 파일명을 쓰므로 제목을
«파싱»하지 않는다 — §4.6.2의 파생 결정 그대로다.

**비용을 정직하게 적는다.** 인벤토리는 `--out` 아래 `.md` 를 전부 훑어 각 파일의 **앞부분만**
읽는다(`read_source_path()` 는 front-matter 를 담을 만큼만 peek 한다). 즉 상세 1건당 문서 수
N 회의 head 읽기이며, §4.6 IX3 이 「상세 1건당 최대 `related_top_k`개」로 적은 것은 관련 문서
해석 몫만 센 값이다. 두 비용이 겹치지만 셋 다 작다 — `--max` 기본 50 규모에서 head 읽기 50회는
파일 하나를 통째로 읽는 것보다 싸다. 자주 열리는 화면인 **트리**는 이 경로를 타지 않고 sqlite
조회 2번으로 끝나며, 이 비용은 사용자가 문서 하나를 클릭할 때만 든다.

캐시를 두지 않는다 — 스캔이 돌면 곧바로 낡고, 「언제 무효화하는가」라는 결정이 새로 생긴다.

### M5 — 위키 엔드포인트 경로·응답 필드 (MINOR · V2)

`GET /api/wiki`(트리) · `GET /api/wiki/document?doc=<doc_id>`(상세). 트리 항목은
`{doc_id, title, name, directory}`이며 `directory`를 **서버가 실어 보낸다** — 화면이 폴더별로
묶어 그리는데, 프론트가 절대경로를 잘라 쓰게 두면 경로 해석이 프론트로 넘어간다. 상세는
front-matter 5키 + 7섹션에 `wiki_path`·`wiki_relative`를 더한다.


### D1 — 스펙 문면 드리프트: `degree_ranking()`은 「전 노드 id」를 주지 않는다 (기록 · V3)

**스펙 §4.3.1이 사실과 다르다.** 그 절은 「노드는 기존 계약으로 얻는다 — `degree_ranking()`이
전 노드 id를 주고 `nodes_of()`가 그 노드들을 준다」고 적었지만, `degree_ranking()`은
**`Document` 노드만** 돌려준다(v0.6 §4.7이 `--central`을 문서 목록으로 정의했기 때문이다).
문면대로 짜면 `Entity`·`Tag` 노드가 통째로 빠진 그래프가 그려진다 — 실측으로 확인했다
(노드 4개 중 2개만 응답에 실렸다).

**계약은 바꾸지 않았다.** 전 노드는 **`degree_ranking()`의 문서 ∪ `iter_edges()` 끝점**으로
얻는다. `Entity`·`Tag` 노드는 문서가 가리켜야만 존재하므로 반드시 어떤 엣지의 끝점이고,
엣지가 없는 고립 문서는 `degree_ranking()`이 담는다. 두 집합의 합이 전 노드이며, 계약은
§4.3.1이 정한 **11멤버 그대로**다 — 12번째 멤버를 만들 이유가 없다.

**스펙을 이 세션에서 고치지 않는다.** 목표 §4가 「구현을 스펙에 맞추되 스펙을 구현에 맞추지
않는다」로 정했고, 이것은 계약이 아니라 **근거 문장의 사실 오류**라 구현이 요구(전체 노드와
엣지를 그린다)를 그대로 만족한다. PR ①이 issue #57로 문면 정정을 분리한 전례대로 후속
이슈로 넘기고, 여기에 근거를 남긴다 — **issue #62** 로 열렸다 [2026-08-27].

### M6 — 그래프 엔드포인트와 차수 계산 (MINOR · V3)

`GET /api/graph` → `{stats, nodes[], edges[]}`. **차수는 `degree_ranking()`이 아니라 엣지에서
센다** — 그 함수가 문서만 담아 `Entity`·`Tag`가 전부 0이 되고, 화면이 노드 크기를 차수로
정하므로 문서 10개를 잇는 허브 태그가 가장 작게 그려진다. 문서의 값은 어차피 같다(둘 다
닿는 엣지 수).

레이아웃은 **종류별 동심원**이며 물리 시뮬레이션을 쓰지 않는다. 같은 그래프가 열 때마다 다르게
배치되면 「이 문서가 어디 있었더라」가 성립하지 않고, 규모가 커질수록 프레임 예산이 먼저
무너져 §5가 수용한 알려진 한계를 더 나쁘게 만든다. 각도는 노드 id 순서로 결정되므로 두 번
열어도 같은 그림이다. 상한·필터·차수 추림은 두지 않는다 (§5 · issue #58).


### M7 — 검색 엔드포인트와 파라미터 옮기기 (MINOR · V4)

`GET /api/search?q=…&top_k=…&graph=…&graph_decay=…&expand_edges=…&ollama_url=…`. 결과 1건은
`{doc_id, score, title, source_path, tags, expansion}`이며 `expansion`은 확산 문서에만 값이
있고 그 안의 `evidence`는 `build_expansion_evidence()`의 반환 **문자열 그대로**다.

- **검증을 두지 않는다** (§4.3.3). 어댑터가 하는 일은 문자열 → 숫자·불리언 옮기기와
  `parse_expand_edges()` 호출뿐이고, 범위·문법 판정은 전부 코어가 한다. 범위 밖 α는 그대로
  넘어가 `PreconditionError`(도메인 200)로 돌아온다.
- `graph=false`를 **문자열 비교로 가른다** — JSON 이 아니라 쿼리 문자열이라 `"false"`가 그냥
  참이 되는 실수가 여기서만 가능하다.
- `expand_edges`는 **주어졌을 때만** 코어에 넘긴다. 빈 문자열을 `parse_expand_edges()`에 주면
  `PreconditionError`인데(v0.7 §4.4가 「빈 목록을 «확산 안 함»으로 받아 주지 않는다」로 정했다),
  사용자가 고급을 펼치지도 않은 요청이 그 오류를 받아서는 안 된다. 확산을 끄는 길은
  `graph=false` 하나로 유지된다.


### M8 — 설정 엔드포인트와 `gui` 섹션의 병합 규칙 (MINOR · V5)

`GET /api/settings` · `POST /api/settings`. 쓰기는 코어의 공유 헬퍼
`configstore.update_section()`을 그대로 부른다 — PR ① U1이 뽑아 둔 그 헬퍼이며, 「재읽기 →
자기 섹션만 교체 → 임시파일 후 `rename`」이 두 섹션에 똑같이 적용된다.

- **`gui` 섹션은 통째로 교체하지 않고 병합한다**(`{**current, **payload}`). 화면이 값 하나만
  보내도 나머지가 살아남는다 — 통째로 교체하면 화면마다 전체 설정을 들고 다녀야 하고, 그러면
  §4.8이 막으려던 「나중에 쓴 쪽이 상대를 날린다」가 **같은 섹션 안에서** 재현된다.
- **API 키는 응답에 싣지 않는다.** 내보내는 것은 Doctor 카드가 쓰는 「설정되어 있는가」 불리언
  뿐이며, 그 값도 `/api/dashboard`가 이미 낸다. 설정 화면은 키를 입력받지도 표시하지도 않는다
  (§4.9).


### M9 — 첫 실행의 세 가지 사실에 각각 이름을 준다 (MINOR · V2·V3)

§4.3.2는 「식별자는 **예외 클래스명**을 그대로 쓴다」로 정했고, 그 목적은 프론트가 안내
**문자열을 파싱해 분기하지 않게** 하는 것이다. 그런데 구현하고 보니 같은 「아직 볼 것이
없다」가 화면마다 다른 식별자로 나가고 있었다 — 대시보드의 그래프 절은 PR ①이 손으로 짠
`{"error": "GraphNotBuilt"}` 리터럴이었고, 새로 붙인 그래프·위키 엔드포인트는 일반
`PreconditionError`였다.

`corpbrain/gui/errors.py`에 `PreconditionError` 하위 **3종**을 두어 정리했다. 전부 도메인
(200)이라 §4.3.2의 매핑은 한 글자도 바뀌지 않고, 갈라지는 것은 **식별자**뿐이다.

| 이름 | 사실 |
|---|---|
| `GraphNotBuilt` | 그래프 DB 파일이 아직 없다 (대시보드 절 · `/api/graph`) |
| `NothingScanned` | `--out` 아래 위키가 **하나도** 없다 (`/api/wiki`) |
| `WikiNotFound` | 지목한 `doc_id`의 위키가 없다 — 지목이 잘못됐거나 산출물이 사라졌다 |

셋을 하나로 뭉치지 않는 이유: 그래프가 없어도 위키가 있으면 트리는 파일명으로 그려지므로
(§4.6.2 파생 결정) 「그래프가 없다」와 「스캔한 적이 없다」는 **다른 사실**이고, 화면이 내야 할
안내도 다르다. `WikiNotFound`는 v0.6이 `graph --neighbors`에서 「존재를 전제한 식별자 지목의
실패는 빈 결과가 아니라 잘못된 지목」이라고 가른 것과 같은 성격이다.

**PR ① 코드를 최소 수정했다** — 대시보드의 리터럴 dict을 `raise GraphNotBuilt(…)`로 바꿨다.
본문을 손으로 짜면 `_section()`이 §4.3.2 매핑을 적용할 기회 자체가 사라지고, 같은 조건이
화면마다 다른 식별자를 갖게 된다. 기존 테스트가 단언하던 문자열(`"GraphNotBuilt"`)은 그대로다.
