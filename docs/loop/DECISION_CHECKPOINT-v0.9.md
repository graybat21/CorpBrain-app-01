## CORE-1 — 관문 불변식 감시를 inbound 서버에 한해 정밀하게 넓힌다

**상황.** `tests/test_gateway.py::test_gateway_is_the_only_module_touching_the_network` 은
`corpbrain/` 아래 모든 모듈에서 `http`·`socket` 등 네트워크 모듈 import 를 금지한다.
GUI 서버는 `http.server.ThreadingHTTPServer` 를 쓰므로 이 감시에 걸렸다.

**충돌 지점.** v0.9 스펙 §4.11 은 "로컬 서버를 여는 것(인바운드)은 이 불변식의 대상이 아니다
— 관문은 나가는 호출만 다룬다"고 적었고, `gateway.py` 모듈 docstring 도 자신을 "프로세스의
유일한 외부 네트워크 **출구**"로 정의한다. 그런데 **감시 구현은 방향을 구분하지 않는다.**
스펙의 문면과 실제 감시가 어긋나 있었다.

**결정.** 모듈을 통째로 면제하지 않고 `_INBOUND_ONLY_MODULES` 에 **inbound 서버 모듈만**
허용한다.

- `corpbrain/gui/server.py` 에서 `http.server` 만 허용한다.
- 같은 파일에서도 `urllib.request`·`requests`·`socket` 같은 **outbound 수단은 여전히
  금지**된다. GUI 가 코어를 우회해 직접 나가는 호출을 하면 그것은 진짜 위반이다.
- 부수적으로 `corpbrain/gui/server.py` 에서 `socket` import 를 없앴다 — 쓰이지 않는
  `is_port_free()` 하나 때문에 들어와 있었고, `create_server()` 가 이미 포트 점유를
  처리한다.

**대안과 기각 사유.** ① 모듈 전체 면제 — 그 파일에서 `urllib.request` 도 허용하게 되어
불변식이 실질적으로 무너진다. ② `http.server` 를 지연 import — 감시는 통과하지만 규칙을
속이는 것이지 지키는 것이 아니다.

**반영.** `tests/test_gateway.py` (`_INBOUND_ONLY_MODULES` · `_is_allowed_inbound()` 신설).
스펙은 고치지 않았다 — 구현을 스펙에 맞추되 스펙을 구현에 맞추지 않는다(goal §4). 다만
§4.11 의 문면이 감시 구현보다 넓게 읽힌다는 사실을 여기 남긴다.

**범위 밖 파일 수정.** `tests/test_gateway.py` 는 goal §1 작업 대상 목록에 없다. 이 변경이
없으면 신규 모듈이 기존 테스트를 깨뜨려 완료의 정의(§3 항목11)를 만족할 수 없으므로 최소
범위로 수정했다.

## MINOR-1 — 그래프 통합테스트의 경로 비교를 구분자 무관하게 고친다

**상황.** `tests/integration/test_graph_pipeline.py` 의 2건이 Windows 에서 실패했다.
`test_graph_tuples_match_expected_set_exactly` 와 `test_unreadable_wiki_suspends_orphan_pruning`.

**원인.** 헬퍼 `_short()` 가 `node_id.endswith("인사/채용계획.docx")` 처럼 **슬래시**로
비교하는데, `doc_id` 는 원문 절대경로라 Windows 에서 `...\인사\채용계획.docx` 로 **역슬래시**다.
매칭이 실패해 절대경로가 그대로 남고 기대 집합과 어긋난다. 같은 이유로 고아 정리 테스트의
`doc_id.endswith("기타/메모.txt")` 도 항상 거짓이 된다.

**이것은 v0.9 가 만든 결함이 아니다.** GUI 는 그래프·파이프라인을 건드리지 않으며, 태그·
엔티티 노드는 두 테스트에서 완전히 일치한다. 어긋나는 것은 경로가 들어가는 항목뿐이다.
POSIX 에서만 통과하던 테스트가 이 작업 트리(Windows)에서 드러난 것이다.

**결정.** 비교 전에 구분자를 정규화한다(`\` → `/`). 기대값을 Windows 표기로 바꾸지 않는다 —
그러면 이번엔 POSIX 에서 깨진다. 프로덕션 코드는 건드리지 않는다. `doc_id` 가 원문 절대경로
문자열이라는 계약(`CLAUDE.md` v0.6 불변식)은 그대로다.

**범위 밖 파일 수정.** 위와 같은 이유로 최소 범위로 수정했다. 이 실패를 남겨 두면 goal 의
ALL_DONE 조건(`uv run pytest` exit 0)에 도달할 수 없다.

## MINOR-2 — 러너 관리 모듈을 `scanjob.py` 로 분리한다

**상황.** goal §1 은 GUI 모듈을 `__init__ · server · runner · workspaces · markdown · static`
여섯으로 적었다. 그런데 자식 프로세스의 수명 관리(기동·stdout 펌프·스냅샷 접기·중지)는
러너(자식 쪽 진입점)도 서버(HTTP 라우팅)도 아니다.

**결정.** `corpbrain/gui/scanjob.py` 를 하나 더 둔다. `runner.py` 는 **자식 프로세스가 실행하는
코드**이고 `scanjob.py` 는 **부모가 그 자식을 다루는 코드**라 방향이 반대다. 한 파일에 넣으면
자식이 자기 관리자를 import 하는 모양이 된다.

**반영.** `corpbrain/gui/scanjob.py` 신설, 테스트는 `tests/unit/test_gui_scanjob.py`.

## CORE-2 — 토큰을 `sessionStorage` 에 둔다

스펙 §4.6.1 초판은 «어디에도 저장하지 않는다»였고 새로고침마다 첫 진입 URL 을 요구했다.
사용자가 불편을 제기했고, **마찰만 남고 얻는 것이 없다**는 판단으로 뒤집었다. CSRF 방어는
커스텀 헤더가 하며 `sessionStorage` 는 출처별 격리라 방어가 유지된다. `localStorage` 는
여전히 금지(탭을 닫으면 사라져야 죽은 토큰이 디스크에 남지 않는다).

**반영**: 스펙 §4.6.1 정정 · `CLAUDE.md` v0.9 불변식 · `app.js`.

## CORE-3 — 모델 선택은 설정 화면 한 곳에서만

스캔 화면의 요약 모델·임베딩 모델 드롭다운을 없앴다.

- **임베딩 모델**은 실행 옵션이 아니라 **인덱스의 속성**이다. 스캔마다 바꾸면 코어가 막으므로
  그 자리에 두면 «고르면 반드시 실패하는 항목»이 된다.
- **요약 모델**은 엔진이 클라우드일 때 모순이다 — `model`(Ollama)과 `cloud_model`(Anthropic)이
  따로인데 Ollama 목록만 보여 주므로, 클라우드를 고르면 아무 효과 없는 컨트롤이 된다.
- 스캔 화면은 대신 **엔진이 쓸 모델을 읽기 전용으로** 보여 주고 설정으로 데려가는 버튼을 둔다.

**반영**: 스펙 §4.7.1 정정 · `CLAUDE.md` · `index.html`·`app.js`·`app.css`.

## CORE-4 — 폴더 열기를 서버가 대신한다 (`POST …/reveal`)

B15 는 화면만으로 고칠 수 없다 — 브라우저가 원리적으로 못 하는 일이다. 서버가 파일 탐색기를
띄운다.

- **파일을 실행하지 않는다.** 요청 한 번이 매크로가 든 통합문서나 실행 파일을 띄우는 통로가
  되면 안 된다. 탐색기에서 그 파일을 **고른 채 폴더를 열고**, 여는 것은 사용자가 한다.
- 경로는 절대경로여야 하고 그 워크스페이스의 `source_dir`·`out_dir` 안이어야 한다.
- `subprocess.Popen` 을 인자 목록으로 부른다(셸 없음). 게이트웨이 감시는 네트워크 모듈만
  보므로 이 import 는 걸리지 않으며, `scanjob.py` 가 이미 같은 방식으로 러너를 띄운다.
- 테스트는 `_open_in_file_manager` 를 monkeypatch 해 창이 실제로 뜨지 않게 한다.

**반영**: 스펙 §4.7·§4.9 · `server.py` · `markdown.py` · `app.js`/`app.css`.

## MINOR-15 — 워크스페이스 버튼을 실제 드롭다운으로

**상황.** 사이드바 맨 위 워크스페이스 버튼은 아래 화살표와 `aria-haspopup="true"` 로
「메뉴가 열린다」고 알리는데, 눌러 보면 설정 화면으로 점프했다. 게다가
`renderWorkspaceButton()` 이 워크스페이스가 2개 미만이면 버튼을 `disabled` 로 만들어,
워크스페이스가 하나인 흔한 상황에서 사이드바에서 가장 눈에 띄는 컨트롤이 죽어 있었다.

**이것은 스펙을 어긴 상태였다.** §4.8 은 사이드바 구성을 「워크스페이스 **선택** → 메뉴
3개 → 하단 설정」으로 적는다. 스펙을 고칠 일이 아니라 구현을 스펙에 맞췄다.

**결정** [사용자 제안 · 사용자 결정].

- 버튼은 **드롭다운을 연다.** 고르면 `useWorkspace(ws)` → `show("dash")` — 그 워크스페이스의
  대시보드로 간다. 이미 활성인 항목을 다시 고르면 아무것도 지우지 않는다(열어 둔 본문이
  이유 없이 닫히지 않게).
- **드롭다운은 전환만 한다.** 맨 아래 구분선 뒤에 **한 줄**이 설정 화면으로 데려간다.
  두 줄(「관리」+「추가」)로 나누지 않는다 — 설정의 추가 폼이 워크스페이스 카드 안에
  함께 있어 목적지가 같기 때문이다. **목록이 비었을 때만** 글자가 「워크스페이스 추가…」로
  바뀐다. 관리할 것이 없는데 「관리」라고 적지 않는다 [사용자 결정].
- **목록이 비거나 하나뿐이어도 버튼은 열린다.** 그때가 「추가」로 가는 길이 가장 필요한
  순간이다.
- 고르는 자리가 둘이 되지 않도록 **설정 화면의 「열기」 버튼을 뗐다.** 그 화면은 관리
  (추가·제거)를 맡고 어느 것이 활성인지는 읽기 전용(「활성」 표시)으로만 보여 준다 —
  모델 선택을 설정 한 곳으로 모은 CORE-3 과 같은 잣대다.
- 여닫기는 **「?」 도움말과 같은 관용구**다(바깥 클릭·Esc). 버튼에 `?` 아이콘을 달지는
  않는다 — 화살표가 이미 「눌러 보면 열린다」를 말한다 [사용자 결정].

**반영.** `index.html`(`.wsmenu` 컨테이너 + `#wsPop`) · `app.css`(`.wsmenu*`) ·

## MINOR-16 — 워크스페이스 목록에 상한을 두고, 추가 폼을 눈에 보이게 가른다

**상황** [사용자 피드백]. ① 설정의 워크스페이스 목록과 「추가」 폼 사이가 `border-top`

**결정.**

- 추가 폼을 **바탕색이 다른 상자**(`--surface-2`)에 담고 「새 워크스페이스 추가」 소제목을

- 목록에 `max-height` + 스크롤을 둔다. 드롭다운은 **목록에만** 스크롤을 걸고 구분선과

  (MINOR-9 와 같은 규칙 — 크기 값을 각자 적으면 한쪽만 바뀐다).

## B18 — 「관련 문서」 링크가 글자로만 보였다

**증상.** 본문 맨 아래 「관련 문서」의 `[제목](경로)` 가 눌리지 않고 마크다운 원문 그대로
보였다. 원인이 셋이 겹쳐 있었다.

1. `_SAFE_LINK` 가 `.`·`/`·`http`·`file` 로 시작하는 대상만 링크로 인정하는데, **같은 폴더**
   문서의 링크는 `채용계획.docx.md` 처럼 이름으로 시작한다.
2. 범용 `_LINK` 는 대상에 **공백을 허용하지 않는다.** 위키 파일명은 원본 이름을 그대로 이어
   붙이므로 `02. 환경설정 가이드.docx.md` 처럼 공백이 흔하다 — B15(「원본 파일 열기」)와
   **같은 결함이 같은 파일에 하나 더 남아 있었다.**
3. `<a href>` 로 만들어졌더라도 열리지 않는다. 위키는 정적 파일이 아니라 API 로 받아 화면
   안에서 여는 것이라 그 주소는 404 다.

**결정.** 마커 블록 **안에서만** `[제목](경로)` 를 `<button class="wikilink">` 로 낸다.
`render(body, base=<그 위키의 out_dir 기준 상대경로>)` 로 「그 위키 파일 기준」 상대경로
(v0.6 §4.5)를 풀어 `data-path` 에 담고, 클릭은 목록·그래프와 **같은 경로**(`openWikiByPath`)를
탄다. 버튼이라 `javascript:` 스킴이 실행될 길도 애초에 없다. 마커 밖의 링크는 종전대로 `<a>` 다.

**B19 — 대상에 괄호가 있으면 경로가 반토막 났다** [2026-09-03 실측]. `(출장형)` 처럼
괄호가 든 문서명에서 `[^)]+` 가 첫 `)` 에서 끊겨 `…환경조사서_(출장형` 으로 열려
「그런 위키가 없습니다」가 떴다. **「원문」 버튼에도 같은 결함이 있었다.** 정규식을 버리고
여는 괄호를 세며 읽는 `_scan_links()` 하나로 두 경로를 함께 고쳤다 — 링크 문법을 아는
자리를 한 곳으로 모은다. 공백·괄호를 견디고 중첩도 처리한다.
- 이로써 이 파일의 **링크 결함 세 번째**다(B15 공백 · B18 상대경로 · B19 괄호). 세 번 다
  「우리 템플릿은 그런 문자를 안 쓴다」는 전제에서 나왔는데, 대상 경로는 **사용자의 파일
  이름**이라 그 전제가 성립한 적이 없다.

**B20 — 괄호를 세는 방식으로도 부족했다** [2026-09-03 실측 · 사용자 질문에서 나옴].
「파일 이름에 `[]()` 가 여러 개 들어가도 되는가」를 실제로 넣어 보니 셋이 깨졌다.
① 여는 괄호만 있는 이름(`회의록 (1차.docx`)은 짝을 못 찾아 링크를 포기했고, ② 닫는 괄호만
있는 이름(`회의록 1차).docx`)은 거기서 끊겨 **조용히 엉뚱한 경로**가 됐으며(에러가 아니라
잘못된 링크라 더 나쁘다), ③ 제목에 `]` 가 있으면(`[대외비] …`) 제목이 끊겨 링크가 깨졌다.

**해결 — 줄의 형식이 우리 것이라는 사실을 쓴다.** 일반 마크다운 파서처럼 굴 이유가 없다.
`render_related_block()` 이 언제나 `[제목](대상)` + ` — 근거` 로 쓰므로, 경계는 **마지막
`](`** 이고 대상을 닫는 괄호는 **그 뒤가 줄 끝이거나 ` — ` 인 첫 `)`** 다. 뒤를 함께 보므로
대상 안의 `)` 와 근거 안의 `)`(태그가 `설계(안)` 인 경우)를 둘 다 넘긴다. 「원문」 줄은 줄
전체가 링크 하나이므로 **마지막 `)` 까지** 읽는다(`](` 가 둘 이상이면 이 지름길을 쓰지 않고
`_scan_links()` 에 맡긴다).

**교훈**: 링크 대상은 **사용자의 파일 이름**이라 마크다운 문법이 가정하는 «잘 쓰인 입력»이
아니다. 우리가 쓴 줄을 우리가 읽을 때는 그 형식을 근거로 삼는 편이 일반 파서 흉내보다
정확하다.

**남은 위험 — 진짜 결함은 상류에 있다** [2026-09-03 · 사용자 지적]. 「관대하게 읽는 것이
나중에 예기치 못한 에러를 만들지 않느냐」는 물음에서 나왔다. 확인한 사실:

- `core/render.py:_link()` 는 경로를 **아무 이스케이프 없이** 적는다. 그래서
  `기타/회의록 1차).docx.md` 는 위키 파일에 `- [회의록](기타/회의록 1차).docx.md) — …` 로
  적힌다 — **이 줄은 마크다운으로서 이미 뜻이 어긋나 있다.** VS Code 미리보기·Obsidian·
  GitHub 도 똑같이 잘못 읽는다. GUI 파서는 그 어긋남을 **보정**할 뿐 파일을 고치지 못한다.
- GUI 파서가 지는 위험은 «관대함»이 아니라 **결합**이다. 근거 구분자(` — `)나 줄 형식을
  코어에서 바꾸면 화면이 조용히 다른 문서를 열 수 있다. 그래서 코어의
  `render_related_block()` 출력을 그대로 GUI 파서에 먹이는 **왕복 테스트**를 뒀다
  (`test_gui_reads_exactly_what_the_core_writes`) — 결합을 없앨 수는 없고 **소리 나게** 둔다.
- **정석 해법은 코어 쪽이다**: 대상에 공백·괄호가 있으면 CommonMark 의 각괄호 형식
  `[제목](<대상>)` 으로 적는다. 그러면 파일 자체가 모호하지 않아 외부 뷰어도 바르게 읽고
  GUI 파서는 단순해진다. 다만 **코어 수정**이라 v0.9 §2 비목표에 걸리고 위키 산출물의
  바이트가 바뀐다.
- **지금은 현상태를 유지한다** [사용자 결정 · 2026-09-03]. 화면은 바르게 동작하고 왕복
  테스트가 결합을 지킨다. 남는 것은 **위키 파일이 외부 뷰어에서 어긋난다**는 사실이며,
  이는 v0.9 가 만든 결함이 아니라 v0.6 부터 있던 것이다. 코어 수정은 스펙 결정을 거쳐
  후속 슬라이스에서 판단한다(아래 「남은 일」).

**「관련 문서」는 한 줄로 유지한다** [사용자 결정 · 2026-09-03]. 제목과 근거가 길어 여러
줄로 접히면 항목 경계가 흐려진다. 넘치는 만큼은 `…` 로 줄인다(`<ul class="rel">` 에만
적용 — 요약 본문의 불릿은 종전대로 접힌다).

**근거 표시는 한 줄 그대로 둔다** [사용자 결정 · 2026-09-03]. 「제목 — 유사도 0.81 · 공유
태그 …」를 두 줄로 나누는 안을 냈으나 우선 현행 유지로 정했다. 근거 **문구 자체**는 바꾸지
않는다 — 화면이 위키의 글을 고쳐 쓰지 않는다는 M12 의 기준을 그대로 따른다. 용어를 바꾸려면
위키를 만드는 코어 렌더러를 고쳐야 하고, 그것은 v0.9 의 「코어 수정 안 함」 밖이다.

**반영.** `markdown.py`(`_REL_LINK`·`_related_item`·`_wiki_button`·`_resolve_wiki_link`) ·
`server.py`(`render(..., base=relative)`) · `app.js`·`app.css` ·

## CORE-5 — 그래프를 지도처럼 다룬다 (방사형 결정을 되돌림)

**상황** [사용자 지적]. 「그래프에서 다른 문서를 클릭하면 그래프가 아예 새로 그려진다.
지도를 검색하면 그 위치가 가운데로 오되 다른 점은 틀어지지 않는데, 위치가 틀어지는 것이
위화감이 든다.」

**확인한 사실.** 방사형 배치에서 **뜻을 가진 것은 「안쪽 고리 = 직접 이어짐」 하나뿐**이었다.
고리 위의 각도는 `angle = (i / ring.length) * 2π` — 서버가 준 노드 순서를 등분한 값이라
아무 뜻이 없고, 두 점 사이의 거리도 마찬가지였다. **뜻도 없는 것이 선택할 때마다 통째로
움직이고 있었다.**

**결정** [사용자 결정 · 2026-09-03 · MINOR-11 의 방사형을 되돌림].

- 배치는 워크스페이스마다 **한 번만** 계산해 고정한다. 이어진 문서끼리 당기고 모두가 서로
  밀어내게 두면 관계가 많은 문서들이 모이므로, **거리에 처음으로 뜻이 생긴다.**
- 문서를 고르면 점을 옮기는 대신 **카메라만** 그 점으로 옮긴다(0.36초). 확대 배율은 그대로
  두므로 확대해 둔 채로 골라도 유지된다.
- 「이웃이 누구인가」는 안쪽 고리 대신 **강조**가 답한다 — 닿는 선과 그 끝의 점을 밝히고
  나머지는 흐리게 한다. 아무것도 움직이지 않는다.
- **결정적이어야 한다.** 시작 위치는 `doc_id` 의 FNV 해시로 정하고 무작위를 쓰지 않는다 —
  열 때마다 지형이 달라지면 되돌리려던 문제가 이름만 바꿔 되살아난다. 테스트가
  `Math.random` 이 `app.js` 에 없음을 단언한다.
- 좌표는 **-1~1 의 추상 값**으로 저장하고 상자에 맞추는 것은 그리는 단계가 한다 — 창 크기를
  바꿔도 상대 위치가 변하지 않는다(확대를 그리는 단계에서만 적용하는 것과 같은 이유).
- 선은 **직선**으로 되돌렸다. 곡선은 방사형에서 지름을 가로지르는 선이 막대처럼 보였기
  때문이며, 고정 배치에는 그 문제가 없다.
- 라벨은 고리 간격으로 일괄 판정하던 것을 **실제로 겹쳐 보고** 접는 방식으로 바꿨다(고리가
  없으므로 간격이라는 개념이 성립하지 않는다). 고른 문서와 이웃이 먼저 자리를 잡는다.

**§4.11 불변식과의 관계.** 좌표 계산은 **그림을 그리기 위한 것**이지 저장된 값을 다시
만드는 것이 아니다. 화면은 중심성·클러스터 같은 파생값을 지어내 **표시하지 않는다** —
방사형도 좌표를 계산했다는 점에서 다르지 않다.
