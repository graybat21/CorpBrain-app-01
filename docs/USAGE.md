# CorpBrain 사용 설명서

흩어진 로컬 문서를 자동 구조화된 마크다운 위키로 바꾸는 CLI 도구다. **기본 동작은 100% 로컬**
이며, 그 상태에서 외부로 나가는 통신은 로컬 Ollama 호출 하나뿐이다. `[v0.5]`부터 클라우드 요약을
**옵트인**으로 켤 수 있으며, 켜지 않으면 v0.4까지와 완전히 동일하게 동작한다.

이 문서는 현재 버전(**v0.7 진행 중**, 임베딩 모델 기본값과 `search` 그래프 확산이 반영됨) 기준이며,
각 기능이 처음 등장한 버전을 `[v0.1]` / `[v0.2]` / `[v0.3]` / `[v0.4]` / `[v0.5]` / `[v0.6]` /
`[v0.7]`로 표시한다.

> ⚠️ **v0.4 파괴적 변경(BREAKING)** — `scan`은 이제 위키 생성과 함께 **항상 벡터 인덱싱까지
> 수행**한다. 그러려면 임베딩 모델(기본 `qwen3-embedding:4b`, `[v0.7]`부터 — 이전 기본값은
> `nomic-embed-text`, §13.5 참고)이 로컬에 있어야 하며, 없으면
> **`scan`이 차단**된다(exit 1, `ollama pull qwen3-embedding:4b` 안내). 별도 플래그로 끌 수 없다 —
> `corpbrain doctor`로 미리 확인하자.

> ⚠️ **v0.3 파괴적 변경(BREAKING)** — v0.2까지 `scan`은 GPU가 없어도 그냥 돌았지만, v0.3부터는
> **GPU가 감지되지 않으면 `scan`이 차단**된다(exit 1). CPU로 실행하려면 `--force-gates`를 붙여야
> 한다. 참고: GPU 감지는 `nvidia-smi` 기반이라 **Apple Silicon·AMD GPU는 CPU로 판정**되어 역시
> `--force-gates`가 필요하다. `plan` / `--dry-run` / `doctor`는 차단하지 않는다.

## 2. 사전 준비

1. **Python 3.12** 와 패키지. 이 저장소는 [`uv`](https://docs.astral.sh/uv/)로 관리한다.
   ```bash
   uv python install 3.12
   uv venv --python 3.12
   uv pip install -e .
   ```
   이후 모든 명령은 `uv run` 접두어로 실행한다(`uv run corpbrain ...`).
2. **Ollama** (요약·인덱싱에 필요 — `scan`에서 사용). 로컬에서 구동 중이어야 한다.
   CorpBrain은 **탐지만** 하며 설치하지 않는다.
   ```bash
   ollama serve                       # 로컬 서버 (기본 127.0.0.1:11434)
   ollama pull qwen2.5:7b-instruct    # 기본 요약 모델
   ollama pull qwen3-embedding:4b     # 기본 임베딩 모델 [v0.4, 모델은 v0.7에서 변경] — 없으면 scan이 exit 1로 차단됨
   ```
   > `plan` / `scan --dry-run`은 Ollama가 필요 없다(LLM·네트워크 0).

## 3. 빠른 시작

```bash
# 1) 먼저 값싸게 훑어보기 — 무엇이 중요하고 얼마나 걸릴지  [v0.2]
uv run corpbrain plan ./inbox

# 2) 실제 변환 — 문서마다 위키 1개 생성 + 벡터 인덱싱 (Ollama 필요)  [v0.1, 인덱싱은 v0.4]
uv run corpbrain scan ./inbox --out ./wiki

# 3) 처리 없이 예상만 보기  [v0.2]
uv run corpbrain scan ./inbox --dry-run

# 4) 위키가 쌓인 폴더에서 관련 문서 검색 (v0.7부터 그래프 확산이 기본)  [v0.4, v0.7]
uv run corpbrain search "휴가 정책" --out ./wiki

# 5) 브라우저에서 쓰기 — 토큰이 실린 URL 이 stdout 에 나온다  [v0.9]
uv run corpbrain gui --out ./wiki
```

## 4. `corpbrain scan` — 스캔 → 요약 → 위키  `[v0.1]`

폴더를 재귀 순회해 지원 포맷 문서를 텍스트 추출하고, 로컬 Ollama로 요약·구조화한 뒤,
**입력 문서 1개당 위키 마크다운 1개**를 생성한다.

```
uv run corpbrain scan <folder> [옵션]
```

| 옵션 | 기본값 | 설명 | 버전 |
|---|---|---|---|
| `--out DIR` | `./corpbrain_wiki` | 위키 출력 폴더(입력 폴더 구조를 미러링) | v0.1 |
| `--model NAME` | `qwen2.5:7b-instruct` | 요약 모델. 환경변수 `CORPBRAIN_MODEL`로도 지정(플래그가 우선) | v0.1 |
| `--max N` | `50` | 스캔 대상 상한. 초과 시 **처리 중단 + 알림** | v0.1 |
| `--max-chars N` | `12000` | 문서당 요약 입력 상한 글자 수(앞부분만 사용) | v0.1 |
| `--ollama-url URL` | `http://127.0.0.1:11434` | 로컬 Ollama 주소 | v0.1 |
| `--force` | (off) | 원문 mtime과 무관하게 강제 재생성 | v0.1 |
| `--dry-run` | (off) | 처리 없이 pre-scan 리포트만 stdout으로(위키 0개) | **v0.2** |
| `--force-gates` | (off) | 차단 게이트(GPU·토큰)를 무시하고 강행. `file_too_large` 스킵에는 영향 없음 | **v0.3** |
| `--max-file-size MB` | `20` | 개별 파일 크기 상한(MB). 초과 파일은 `file_too_large`로 스킵 | **v0.3** |
| `--max-total-tokens N` | `200000` | 스캔 전체 예상 토큰 예산. 초과 시 **차단**(exit 3) | **v0.3** |
| `--embed-model NAME` | `qwen3-embedding:4b` | 인덱싱에 쓸 임베딩 모델. 환경변수 `CORPBRAIN_EMBED_MODEL`로도 지정(플래그가 우선). 없으면 `scan` 차단(exit 1). 기본값은 v0.7에서 `nomic-embed-text`에서 교체됨(§13.5) | **v0.4** |
| `--similarity-threshold F` | `0.5717` | 지식그래프의 유사도 엣지를 만드는 코사인 하한(이 값 **이상**이면 연결). 기본값은 v0.7에서 `0.75`에서 재산정됨(§13.5) | **v0.6** |
| `--related-top-k N` | `5` | 위키 「관련 문서」 섹션에 넣을 최대 항목 수 | **v0.6** |

**자원 게이팅 `[v0.3, v0.4에서 토큰 산정 확장]`** — 본격 처리 전에 세 축을 강제한다:
- **GPU**: 미탐지면 `scan` 차단(exit 1). `--force-gates`로만 CPU 강행.
- **토큰**: 스캔 전체 예상 토큰(v0.4부터 임베딩 비용 근사 10% 포함)이 `--max-total-tokens`를
  넘으면 차단(exit 3). `--force-gates`로 강행.
- **파일 크기**: 개별 파일이 `--max-file-size`를 넘으면 그 파일만 스킵하고 나머지는 계속(부분 성공).
  `--force-gates`로 우회되지 않으며, 포함하려면 `--max-file-size`를 올린다.

**벡터 인덱싱 `[v0.4]`** — 위키 생성과 함께 항상 수행된다(옵트인 플래그 없음):
- 문서당 벡터 1개(위키 요약 콘텐츠를 청크 분할 없이 임베딩), `<out>/.corpbrain_index.sqlite`에 저장.
- 위키가 mtime상 스킵돼도 인덱스에 벡터가 없으면 기존 위키에서 채워 넣는다(백필). `--force`는 둘 다 강제 재계산.
- 원문·위키가 사라지면 다음 `scan`에서 인덱스의 대응 벡터를 정리한다(고아 벡터 없음).
- 프리플라이트를 통과한 뒤 개별 문서의 임베딩 호출만 런타임에 실패하면, 위키는 그대로 두고
  해당 문서의 인덱싱만 실패로 기록한다(부분 성공, exit 0).

**동작 규칙**
- 진행 로그·종료 요약은 **stderr**로 나가고 **stdout은 비어 있다**(파이프 친화적).
- 재실행 시 원문 mtime이 기존 위키보다 최신일 때만 재생성한다(아니면 `up_to_date`로 스킵). `--force`로 무시.
- 텍스트는 앞부분 `--max-chars`까지만 읽는다(파일을 통째로 메모리에 올리지 않음).
- 개별 파일 실패는 **전체 실패로 위장하지 않는다** — 해당 파일만 스킵하고 나머지는 계속(부분 성공).
- `--out`이 스캔 대상 폴더 **안**에 있으면(예: `scan ./docs --out ./docs/wiki`) 그 하위 트리는
  자동으로 스캔에서 제외된다 — 위키 산출물(`.md`)이 다음 실행에서 새 입력 문서로 재처리되는
  것을 막기 위함이다. 이때 stderr에 제외 안내가 한 줄 뜬다. **그래도 `--out`은 스캔 대상 밖의
  형제 폴더로 두는 것을 권장한다**(예: `--out ./docs-wiki`) — 더 명확하고, `--out`이 스캔
  대상과 완전히 같은 경로인 경우(원본과 산출물이 한 폴더에 섞임)는 이 안전장치가 다루지 않는다.

**시작 배너 `[v0.2]`** — `scan`을 실행하면 처리 전 stderr에 한 줄 요약이 먼저 뜬다:
```
pre-scan: 6개 파일 · 예상 소요 약 1분 54초 (근사)
중요도 TOP 3: report.docx, guide.md, empty.txt
```

**예시**
```bash
uv run corpbrain scan ./inbox --out ./wiki --model qwen2.5:7b-instruct
uv run corpbrain scan ./inbox --max 200 --force
CORPBRAIN_MODEL=llama3.1:8b uv run corpbrain scan ./inbox   # 환경변수로 모델 지정
```

## 5. `corpbrain plan` — pre-scan 계량  `[v0.2]`

본격 스캔 **전에** 폴더를 값싸게 훑어 "무엇이 중요하고 얼마나 걸릴지"를 먼저 보여 준다.
**LLM·네트워크를 전혀 쓰지 않으며**(소켓 0), 파일 내용을 열지 않고 경로·`os.stat` 크기만 사용한다.

```
uv run corpbrain plan <folder> [--max N] [--max-chars N]
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--max N` | `50` | scan 상한 **경고 기준**. plan은 중단하지 않고 초과 시 경고만 표시 |
| `--max-chars N` | `12000` | 예상 토큰 추정의 문서당 상한 글자 수 |
| `--max-file-size MB` `[v0.3]` | `20` | 게이트 판정 **표시용** 개별 파일 상한(MB) |
| `--max-total-tokens N` `[v0.3]` | `200000` | 게이트 판정 **표시용** 토큰 예산 |

리포트는 **stdout**으로 나가며 다음을 담는다:
- **중요도 내림차순 TOP 20행** + "…외 M건"
- **합계**: 파일 수 · 총 예상 토큰 · 예상 소요(근사)
- **감지 하드웨어**(GPU 이름 또는 CPU)
- **게이트 판정(표시만)** `[v0.3]` — GPU·토큰·`file_too_large` 예정 파일 수. `plan`은 차단하지 않는다.
- 발견 수가 `--max`를 넘으면 경고 한 줄

```
CorpBrain pre-scan 계량 — 중요도 상위 6개 (근사)
  [ 58] report.docx  (.docx, ~880 tok)
  [ 45] guide.md  (.md, ~11 tok)
  ...
합계: 6개 파일 · 예상 토큰 5,709 · 예상 소요 약 1분 54초
감지 하드웨어: GPU: NVIDIA GeForce GTX 1050
```

**중요도 점수(0~100)** 는 파일 내용을 읽지 않고 경로·이름·확장자·트리 깊이만으로 결정적으로 매긴다:
- 확장자 기본점수(`.pdf`/`.docx`/`.xlsx`/`.xlsm`/`.pptx` 40, `.md` 30, `.txt` 25)
- 루트에 가까울수록 가산(깊이 페널티, 하한 −20)
- 신호 키워드(계약·보고서·report·spec·제안·계획·최종·final·정책) 가산(최대 +30)
- 잡음 키워드(temp·tmp·backup·사본·copy·old·임시·draft·archive·`~$`) 감산(최대 −30)

> 예상 토큰·시간은 "**근사**"다(정적 처리율 기반). 실측 rate 보정은 후속 예정(v0.3 비목표).

## 6. `corpbrain search` — 유사 문서 검색  `[v0.4, v0.7에서 그래프 확산 추가]`

`scan`이 만든 벡터 인덱스에서 자연어 쿼리와 유사한 문서를 찾고, `[v0.7]`부터 **지식그래프로
이어진 문서를 후보에 끌어올려** 재순위화한다. RAG의 "답변 생성" 단계는 포함하지 않는다 —
검색 결과(제목·경로·점수) 목록까지만 낸다.

```
uv run corpbrain search <query> [--out DIR] [--top-k N] [--ollama-url URL]
                                [--no-graph] [--graph-decay FLOAT] [--expand-edges LIST]
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--out DIR` | `./corpbrain_wiki` | `scan --out`으로 위키·인덱스·그래프 DB가 쌓인 폴더 |
| `--top-k N` | `5` | 시드 개수이자 최종 결과 개수 |
| `--ollama-url URL` | `http://127.0.0.1:11434` | 로컬 Ollama 주소 |
| `--no-graph` `[v0.7]` | 꺼짐 | 그래프 확산 없이 코사인 단독 (v0.4 동작) |
| `--graph-decay FLOAT` `[v0.7]` | `0.5` | 확산 감쇠 계수 α — **0과 1 사이**(양 끝 제외). 기본값에서는 확산이 순위를 바꾸지 않는다 → §6.3 |
| `--expand-edges LIST` `[v0.7]` | `CONTAINS_ENTITY,REFERENCES,TAGGED_WITH` | 확산에 쓸 엣지 종류(쉼표 구분) |

쿼리 임베딩은 **인덱스에 기록된 모델을 강제로 사용**한다 — `--embed-model` 플래그는 없다(인덱싱
시와 검색 시 모델이 달라 벡터 공간이 어긋나는 사고를 원천 차단).

### 6.1 그래프 확산이 하는 일 `[v0.7]`

코사인 상위 `--top-k` 문서를 **시드**로 삼고, 각 시드와 태그·엔티티·명시적 참조로 이어진 문서를
후보에 추가한다. 확산 문서의 점수는

```
점수 = max( 자기 코사인,  기준 시드 점수 × α )
```

이며, `0 < α < 1` 이므로 **확산 문서가 자기 시드를 추월하는 일은 없다**. 재순위화 뒤 다시
`--top-k`로 자르므로, 확산 문서가 들어온 만큼 코사인 하위 시드는 밀려난다(의도된 동작이다).

다음은 `--graph-decay 0.7` 로 확산을 켠 예다(기본값 `0.5` 에서는 §6.3 대로 확산 문서가
결과에 들어오지 않는 경우가 많다). 시드 `0.710 × 0.7 = 0.497` 이 두 확산 문서의 점수가 된다.

```
검색 결과 3건
  1. [0.710] 신입사원 온보딩 가이드 — /work/docs/인사/온보딩.md
  2. [0.497] 2026년도 신입 채용 계획 — /work/docs/인사/채용계획.docx
       └ 코사인 0.380 · 시드 «신입사원 온보딩 가이드» · 공유 태그 `인사` · 공유 엔티티 `인사팀` · 서로 참조함
  3. [0.497] 사내 복지제도 — /work/docs/인사/복지제도.md
       └ 시드 «신입사원 온보딩 가이드» · 공유 태그 `인사`
```

3번 문서는 벡터가 없어(개별 임베딩 실패, §5) 점수가 `시드 × α` 그대로이고 「코사인 …」
항목이 생략됐다. 2번은 자기 코사인 `0.380` 이 `0.497` 보다 낮아 `max()` 가 `시드 × α` 를
골랐고, 그래서 대괄호 숫자와 코사인이 서로 다른 값으로 함께 적힌다.

- **근거 줄(`└`)은 확산으로 후보가 된 문서에만** 붙는다. 시드는 코사인 상위라 이유가 자명하다.
- 대괄호 안 숫자는 **최종 점수**다. 코사인이 아닐 수 있으므로 근거 줄이 원 코사인을 함께 적는다.
  두 값이 같거나 그 문서에 벡터가 없으면 「코사인 …」 항목을 생략한다.
- 참조 문구는 기준이 **시드**다 — `시드를 참조함`(확산 문서 → 시드) · `시드가 참조함`(시드 →
  확산 문서) · `서로 참조함`. 위키 「관련 문서」의 문구(기준이 그 문서 자신)와 다른 것은
  두 화면이 서로 다른 기준을 말하기 때문이다.

`--expand-edges`는 `graph --stats` 출력·그래프 DB의 `type` 컬럼과 **같은 문자열**을 받는다
(`TAGGED_WITH` · `CONTAINS_ENTITY` · `SEMANTICALLY_SIMILAR` · `REFERENCES`). 소문자나 별칭은
받지 않는다. `SEMANTICALLY_SIMILAR`가 기본에서 빠져 있는 것은 임베딩 코사인 그 자체라 같은
신호를 두 번 세게 되기 때문이며, 필요하면 목록에 넣어 켤 수 있다.

빈 목록(`--expand-edges ""`)은 받지 않는다 — 확산을 끄는 길은 `--no-graph` 하나다.

### 6.2 종료 코드

**종료 코드**: `--out` 폴더에 인덱스가 없거나(먼저 `scan` 필요) 쿼리 임베딩 자체가 실패(Ollama
다운 등)하면 `1`. `--graph-decay`가 범위 밖이거나 `--expand-edges`가 잘못된 값이어도 `1`.
그래프 DB가 **손상**되었거나 스키마가 맞지 않아도 `1`(자동 복구하지 않는다 — 파일을 지우고 다시
`scan`). 단 **`--no-graph`를 주면 그래프 DB를 아예 열지 않으므로 손상 여부와 무관하게 `0`이다**
— 손상을 확인하려면 플래그 없이 실행하거나 `corpbrain graph --stats`를 쓴다. 그래프 DB가
**없는** 것은 정상이라 `0`이며, 코사인 단독으로 검색했음을 stderr에 한 줄 알린다. 인덱스는 정상인데 일치 문서가 0건이면 `0`("일치하는 문서가 없습니다"). 정상 결과도 `0`.
유사도 임계값은 없다 — top-K를 점수와 함께 그대로 보여주므로 점수를 보고 판단한다.

### 6.3 기본값에서는 확산이 순위를 바꾸지 않는다 `[알려둘 것]`

`--graph-decay` 기본값은 **`0.5`** 이고, 이 값에서는 대개 **확산 문서가 결과에 들어오지
않는다** — 출력이 `--no-graph` 와 같아진다. 실수가 아니라 실측으로 고른 값이다.

**왜 그렇게 정했나.** 24문서 한국어 코퍼스와 사람이 라벨링한 쿼리 15개로 α를 0.5~0.95
스윕한 결과, **어떤 α에서도 그래프 확산이 코사인 단독보다 나은 순위를 내지 못했다**
(`docs/SMOKE.md` 실행 J). 확산이 개입할수록 지표가 단조 하락해, 규칙이 고른 최적값이
「개입하지 않는 지점」이 됐다.

```
설정            MRR      Recall@3
코사인 단독     0.2056    0.4000   ← 기준선
α=0.50~0.65     0.2056    0.4000   ← 기본값. 기준선과 동일
α=0.70~0.85     0.2056    0.3667
α=0.90          0.1900    0.2333
α=0.95          0.2022    0.3000
```

**원인은 엔티티 노드의 선택성이다.** 요약 모델이 뽑는 엔티티가 대부분 부서명이라, 그
코퍼스에서 `인사팀` 하나가 23문서 중 10개를 이었다. 시드가 그런 엔티티를 가지면 관련
문서 10개가 한꺼번에 같은 점수로 후보에 들어와 코사인 상위의 정답을 밀어낸다.

**그래서 어떻게 쓰나.**

- **그대로 둔다** — 기본값에서는 v0.4의 코사인 검색과 사실상 같은 결과를 얻는다. 손해가
  없다.
- **확산을 켜 보려면 α를 올린다.** `--graph-decay 0.85` 정도부터 확산 문서가 눈에 띄게
  들어온다. 여러분의 코퍼스는 엔티티 품질이 다를 수 있으므로, 몇 개 쿼리로 직접 비교해
  보는 것이 가장 빠르다.
  ```bash
  corpbrain search "쿼리" --out ./wiki --no-graph          # 코사인 단독
  corpbrain search "쿼리" --out ./wiki --graph-decay 0.85  # 확산을 세게
  ```
- **엔티티가 부서명으로 쏠려 있다면 그 엣지를 뺀다.** `graph --stats` 와
  `graph --neighbors` 로 확인한 뒤:
  ```bash
  corpbrain search "쿼리" --out ./wiki --expand-edges TAGGED_WITH,REFERENCES --graph-decay 0.9
  ```
  위 코퍼스에서 이 조합이 기준선보다 나은 MRR을 낸 유일한 설정이었다(0.2500 vs 0.2389).
  다만 표본이 얇아 기본값으로 삼지는 않았다.
- **근거 줄(`└`)이 판단 재료다.** 확산 문서에는 왜 올라왔는지가 항상 적히므로, 공유 엔티티가
  `인사팀` 같은 부서명뿐이면 그 확산은 신뢰하지 않는 편이 낫다.

`TAGGED_WITH`·`CONTAINS_ENTITY`·`REFERENCES` 엣지 자체는 정상 동작했다 — 문제는 엣지가
아니라 **엔티티 라벨의 품질**이다. 자세한 실측은 `docs/SMOKE.md` 실행 J를 본다.

## 7. `corpbrain doctor` — 환경 준비 점검  `[v0.3, v0.4에서 임베딩 모델 점검 추가]`

Ollama 설치·구동·대상 모델 존재와 GPU·게이트 임계를 한 번에 점검한다. **folder 인자가 없는
환경 전용** 명령이며, 전 항목을 점검해 집계 리포트를 stdout으로 낸다(fail-fast 아님).

```
uv run corpbrain doctor [--model NAME] [--embed-model NAME] [--ollama-url URL]
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--model NAME` | `qwen2.5:7b-instruct` | 존재를 점검할 요약 모델(환경변수 `CORPBRAIN_MODEL`도 가능) |
| `--embed-model NAME` | `qwen3-embedding:4b` | 존재를 점검할 임베딩 모델(환경변수 `CORPBRAIN_EMBED_MODEL`도 가능) `[v0.4, 기본값은 v0.7에서 변경]` |
| `--ollama-url URL` | `http://127.0.0.1:11434` | 로컬 Ollama 주소 |

점검 항목과 실패 시 안내(순서 = 설치 → 구동 → 대상 모델 → **임베딩 모델** → GPU → 게이트 임계값):
- Ollama **설치**(`shutil.which`) — 미설치 → `https://ollama.com 에서 설치`
- Ollama **데몬 구동**(`/api/tags`) — 미구동 → `ollama serve` 실행
- **대상 모델 존재** — 없음 → `ollama pull <model>`
- **임베딩 모델 존재** `[v0.4]` — 없음 → `ollama pull <embed-model>`
- **GPU 감지** — 없으면 경고(실패 아님)
- **게이트 임계값** 표시(정보)

**종료 코드**: 필수 조건(설치·구동·대상 모델·**임베딩 모델**)이 모두 충족되면 `0`, 하나라도
미충족이면 `1`. GPU 없음은 **경고**일 뿐 종료 코드에 영향을 주지 않는다.

```
CorpBrain doctor — 환경 점검
  [OK] Ollama 설치됨
  [OK] Ollama 데몬 구동 중
  [실패] 모델 없음: qwen2.5:7b-instruct — `ollama pull qwen2.5:7b-instruct`
  [실패] 임베딩 모델 없음: qwen3-embedding:4b — `ollama pull qwen3-embedding:4b`
  [경고] CPU — scan은 GPU 없이 --force-gates 필요
  [정보] 게이트 임계: 파일 20,000,000 bytes · 총토큰 200,000
준비 미완료 — 위 [실패] 항목을 해결한 뒤 다시 확인하세요.
```

## 7.5 `corpbrain gui` — 브라우저 GUI  `[v0.9]`

로컬 서버를 띄우고 브라우저에서 CorpBrain을 쓴다. **신규 런타임 의존성이 0**이며(표준
라이브러리 `http.server` + 빌드 스텝 없는 바닐라 JS/CSS), 외부 통신 규칙은 CLI와 같다 —
로컬 Ollama와 옵트인된 Anthropic 외에는 나가지 않는다.

```bash
uv run corpbrain gui --out ./wiki
```

```
CorpBrain GUI — http://127.0.0.1:53119/?token=T_U32cXyfcFPPBZMJZU3bPX4ZhBq3AZAveQ9aQoYELE
종료하려면 Ctrl+C 를 누르세요.
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--out DIR` | `./corpbrain_wiki` | 위키·인덱스·그래프 DB 위치 |
| `--no-browser` | (끔) | 브라우저를 자동으로 열지 않는다 |

- **포트는 OS가 고르는 빈 포트**이며 지정할 수 없다. 서버를 다시 띄우면 포트와 토큰이 모두
  바뀐다.
- **듣는 주소는 `127.0.0.1` 고정**이다. `--host` 플래그가 없다 — 원격에서 쓰려면 SSH 터널을
  쓴다. 멀티유저·계정 인증은 범위 밖이다.
- **토큰은 파일에 쓰이지 않고** 프로세스 수명과 같이 간다. 첫 접속에서 `HttpOnly` 세션
  쿠키로 교환되고, 브라우저 주소창의 토큰 쿼리는 곧바로 지워진다.
- 그 뒤 모든 요청은 **쿠키 + `Origin`/`Host` 검증**을 함께 통과해야 한다. 토큰은 같은
  머신의 다른 프로세스를, `Origin`/`Host`는 브라우저발 CSRF·DNS rebinding을 각각 막는다.
- 서버는 **포그라운드**로 떠 있고 `Ctrl+C`로 끝낸다.

### 화면

사이드바에 화면 6개가 있고, 주소창의 **해시가 화면 상태의 단일 출처**다(`#/graph?node=…`).
새로고침·뒤로가기·링크 공유가 모두 그대로 동작한다.

| 화면 | 상태 |
|---|---|
| 대시보드 | ✅ 환경 점검(Doctor)·지식그래프 규모·실행 상태 |
| 플랜 & 스캔 · 위키 탐색기 · 지식그래프 · 지식 검색 · 설정 | 다음 슬라이스 (지금은 빈 상태를 그린다) |

### 알려진 사항

- 위키의 「원문」은 `file://` 링크라 http 페이지에서 브라우저가 차단한다. GUI는 죽은 링크
  대신 **경로 표시 + 복사 버튼**으로 낸다 — 서버가 임의 파일을 OS 기본 앱으로 여는
  엔드포인트는 두지 않는다.
- 진행 스트림이 끊기면 브라우저가 자동으로 재연결하고, 서버는 접속 즉시 현재 스냅샷을 한 번
  보낸다. 그때까지의 **줄 단위 로그는 복원되지 않고** 집계로 대체된다.

## 8. 지원 포맷과 스킵 규칙

**지원**: `.docx` · `.txt` · `.md` `[v0.1]` · `.pdf`(텍스트 레이어) `[v0.2]` ·
`.xlsx` · `.xlsm` · `.pptx` `[v0.8]`

오피스 3종에서 뽑는 것은 **텍스트 레이어뿐**이다 `[v0.8]`.

- **엑셀(`.xlsx`·`.xlsm`)** — 내용이 있는 시트마다 `[시트: <이름>]` 경계 줄을 내고, 각 행의
  셀 값을 탭으로 잇는다. **숨긴 시트는 제외**되고, 수식 셀은 파일에 저장된 **계산값 캐시**를
  읽는다. Excel이 저장하지 않은 파일(스크립트·LibreOffice 생성)에는 그 캐시가 없어 수식 셀이
  비어 읽히며, 시트가 수식뿐이면 「빈 문서」로 스킵된다.
  - 알려진 한계: **숨긴 행은 제외되지 않는다.** 통합문서를 통째로 메모리에 올리지 않는
    읽기 전용 개봉에서는 행 숨김 여부를 판별할 수 없다(`openpyxl` 3.1.5 실측).
- **PPT(`.pptx`)** — 내용이 있는 슬라이드마다 `[슬라이드 N]` 경계 줄을 내고(`N`은 원본
  슬라이드 번호), 도형·표·그룹 도형 안의 텍스트를 파일에 적힌 순서대로 잇는다. 발표자 노트는
  `[노트]` 줄 뒤에 덧붙인다. 이미지만 있는 슬라이드는 경계 줄도 나오지 않는다.
- **암호로 보호된 통합문서·프레젠테이션**은 열 수 없어 「텍스트 추출 실패」로 스킵된다.
  암호를 풀어 다시 저장한 뒤 스캔한다.
- **구형 `.xls`·`.ppt`(97-2003 이진 포맷)와 `.pptm`·`.xltx`·`.xltm`은 지원하지 않는다** —
  「미지원 확장자」로 스킵된다. `.xlsx`/`.pptx`로 다시 저장하면 처리된다.

산출물을 만들지 않고 **스킵 리포트**에 사유와 함께 표시되는 경우:

| 사유(라벨) | 설명 |
|---|---|
| 미지원 확장자 | 지원 7종 외 (구형 `.xls`·`.ppt`, `.pptm` 등) |
| 빈 문서 | 내용 없음. 텍스트 없는 스캔 이미지 PDF `[v0.2]`, 계산값 캐시가 없는 수식 전용 통합문서·이미지만 있는 프레젠테이션 `[v0.8]` 포함 |
| 텍스트 추출 실패 | 손상·파싱 실패, **암호화 PDF** `[v0.2]`, **암호화 통합문서·프레젠테이션** `[v0.8]` |
| 권한 거부 | 읽기 권한 없음 |
| 경로 길이 초과(>260자) | 긴 경로 |
| LLM JSON 파싱 실패 | 모델 응답이 기대 형식이 아님(해당 파일만 스킵) |
| 최신 상태(재생성 불필요) | 기존 위키가 원문보다 최신(`--force`로 무시) |
| 파일 크기 초과 `[v0.3]` | 개별 파일이 `--max-file-size` 초과(`file_too_large`, `--force-gates`와 무관) |

**인덱싱 실패(스킵과 다름) `[v0.4]`** — 위 스킵 사유들과 달리 **위키는 정상 생성**되고 인덱싱만
실패한 경우, 종료 요약에 별도로 "인덱싱 실패 K건(위키는 생성됨)"으로 집계된다(프리플라이트를
통과한 뒤 개별 문서의 임베딩 호출이 런타임에 실패한 경우).

## 9. 출력 마크다운 구조

출력 위치는 `--out` 하위에 입력 폴더 구조를 미러링한다. 파일명은 **원본 확장자를 유지한 채**
`.md`를 덧붙인다: `report.docx` → `report.docx.md`, `a.txt` → `a.txt.md`, `notes.pdf` → `notes.pdf.md`,
`예산.xlsx` → `예산.xlsx.md` `[v0.8]`.

```markdown
---
source_path: "<원문 절대경로>"
generated_at: "<ISO8601>"
model: "<사용 모델>"
source_bytes: <숫자>
---

# <제목>

## 한 줄 요약
<한 문장>

## 핵심 포인트
- <불릿 3~7개>

## 요약
<문단 요약>

## 태그·키워드
<태그 목록>

## 원문
[원본 파일 열기](file://<원문 절대경로>)

<!-- corpbrain:related:start -->
## 관련 문서
- [<제목>](<이 파일 기준 상대경로>) — 유사도 0.81 · 이 문서가 참조함 · 공유 태그 `인사`
<!-- corpbrain:related:end -->
```

출력 언어는 항상 한국어다.

인덱스 파일은 `--out` 하위 숨김 파일 `.corpbrain_index.sqlite`에 저장된다 `[v0.4]` — 위키
`.md` 산출물과 생명주기를 함께하며, 사용된 임베딩 모델명을 메타데이터로 기록한다.

## 11. 자주 겪는 문제

- **`선행 조건 실패: 구동 중인 로컬 Ollama를 찾지 못했습니다`** → Ollama가 안 떠 있음. `ollama serve`
  실행 후 재시도. (`plan`/`--dry-run`은 Ollama 없이도 동작한다.) 먼저 `corpbrain doctor`로 상태 확인. `[v0.3]`
- **`선행 조건 실패: 대상 모델을 찾지 못했습니다`** `[v0.3]` → 모델 미설치. 안내대로 `ollama pull <model>`.
- **`선행 조건 실패: GPU를 감지하지 못했습니다`** `[v0.3]` → GPU 미탐지(또는 비-NVIDIA). CPU로 강행하려면
  `--force-gates`를 붙인다(느림). `corpbrain doctor`로 하드웨어 확인 가능.
- **`자원 게이트 차단: 스캔 전체 예상 토큰 …이 예산 …을 초과`** `[v0.3]` → `--max-total-tokens`를 올리거나
  입력 폴더를 좁히거나, `--force-gates`로 강행(v0.4부터 이 예산엔 임베딩 비용 근사도 포함된다).
- **`선행 조건 실패: 대상 모델을 찾지 못했습니다: qwen3-embedding:4b`** `[v0.4]` → 임베딩 모델 미설치.
  `ollama pull qwen3-embedding:4b` (다른 모델을 쓰려면 `--embed-model`). `corpbrain doctor`로 확인 가능.
- **`선행 조건 실패: 인덱스가 다른 임베딩 모델로 생성되어 있습니다`** `[v0.4]` → v0.7 이전에 만든
  인덱스(기본 모델이 `nomic-embed-text`였을 때)를 v0.7 이후 기본값으로 다시 스캔하면 뜬다.
  안내대로 기존 모델을 `--embed-model`로 맞추거나, 인덱스를 지우고 `--force`로 새로 만든다(§13.5).
- **`선행 조건 실패: 인덱스가 없습니다`** `[v0.4]` → `search`의 `--out` 폴더에 아직 `scan`을 돌리지
  않았거나 경로가 틀림. 먼저 `corpbrain scan <folder> --out <그 폴더>`를 실행한다.
- **모든 파일이 `LLM JSON 파싱 실패` + `CUDA error ... PTX ... unsupported toolchain`** → CorpBrain이
  아니라 **Ollama/GPU 문제**. VRAM이 작은 GPU에 큰 모델을 올릴 때 흔하다. 해결:
  - CPU로 강제: Ollama 종료 후 `CUDA_VISIBLE_DEVICES=-1` 로 `ollama serve` 재기동(느리지만 안정적)
  - 또는 더 작은 모델 사용: `ollama pull qwen2.5:3b-instruct` → `--model qwen2.5:3b-instruct`
- **출력이 레포/현재 폴더에 흩어짐** → `--out ./` 는 현재 폴더에 위키를 뿌린다. 전용 폴더(`--out ./wiki`)를 쓰자.
- **`--out`을 스캔 대상 폴더 안에 뒀다** → 안전하게 자동 제외되지만(권장 사항은 아님), 혼란을 피하려면
  `--out`을 스캔 대상 밖의 형제 폴더로 옮기자(예: `scan ./docs --out ./docs-wiki`).

## 12. 클라우드 옵트인 `[v0.5]`

기본은 로컬이다. 아래 절차를 **직접 밟은 경우에만** 문서 내용이 외부로 나간다.

### 12.1 켜는 법 (2단계)

```bash
# 1) 최초 1회 동의 — 로컬 설정 파일(~/.corpbrain/config.json)에 기록된다
corpbrain consent cloud --grant

# 2) API 키를 환경변수로 지정 (파일에 저장되지 않는다)
export ANTHROPIC_API_KEY=sk-ant-...      # Windows: $env:ANTHROPIC_API_KEY="sk-ant-..."

# 3) 실행할 때 엔진을 명시
corpbrain scan ./docs --out ./wiki --engine cloud
```

`corpbrain doctor`가 동의·키 준비 상태를 함께 보여준다(둘 다 **경고성 표시**이며 doctor의 종료
코드에는 영향을 주지 않는다 — 클라우드를 안 쓰는 것이 정상 상태이기 때문이다).

동의를 되돌리려면 `corpbrain consent cloud --revoke`. 이후 `--engine cloud`는 다시 차단된다.

### 12.2 플래그

| 플래그 | 기본값 | 설명 |
|--------|--------|------|
| `--engine {local,cloud}` | `local` | `cloud`는 동의 + `ANTHROPIC_API_KEY`가 모두 있어야 한다 |
| `--cloud-model NAME` | `claude-haiku-4-5-20251001` | `--engine cloud`일 때 쓸 Anthropic 모델 |

### 12.3 무엇이 나가고 무엇이 안 나가나

- **나가는 것**: 요약 대상 문서 텍스트(`--max-chars`까지 절단, PII 마스킹 후)와 모델 이름.
- **나가지 않는 것**: API 키(환경변수에서만 읽고 디스크에 쓰지 않는다), 임베딩(**항상 로컬**
  `qwen3-embedding:4b` — 엔진과 무관하다), 파일 경로 목록, 텔레메트리.
- **Ollama가 아예 없어도 된다**: `--engine cloud`는 로컬 Ollama가 없으면 위키만 만들고 벡터
  인덱싱을 건너뛴다(종료 요약에 `인덱싱 생략`으로 알린다). 이 경우 `corpbrain search`로는
  해당 문서를 찾을 수 없으며, 나중에 Ollama를 설치하고 `--force`로 다시 스캔하면 채워진다.
  로컬 엔진(`--engine local`)은 요약 자체가 불가능하므로 종전대로 Ollama를 요구한다.
- **목적지**: `api.anthropic.com` 하나로 하드코딩되어 있고 플래그로 바꿀 수 없다. HTTPS가
  강제되며 리다이렉트는 따라가지 않는다.

### 12.4 PII 자동 마스킹

클라우드로 보내기 **직전에** 아래 7종을 `[REDACTED_...]`로 치환한다. 원본 위키에는 영향이 없다.

주민등록번호 · 전화번호 · 이메일 · 사업자등록번호 · 신용카드번호 · 계좌번호 · IP주소

형태(자릿수·구분자) 기반의 느슨한 매칭이라 **과탐(정상 숫자열이 가려짐)을 감수하고 누락을
줄이는 쪽**으로 맞춰져 있다. 다만 `2026-08-21` 같은 ISO 날짜는 개인정보가 아니고 계약서·회의록
거의 모든 줄에 등장해 요약을 뭉개므로 계좌번호 판정에서 제외한다(월·일 범위가 맞지 않는
`1234-56-78` 같은 값은 그대로 마스킹된다).

실행이 끝나면 어느 문서가 무엇을 가린 채 나갔는지 파일별로 보이고, 마지막에 합계가 나온다:

```
[PII 마스킹] 계약서.docx — 5건 (주민등록번호 4건, 사업자등록번호 1건)
[PII 마스킹] 연락처.txt — 2건 (전화번호 2건)
PII 마스킹 7건 (문서 2개) — 주민등록번호 4건, 전화번호 2건, 사업자등록번호 1건
```

### 12.5 알아둘 동작

- **엔진을 바꿔 재스캔하면 원문이 그대로여도 다시 생성된다.** 위키 front-matter의
  `engine: "local"|"cloud"` 값이 이번 실행과 다르면 mtime을 보지 않고 재생성한다. 같은 엔진으로
  재스캔할 때는 기존 mtime 규칙 그대로다.
- **GPU 게이트는 `--engine cloud`에서 자동으로 생략된다** — 클라우드 요약은 로컬 GPU를 쓰지
  않기 때문이다. `--max-total-tokens` 예산 게이트는 **비용 보호 목적이라 그대로 적용**된다.
- **개별 파일 실패는 전체를 멈추지 않는다.** 레이트리밋(429)은 `클라우드 레이트리밋(429)`,
  그 외 실패(5xx·타임아웃·잘못된 모델명 등)는 `클라우드 호출 실패`로 그 파일만 스킵되고 나머지는
  계속 처리된다(exit 0). **자동 재시도는 하지 않는다.**
- **동의 없음 / 키 없음 / 인증 실패(401)** 는 선행 조건 실패라 파일을 **하나도** 처리하지 않고
  exit 1로 끝난다. 인증은 파일 루프 전에 `GET /v1/models`로 한 번 확인한다(토큰 비용 없음).

## 13. 지식그래프 `[v0.6]`

`corpbrain scan` 한 번이 요약·벡터 인덱싱에 이어 **지식그래프까지** 만든다. 별도 명령이나
플래그가 필요 없다.

만들어지는 것은 두 가지다.

1. **위키마다 붙는 「관련 문서」 섹션** — 다른 문서로 가는 링크가 근거와 함께 달린다. 파일
   탐색기나 에디터에서 그대로 눌러 이동할 수 있다.
2. **`<out>/.corpbrain_graph.sqlite`** — `corpbrain graph`가 읽는 그래프 DB. 벡터 인덱스
   (`.corpbrain_index.sqlite`)와 **별도 파일**이라 한쪽만 지워 재구축할 수 있다.

### 13.1 무엇이 무엇과 이어지나

노드는 3종(문서·엔티티·태그), 엣지는 4종이다. **넷 다 추가 LLM 호출이 0**이고 결과가
결정적이다 — 같은 입력이면 항상 같은 그래프가 나온다.

| 엣지 | 의미 | 재료 |
|---|---|---|
| `TAGGED_WITH` | 문서 → 태그 | 요약이 뽑은 태그 |
| `CONTAINS_ENTITY` | 문서 → 엔티티(인물·부서·시스템·프로젝트명) | 요약이 뽑은 엔티티 |
| `SEMANTICALLY_SIMILAR` | 문서 ↔ 문서 (가중치 = 코사인 유사도) | v0.4 벡터 인덱스 |
| `REFERENCES` | 문서 → 문서 (본문이 다른 파일명을 언급) | 요약에 쓴 원문 텍스트 |

**태그와 엔티티는 층위가 다르다.** 태그는 "이 문서가 무슨 주제인가"(`인사`), 엔티티는 "문서
안에 누가·무엇이 등장하는가"(`인사팀`, `그리팅 ATS`)다. `그리팅 ATS를 언급한 문서 전부` 같은
질문은 태그로도 벡터 검색으로도 잘 안 잡히지만 엔티티 노드로는 정확히 잡힌다.

`인사팀`과 `인사 팀`은 한 노드로 합쳐진다(유니코드 NFC + 소문자화 + 공백 제거). 다만
`인사팀`과 `HR팀`처럼 표기가 아예 다른 동의어를 합치지는 않는다.

### 13.2 「관련 문서」 섹션

```markdown
<!-- corpbrain:related:start -->
## 관련 문서
- [신입사원 온보딩 가이드](온보딩.md.md) — 유사도 0.81 · 이 문서가 참조함 · 공유 태그 `인사`
- [입사자 체크리스트](../인사/체크리스트.md.md) — 공유 엔티티 `인사팀`
<!-- corpbrain:related:end -->
```

- 최대 `--related-top-k`개(기본 5)를 낸다.
- 순서는 **① 참조 관계가 있는 문서 → ② 유사도 높은 순 → ③ 공유 엔티티 많은 순 →
  ④ 공유 태그 많은 순 → ⑤ 경로 사전순**이다. 작성자가 직접 가리킨 문서가 늘 앞에 온다.
- 관련 문서가 하나도 없으면 섹션을 지우지 않고 `관련 문서 없음`이라고 쓴다.
- **마커(`<!-- corpbrain:related:... -->`)를 지우지 말자.** 도구는 이 사이만 교체한다.
  지우면 다음 실행에서 섹션이 하나 더 붙는다. 렌더된 화면에는 보이지 않는다.

### 13.3 플래그

| 플래그 | 기본값 | 하는 일 |
|---|---|---|
| `--similarity-threshold` | `0.5717` | 이 값 **이상**이면 유사도 엣지를 만든다(v0.7에서 재산정, §13.5) |
| `--related-top-k` | `5` | 「관련 문서」에 넣을 최대 항목 수 |

임계치를 바꿔 보려면 `scan`을 다시 돌리면 된다. 문서가 그대로면 **재요약은 일어나지 않고**
(전부 `최신 상태`로 스킵) 그래프 재빌드와 「관련 문서」 갱신만 돈다.

```bash
corpbrain scan ./docs --out ./wiki --similarity-threshold 0.85
```

### 13.4 알아둘 동작

- **v0.6은 파괴적 변경이 아니다.** v0.5까지 만든 위키가 있어도 재요약을 강제하지 않는다.
  그런 문서는 위키에서 제목·태그만 되살려 **엔티티 없는 부분 그래프**로 참여하고, 종료
  요약이 `--force`로 재스캔하면 엔티티까지 채워진다고 안내한다.
- **벡터 인덱스가 비어 있으면**(예: `--engine cloud` + Ollama 미구동) 유사도 엣지만 빠지고
  태그·엔티티·참조 3종으로 그래프를 만든다. 종료 코드는 0이다.
- **재실행 비용은 낮다.** 「관련 문서」가 실제로 달라진 위키만 다시 쓴다 — 나머지는
  타임스탬프가 그대로라 동기화 도구가 전체를 재전송하지 않는다.

### 13.5 유사도 엣지의 품질은 임베딩 모델에 달렸다 `[알려둘 것]`

`SEMANTICALLY_SIMILAR` 엣지만은 **어떤 임베딩 모델을 쓰느냐**에 따라 품질이 크게 갈린다.
나머지 3종(태그·엔티티·참조)은 임베딩과 무관하다.

> ⚠️ **v0.7 파괴적 변경(BREAKING)** — 기본 임베딩 모델이 `nomic-embed-text`에서
> **`qwen3-embedding:4b`**로, 기본 유사도 임계치가 `0.75`에서 **`0.5717`**로 바뀌었다
> (issue #42, 근거는 `docs/SMOKE.md` 실행 I). **v0.6 이하로 만든 인덱스가 있다면** 다음
> `scan`에서 모델 불일치로 막힌다 — 안내대로 인덱스를 지우고 `--force`로 다시 만들거나,
> 예전처럼 쓰려면 `--embed-model nomic-embed-text --similarity-threshold 0.75`를 명시한다.

**바뀐 이유**: 한국어 문서 6개(v0.6 실행 H)와 24개(v0.7 실행 I) 두 표본 모두에서
`nomic-embed-text`가 **무관한 문서 쌍에 관련 있는 쌍보다 높은 점수**를 주는 경우가 반복
확인됐다. `--similarity-threshold`를 올리거나 내려도 순서 자체가 틀려 고쳐지지 않는다.

| | `nomic-embed-text`(v0.6 이하 기본값) | `qwen3-embedding:4b`(v0.7 기본값) |
|---|---|---|
| 관련 있는 문서를 1순위로 꼽은 비율(24문서) | 6/22 (27%) | **18/22 (82%)** |
| 유사도 값 범위(24문서) | — | 0.20 ~ 0.70 |

**`qwen3-embedding:4b`도 완벽하지 않다.** 같은 클러스터 안에서 명시적으로 참조하지 않는
문서끼리 어휘가 겹쳐 더 높은 점수를 받는 경우가 있다(예: 예산 문서와 원가분석 문서). 그래서
기본 임계치(`0.5717`, 의도된 관련 쌍 코사인의 중앙값)는 **재현율보다 정밀도를 우선한다** —
관련 쌍의 절반 정도만 잡지만, 무관한 쌍이 섞여 들어가는 경우는 249쌍 중 2개로 억제된다.
자세한 실측은 `docs/SMOKE.md` 실행 I를 본다.

**선택 가능한 대안: `hf.co/mykor/KURE-v1-gguf`.** top-1 적중률만 보면 다른 후보(`bge-m3`,
`bona/bge-m3-korean`, `KURE-v1-gguf` 모두 77% 안팎)와 기본값 사이에 큰 차이가 없어 보이지만,
순위 기반 지표(MRR·Recall@3, `docs/SMOKE.md` 실행 I "보강" 절)로 다시 보면 `KURE-v1-gguf`가
2위다 — top-1을 놓친 문서도 대부분 2~3위 안에 정답을 뒀다(Recall@3 100%, 기본값과 동률).
`bge-m3`를 한국어 질의-문서 200만 쌍으로 파인튜닝한 모델(원본 `nlpai-lab/KURE-v1`, 고려대
NLP랩)이라 출처도 명확하다. 기본값을 바꾸는 대신 이 모델을 시도해 보려면:

```bash
ollama pull hf.co/mykor/KURE-v1-gguf
corpbrain scan ./docs --out ./wiki-kure --embed-model hf.co/mykor/KURE-v1-gguf --similarity-threshold 0.6795
```

(`bge-m3`를 직접 쓰려면 `--embed-model bge-m3 --similarity-threshold 0.46`.)

- **`--out` 을 새 폴더로 잡는다.** 인덱스는 자기를 만든 임베딩 모델을 기록하고 혼입을
  거부하므로, 모델을 바꾸면 인덱스를 새로 만들어야 한다.
- **임계치도 함께 바꾼다.** 모델마다 유사도 값의 분포가 달라, `0.5717`은 `bge-m3`의 전
  범위(최대 0.53)보다 높다 — 그대로 두면 유사도 엣지가 하나도 생기지 않는다. `graph --stats`
  로 엣지 수를 보며 맞춘다.
- 그래프 DB가 손상되거나 스키마 버전이 다르면 **자동 복구하지 않고 멈춘다**(exit 1).
  파일을 지우고 다시 `scan` 하면 된다.

## 14. `corpbrain graph` — 그래프 조회  `[v0.6]`

```bash
corpbrain graph --out ./wiki --stats
corpbrain graph --out ./wiki --neighbors 개발/설계.md.md
corpbrain graph --out ./wiki --central
```

**읽기만 하는 명령이다.** 조회 시점에 엣지를 다시 계산하지 않으므로 출력이 그래프 DB·위키와
항상 같은 값을 가리킨다. 네트워크도 쓰지 않는다 — 소켓을 하나도 열지 않는다.

| 뷰 | 하는 일 |
|---|---|
| `--stats` | 노드·엣지 종류별 개수 |
| `--neighbors <경로>` | 그 문서에 닿는 4종 엣지 |
| `--central` | 연결 차수 내림차순 문서 목록 |

세 뷰는 상호배타이며 하나는 반드시 줘야 한다.

```
$ corpbrain graph --out ./wiki --stats
노드 23개  문서 6 · 엔티티 11 · 태그 6
엣지 41개  TAGGED_WITH 20 · CONTAINS_ENTITY 15 · SEMANTICALLY_SIMILAR 5 · REFERENCES 1

$ corpbrain graph --out ./wiki --neighbors 인사/채용계획.docx.md
2026년도 신입 채용 계획  —  /work/docs/인사/채용계획.docx
  TAGGED_WITH                 인사
  CONTAINS_ENTITY             인사팀
  SEMANTICALLY_SIMILAR  0.81  신입사원 온보딩 가이드  (/work/docs/인사/온보딩.md)
  REFERENCES →                신입사원 온보딩 가이드  (/work/docs/인사/온보딩.md)
```

`REFERENCES`의 화살표는 방향이다 — `→`는 이 문서가 상대를 가리킨 것, `←`는 상대가 이 문서를
가리킨 것이다.

`--neighbors`는 경로를 세 형태로 받는다: **위키 상대경로**(`개발/설계.md.md`) ·
**원문 상대경로**(`개발/설계.md`) · **절대경로**. 출력에 찍힌 문서 경로를 그대로 다시 넣어도
된다.

**종료 코드**: 그래프 DB가 없거나 스키마가 맞지 않으면 `1`. `--neighbors`가 지목한 문서가
그래프에 없어도 `1`(오타를 조용히 넘기지 않는다). 그래프가 비어 있는 것은 정상이라 `0`이다.

## 15. 이번 범위 밖 (v0.7 이후)

구형 `.xls`/`.ppt`(97-2003 이진 포맷) 추출 — `.ppt`는 순수 파이썬 경로가 없어 외부 변환기
프로세스에 의존하게 되고, 그것은 100% 로컬 구동형 제품에 「특정 데스크톱 앱이 깔려 있어야만
동작하는 기능」을 처음 들이는 일이다. `.pptm`·`.xltx`·`.xltm`도 범위 밖이다 `[v0.8]`.
스캔 이미지 OCR·암호화 PDF 해제·오피스 파일 암호 해제, GPU 감지 확장(AMD·Apple Silicon), Ollama 자동
설치·모델 자동 pull, 중요도 기반 처리순서 변경·필터, 실측 rate 기반 예상시간 보정,
UI(pywebview·React), 검색 결과를 근거로 한 RAG 답변 생성(LLM 자연어 응답 합성 — v0.4는
인덱싱·검색까지만), 문서 청크 분할, 벡터 저장소 원격·분산·다중 사용자 동시접근.
그래프 쪽으로는 엔티티 사이의 관계(`RELATES_TO`), LLM 기반 엔티티 동의어 병합, 엔티티→태그
엣지, 매개 중심성 등 고급 지표, 그래프 DB 스키마 마이그레이션이 범위 밖이다.
검색 쪽으로는 BM25·키워드 결합(업계에서 «하이브리드 검색»이라 부르는 그것 — v0.7은 벡터+그래프
결합이다), 확산 점수의 사전 계산·저장, 문서 2홉 이상 확산, 정적 중심성 가산, 쿼리 문자열 ↔
태그·엔티티 라벨 직접 매칭이 범위 밖이다. `[v0.7]`
클라우드 쪽으로는 복수 provider·임의 엔드포인트, 임베딩의 클라우드 경로, ML 기반 PII 탐지,
자동 재시도·백오프, 파일별 자동 라우팅·폴백, API 키의 OS 키링 저장이 모두 범위 밖이다.
