## :white_check_mark: Task Breakdown (실행 계획)
- [ ] `corpbrain/core/pipeline.py`에 코어 진입 함수 `run_scan(config) -> ScanResult`를 구현한다. CLI 없이 함수 호출만으로 end-to-end 실행 가능해야 한다(§4.5).
- [ ] 단계 조립: 스캐너(FR-004/005) → 텍스트 추출(FR-006/007/008) → 요약·JSON 파싱(FR-010) → 마크다운 렌더(FR-011) → 출력 배치(FR-012) → 재실행 정책(FR-013)을 순차 호출한다.
- [ ] 각 파일 처리를 개별 try 단위로 감싸 실패를 격리한다. 실패·스킵 사유별로 스킵 항목을 수집한다:
  - [ ] 미지원 확장자 / 빈 문서 / 텍스트 추출 실패 / 권한 거부 / 경로 길이 >260자 → 스킵+로그(§5)
  - [ ] LLM JSON 파싱 실패 → 해당 파일만 실패로 스킵+로그, 나머지 계속(§5, §4.3)
- [ ] 스캔 대상이 상한(`--max`, 기본 50)을 초과하면 처리를 중단하고 알림 신호를 결과에 담는다(§5). (선행 조건 실패로 취급 — 종료코드 매핑은 FR-016)
- [ ] `ScanResult`에 처리 건수, 스킵 항목(경로+사유), 출력 경로, 상한 초과·선행조건 실패 플래그를 담아 어댑터(FR-016)가 요약·종료코드로 변환할 수 있게 한다.
- [ ] 모든 외부(Ollama) 호출은 단일 관문 모듈(FR-003)만 경유한다. 파이프라인은 네트워크 라이브러리를 직접 호출하지 않는다(§4.5).

## :test_tube: Acceptance Criteria (BDD/GWT)
Scenario 1: 혼합 폴더 부분 성공 처리
- Given: 지원 `.txt/.md/.docx`, 미지원 확장자, 빈 파일, 하위폴더가 섞인 폴더가 주어진다.
- When: `run_scan(config)`를 코어 API로 직접 호출한다.
- Then: 지원 파일마다 위키 `.md`가 생성되고, 미지원·빈 파일은 산출물 없이 `ScanResult`의 스킵 리포트에 사유와 함께 나타난다. 처리 건수와 스킵 건수가 모두 보고된다.

Scenario 2: 개별 파일 실패가 전체를 실패시키지 않음
- Given: 한 파일의 LLM 응답이 유효 JSON이 아니거나 텍스트 추출에 실패한다.
- When: 파이프라인이 해당 파일을 처리한다.
- Then: 그 파일만 실패로 스킵+로그되고 나머지 파일 처리는 계속되며, 개별 실패가 전체 실패로 위장되지 않는다(부분 성공 보고).

## :gear: Technical & Non-Functional Constraints
- 보안: 모든 외부 네트워크 호출은 단일 관문(FR-003)을 통과하며 `--ollama-url`(localhost) 외 연결이 발생하지 않는다(§4.5, §3-6).
- 성능/안정성: 파일을 통째로 메모리에 올리지 않고 앞부분 `--max-chars`까지만 요약 입력으로 사용한다(§4.2). LLM 레이턴시 SLA는 없다. 개별 파일 부분 실패는 성공으로 위장하지 않는다(§5).
