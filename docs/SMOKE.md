# 수동 스모크 절차 (릴리스 전 사람이 1회 실행)

릴리즈 전 최종 수동 확인 단계다(자동 CI 게이트 아님). mock이 아닌 실제 로컬 Ollama로
파이프라인을 1회 돌려 산출물 품질과 계약(한국어 출력·템플릿·스킵/종료 코드)을 확인한다.

## 사전 조건

- 로컬 Ollama 데몬 기동 (`ollama serve` 또는 앱 실행).
- 모델 준비. 스펙 기본값은 `qwen2.5:7b-instruct`. 없으면 `ollama pull qwen2.5:7b-instruct`,
또는 이미 받아 둔 다른 모델을 `--model`로 지정한다(설치·pull은 CorpBrain이 하지 않는다).
- 개발 환경: `uv venv --python 3.12 && uv sync && uv pip install -e .`

## 스모크용 실샘플

소형 실샘플(정상 `.txt`/`.md`/`.docx` 소수)을 임의 폴더에 둔다. 예시로 이 저장소는
`tests/fixtures/sample_corpus/`(정상 txt·md·docx + 하위폴더·빈 파일·미지원·초과 파일)를
갖고 있으나, 순수 정상 문서만으로 스모크하려면 별도 폴더에 `.txt`/`.md` 2~3개를 만든다.

## 실행 — Scenario 1 (정상)

```
uv run corpbrain scan <sample> --out <tmp_out> --model qwen2.5:7b-instruct
```

기대(스펙 §3-1·2, §4.1, §4.3, §4.4):

- [x] 지원 파일마다 `<원본이름.확장자>.md`가 입력 하위구조를 미러링하여 생성된다.
- [x] 각 `.md`에 front-matter 4키(`source_path`/`generated_at`/`model`/`source_bytes`)가 있다.
- [x] 6섹션(`# 제목`/`## 한 줄 요약`/`## 핵심 포인트`/`## 요약`/`## 태그·키워드`/`## 원문`)이 있다.
- [x] 요약·핵심 포인트·태그가 **한국어**로 채워진다.
- [x] 종료 요약에 `처리 N건 / 스킵 M건(+사유)` 과 `출력 경로`가 stderr로 표시된다.
- [x] 종료 코드 0 (부분 실패가 있어도 0).

## 실행 — Scenario 2 (Ollama 미기동)

데몬을 끄거나 닿지 않는 포트를 지정해 선행 조건 실패를 확인한다.

```
uv run corpbrain scan <sample> --out <tmp_out> --ollama-url http://127.0.0.1:1
```

기대(스펙 §4.3, §5):

- [x] 설치를 시도하지 않고 비-0 종료.
- [x] stderr에 미탐지 사유가 남는다.

- 모델: `qwen2.5:7b` (로컬 보유. 스펙 기본값 `qwen2.5:7b-instruct`는 미보유라 `--model`로 지정).
- 샘플: `sales.txt`(영업 실적 문단), `roadmap.md`(로드맵 불릿) 2건.
- Scenario 1: 처리 2건 / 스킵 0건, 종료 코드 0. 소요 약 24초(2건 합산, M-계열 로컬).
  - 산출물 `sales.txt.md`: front-matter 4키·6섹션 모두 존재, 제목/요약/핵심포인트/태그가

## 실행 기록 (2026-08-12, run-status + CPU 우회)

- 환경 특이사항: 로컬 Ollama가 GPU에서 `CUDA error: the provided PTX was compiled with an unsupported toolchain`(HTTP 500)으로 모델 실행에 실패 — 입력 크기와 무관하게 전건 실패.
원인은 NVIDIA 드라이버 ↔ Ollama CUDA 런타임 버전 불일치(환경 문제, CorpBrain 무관).
CorpBrain은 스펙 §5대로 각 파일을 `summary_failed`로 스킵+로그하고 크래시 없이 종료 코드 0.
- 우회: Ollama 서버를 `CUDA_VISIBLE_DEVICES=-1`(+`OLLAMA_LLM_LIBRARY=cpu`)로 재시작해 CPU
추론으로 전환. **주의: 이 env는 해당 서버 프로세스 한정 — 트레이 앱 재시작·재부팅 시 GPU
모드로 복귀해 500이 재발한다. 근본 해결은 NVIDIA 드라이버 업데이트.**
- 모델: `qwen2.5:7b-instruct`(CPU). 샘플: `sales.txt`, `roadmap.md` 2건.
- 결과: 처리 2건 / 스킵 0건, 종료 코드 0, stdout 0바이트. 요약당 CPU 소요 약 52~62초.
  - 산출물 `roadmap.md.md`: front-matter 4키·6섹션 모두 존재, 제목/요약/핵심포인트/태그가
  자연스러운 한국어로 채워짐, `## 원문` `file://` 링크 생성. (A/B/C 항목 모두 충족)
  - 라이브 라인: index/total·stage·`loading` 전환·경과/ETA/rate·net 지연 모두 정상 표시.
- 관문 개선(별건): `gateway.py`가 HTTP 오류 본문을 버리던 문제를 고쳐, 이후 500 시 서버
메시지(`{"error": ...}`)가 종료 로그에 함께 표시된다(테스트 3건 추가).
- 이상 여부: 없음(환경 CUDA 이슈 제외). run-status 계약·CPU 경로 모두 충족.

## v0.5 클라우드 옵트인 스모크 (실제 Anthropic API 1회)

스펙: `static/docs/specs/features/corpbrain-v0.5-cloud-opt-in.md` §3 검증 방식 — *"마무리로
실제 Anthropic API 1회 수동 스모크를 실행한다"*. v0.5 구현 루프는 목표 문서
(`docs/goals/corpbrain-v0.5-cloud-opt-in-loop.md` §1)가 **실제 API 호출(비-mock)을 금지**했기
때문에 이 절차를 수행하지 못했다. 따라서 이 절은 루프가 아니라 사람이 한 번 돌려야 한다.

mock 통합테스트가 이미 계약(스킵 사유 매핑·재생성 판정·exit 코드)을 덮고 있으므로, 여기서는
**mock으로는 증명할 수 없는 것**만 본다 — 실제 인증이 통과하는지, 실제 응답이 템플릿에 들어오는지,
그리고 실제로 전선에 나가는 payload가 마스킹되어 있는지.

### 사전 조건

- 유효한 Anthropic API 키. `export ANTHROPIC_API_KEY=sk-ant-...` — 디스크에 저장하지 않는다.
- 로컬 Ollama 데몬 + `nomic-embed-text` — 실행 D의 인덱싱 단계에 필요하다. F는
  프리플라이트에서 끊기고, G(doctor)는 이 모델의 유무를 보고만 한다.
- 비용: 기본 모델 `claude-haiku-4-5-20251001`로 소형 문서 2~3건이면 1센트 미만이다.
- **주의**: `consent cloud --grant`는 테스트 격리 경로가 아니라 실제 `~/.corpbrain/config.json`에
  기록된다. 스모크가 끝나면 `consent cloud --revoke`로 되돌린다.
- **주의**: `--out`은 **리포지토리 밖 임시 폴더**로 잡는다. `tests/fixtures/` 안에 산출물을
  남기면 다음 `pytest`가 그 `.md`를 입력 문서로 다시 잡아 통합테스트가 깨진다(2026-08-22 실측).

### 스모크용 실샘플

`.txt`/`.md` 2~3개를 임의 폴더에 두되, **그중 한 건에는 PII 7종을 한글 조사가 바로 붙은 형태로
심는다** — 실행 E가 이걸 본다. 예:

```
담당자 연락처는 010-1234-5678로 주시고, 메일은 hong@corp.co.kr.
주민등록번호 900101-1234567입니다. 사업자등록번호 123-45-67890,
카드 4111-1111-1111-1111, 계좌 110-123-456789, 서버는 192.168.0.1에서 돕니다.
```

```

uv run corpbrain consent cloud --grant
uv run corpbrain scan <sample> --out <tmp> --engine cloud
```

- [x] 첫 실행: 산출물 0개, **exit 1**, stderr 안내에 `corpbrain consent cloud --grant`가 나온다.
- [x] `~/.corpbrain/config.json`에 `cloud_consent.anthropic.granted: true`가 기록된다.
- [x] 둘째 실행: 위키가 생성되고 **exit 0**.
- [x] 생성된 `.md`의 front-matter에 `engine: "cloud"`와 `model: "claude-haiku-4-5-20251001"`.
- [x] 요약·핵심 포인트·태그가 **한국어**로 채워진다(로컬 엔진과 품질 계약이 같다).

### 실행 E — 실제 전선의 PII 마스킹 (DoD 6·16)

실행 D의 종료 요약을 그대로 본다. 전선 payload 자체는 통합테스트가 캡처해 검증하므로, 여기서는
**실제 API 경로에서도 집계가 도는지**와 리포트 문구를 확인한다.

- [x] 종료 요약에 `[PII 마스킹] <파일경로> — N건`이 **파일별로** 나온다.
- [x] 합계 줄 `PII 마스킹 N건 (문서 M개) — ...`의 유형명이 **한국어**다
      (`주민등록번호`·`전화번호`·… — `RRN`·`PHONE` 같은 내부 토큰이 노출되면 실패).
- [x] 한글 조사가 붙은 `010-1234-5678로`·`900101-1234567입니다`·`192.168.0.1에서`가 모두 집계에
      잡힌다(7종 전부 카운트되는지 대조).
- [x] 생성된 위키 본문에 원본 PII 문자열이 되살아나지 않는다(모델은 마스킹본만 봤으므로).

#### 이 실행에서 얻은 절차상 교훈
`--out`을 스캔 대상인 `tests/fixtures/sample_corpus/` **안**(`.../sample_corpus/wiki/`)으로
잡아 실행했다. 그 실행 자체는 §4.2 자동 제외 덕분에 정상이었지만, 남은 `wiki/*.md`가 다음
`pytest`에서 픽스처의 **입력 문서로 다시 잡혀** `test_pipeline.py` 3건이 깨졌다
(`normal.txt.md.md` 같은 이중 산출물이 기대 트리와 어긋났다). 산출물은 리포지토리 밖으로 옮겨 원복했다.

**스모크는 반드시 리포지토리 밖 임시 폴더를 `--out`으로 쓴다.** 픽스처 폴더는 테스트가
파일 목록을 그대로 기대하므로 어떤 산출물도 남기면 안 된다(`.gitignore`로는 못 막는다 —
커밋이 아니라 디스크에 존재하는 것만으로 테스트가 깨진다).

#### 실행 E(PII 마스킹) — 별도 장비에서 확인
이 기록의 샘플로 쓴 픽스처 코퍼스에는 PII가 없어, 실행 E는 **다른 장비에서 PII를 심은 샘플로
따로 돌려 확인했다. 이상 없음.** 따라서 D~G 전 항목이 실키로 검증됐다.

기록을 읽는 사람이 헷갈리지 않도록: 위 산출물 목록은 PII 없는 코퍼스의 것이므로 마스킹 집계가
보이지 않는 것이 정상이다.

**`--out`은 반드시 리포지토리 밖 임시 폴더**를 쓴다(위 v0.5 실행 기록의 교훈).

### 실행 H — 실제 모델로 만든 그래프 (DoD 1·2·3)

코퍼스는 **`docs/smoke/corpus/`** 에 있다(문서 6개, 하위 폴더 3개). 실행 절차와 코퍼스 구성
설명은 `docs/smoke/README.md` 에 있다.

```
docs/smoke/corpus/인사/채용계획.md   — 인사팀·그리팅 ATS 언급, 본문에 "온보딩.md" 참조

docs/smoke/corpus/개발/README.md     — 본문에 자기 파일명 "README.md" 언급
```

```bash
corpbrain scan docs/smoke/corpus --out "$OUT" --force-gates
```

입력 코퍼스를 리포지토리에 두는 것은 안전하다 — 테스트는 `tests/fixtures/` 와 `tmp_path`
만 쓰고 `docs/` 를 읽지 않는다. **`--out` 만 리포지토리 밖으로 잡으면 된다**(2026-08-22
사고는 산출물이 픽스처 폴더에 남아 생긴 것이다).

체크리스트:

- [ ] **실제 모델이 `entities`를 채웠는가** — `graph --stats`의 `엔티티` 수가 **0이 아니다**.
      0이면 로컬 모델이 이 필드를 늘 비워 보낸다는 뜻이고, 프롬프트를 손봐야 한다.
      (`entities`는 선택 필드라 비어도 위키는 정상 생성되고 테스트도 전부 통과한다 —

- [ ] **뽑힌 엔티티가 쓸 만한가** — `--neighbors` 출력의 `CONTAINS_ENTITY` 줄이 `인사팀`

- [ ] **기본 임계치 `0.75`가 합리적인가** — `SEMANTICALLY_SIMILAR` 엣지 수를 본다.

      (재요약은 일어나지 않는다 — 전부 `최신 상태`로 스킵되고 그래프만 다시 만들어진다.)
- [ ] **「관련 문서」가 사람이 보기에 납득되는가** — 위키를 열어 목록 순서를 본다. 참조한

- [ ] **링크가 실제로 열리는가** — 하위 폴더 문서(`개발/아키텍처.md.md`)의 「관련 문서」
      링크를 에디터에서 눌러 대상 위키로 이동하는지 확인한다(`../인사/...` 형태).
- [ ] **고립 문서**(`기타/메모.md.md`)에 `관련 문서 없음`이 찍혔는가.
- [ ] **자기참조가 없는가** — `개발/README.md.md`의 「관련 문서」에 자기 자신이 없다.
- [ ] `graph --stats` / `--central` / `--neighbors` 가 모두 exit 0이고, 없는 문서를 지목하면
      exit 1이다.

#### 발견 1 (중대) — 절대 코사인 임계치가 이 모델·이 입력에서 작동하지 않는다

생성된 위키의 요약 텍스트를 파이프라인과 **같은 입력으로** 임베딩해 전 쌍 유사도를 측정했다
(실행 1의 7문서 기준, 15쌍).

```
  0.8696  기타/메모      ~ 인사/온보딩       ⚠ 무관한 쌍이 1위
  0.8478  인사/온보딩     ~ 실행방법
  0.8369  인사/채용계획    ~ 실행방법
  0.8215  기타/메모      ~ 실행방법          ⚠ 무관

  0.7455  개발/벡터설계    ~ 인사/온보딩

```

**임계치를 어떻게 잡아도 신호와 잡음이 갈라지지 않는다.**

- 의도한 두 관련 쌍이 각각 5위(0.8185)와 **13위**(0.6606)다.
- 가장 무관한 쌍(탕비실 비품 ~ 입사 온보딩)이 **1위**(0.8696)다.
- `0.75`면 6쌍 통과 — 개발 쌍은 탈락하고 무관한 3쌍이 통과한다.
- `0.85`로 올리면 1쌍만 남는데 **그 1쌍이 무관한 쌍**이다.

**기본값을 올리는 것으로는 해결되지 않는다.** 원인을 가리기 위해 두 가지를 더 측정했다.

##### 원인 규명 (1) — 요약을 입력으로 쓴 탓이 아니다

처음에는 임베딩 입력이 원문이 아니라 요약 텍스트라(v0.4 §4.3) 장르 유사도가 주제 유사도를
덮는다고 봤다. **원문을 그대로 임베딩해 보니 더 나빴다.**

| | 요약 임베딩(현행) | 원문 임베딩 |
|---|---|---|
| 유사도 범위 | 0.6436 ~ 0.8696 (폭 0.226) | 0.7529 ~ 0.8919 (폭 **0.139**) |
| `0.75` 통과 | 15쌍 중 6 | **15쌍 전부** |
| 문서별 top-1 적중 | 1/4 | 1/4 |

절대 임계치 대신 **문서당 상대 순위(top-N)**로 바꿔도 적중률이 같았고, `인사/온보딩`이 거의
모든 문서의 1순위로 나오는 **허브 현상**이 보였다. 임베딩 공간에서 특정 벡터가 모든 것과
가까워지는 전형적 증상이다.

##### 원인 규명 (2) — 임베딩 모델이 원인이다 ★

같은 코퍼스·같은 요약을 `bge-m3`로 임베딩하니 **순서가 정확해졌다.**

```
   1. 0.5307  인사/온보딩   ~ 인사/채용계획    ←── 의도한 관련 쌍
   2. 0.4769  개발/벡터설계  ~ 개발/아키텍처    ←── 의도한 관련 쌍
   3. 0.4482  기타/메모    ~ 인사/온보딩      ⚠ 무관
   …
  10. 0.3046  개발/벡터설계  ~ 기타/메모        ⚠ 무관

범위 0.3046 ~ 0.5307 · 의도한 관련 쌍이 1위·2위
```

| | `nomic-embed-text`(기본) | `bge-m3` |
|---|---|---|
| 의도한 관련 쌍 순위 | 5위 · **13위** / 15쌍 | **1위 · 2위** / 10쌍 |
| 문서별 top-1 적중 | **1/4** | **4/4** |
| 신호·잡음 분리 | 없음 (무관한 쌍이 1위) | 있음 (2위 0.4769 · 3위 0.4482) |

**`nomic-embed-text`는 이 한국어 코퍼스에서 순서 자체를 틀리므로 임계치를 어떻게 잡아도
고칠 수 없고, `bge-m3`는 순서가 맞아 임계치만 그 모델의 범위에 맞추면 된다.**

즉 기본값 `0.75`의 문제는 값이 아니라 **값이 모델에 종속된다**는 데 있다. `0.75`는
`gui_preview` 목업의 "유사도 75% 이상"에서 온 숫자이고(스펙 §4.7) 실측 근거가 없었다.
`bge-m3` 기준으로는 `0.46` 근처가 의도한 두 쌍만 정확히 통과시킨다(문서 5개 표본이므로
일반화에는 주의가 필요하다).

##### 실험 B 실행 결과 (`--embed-model bge-m3`)

```
그래프: 노드 38개(문서 5 · 엔티티 15 · 태그 18) / 엣지 42개
  TAGGED_WITH 18 · CONTAINS_ENTITY 21 · SEMANTICALLY_SIMILAR 0 · REFERENCES 3
```

기본 임계치 `0.75`가 `bge-m3`의 전 범위(최대 0.5307)보다 높아 **유사도 엣지가 0개**가 됐다.
그 결과 「관련 문서」에서 잡음이 사라졌다 — `기타/메모.md` 가 진짜 고립 문서가 되고
`인사/채용계획.md` 의 이웃이 참조 관계 하나로 정리됐다. 다만 이는 **분리가 잘 돼서가 아니라
전부 잘려서**이므로, 체크리스트의 «고립 문서» 항목이 이 실행에서 통과한 것은 우연이다.

`corpbrain graph` 는 `--embed-model` 을 받지 않는다(순수 조회 명령, §4.7). 로그의
`unrecognized arguments: --embed-model` 은 정상 동작이다.

#### 발견 2 (중대) — 특정 문서가 로컬 모델에서 결정적으로 요약 실패한다

`개발/README.md` 가 두 실행 모두 같은 오류로 스킵됐다.

```
[스킵] .../개발/README.md — LLM JSON 파싱 실패 (필수 배열 필드가 문자열 배열이 아닙니다: tags)
```

`temperature=0` 인 실제 설정으로 **6회 재시도 6회 모두 실패**했다. 원응답을 보면 모델이
`summary` 중간부터 중국어 메타 설명으로 새고 JSON이 잘려 `tags` · `entities` 키가 아예
없어진다.

```json
"summary": "이 문서는 개발 폴더 내의 주요 문서들에 대한 안내와 함께 문서를 추가하거나
            수정할 때应注意保持答案的准确性…请确认是否符合要求。"
```

이 문서의 내용이 **"문서를 어떻게 쓸 것인가"라는 작성 규칙**이라, 7b 모델이 그 규칙을
자기 과제 지시로 혼동한 것으로 보인다. 프롬프트에 "모든 값은 반드시 한국어로 작성합니다"가
있는데도 언어가 샜다.

파이프라인 자체는 정상이다 — 해당 파일만 스킵하고 나머지를 계속 처리했으며 종료 코드는
0이었다(v0.1 §5 부분 성공 원칙). 다만 **연쇄 손실**이 있다: `아키텍처.md → README.md`
참조 엣지가 대상 문서 부재로 함께 사라졌다.

#### 발견 3 — 태그와 엔티티의 층위가 섞인다

프롬프트가 "`인사`는 tags, `인사팀`은 entities"로 구분을 명시했는데도 모델이 부서명을
양쪽에 넣었다. 문서 5개에 **태그 18개**는 과다하다.

```
채용계획.md   태그: 신입사원 · 인사팀 · 채용        ← `인사팀`이 태그이자 엔티티
메모.md      태그: 비품 · 총무팀 · 탕비실          ← `총무팀`도 마찬가지
```

`tag:인사팀` 과 `entity:인사팀` 이 별도 노드로 공존한다. 그래프가 틀린 것은 아니지만
노드 수가 부풀고 「관련 문서」의 «공유 태그»와 «공유 엔티티»가 같은 말을 두 번 하게 된다.

##### 새로 드러난 것 ★ — `entities` 를 선택 필드로 둔 대가

> **v0.6.1에서 스키마를 고쳤고, 효과가 실측으로 확인됐다** [2026-08-27 · issue #40].
> `SUMMARY_TOOL_SCHEMA` 의 `required` 에 `entities` 를 넣은 뒤 24문서 코퍼스를
> `--engine cloud` 로 1회 스캔한 결과 **24문서 전부가 비어 있지 않은 `entities` 를 받았다**
> (종전 6문서 중 5개가 빈 배열). 상세는 아래 「실험 A 후속」에 있다.
>
> `required` 는 «키가 존재할 것» 이지 «비어 있지 않을 것» 이 아니므로 모델이
> `"entities": []` 를 보내도 스키마는 충족된다 — 그래서 실측이 필요했고, 실제로는 채웠다.
>
> 아래는 그렇게 결정하게 된 종전 실측 기록이다.

**문서 6개 중 5개가 `entities: []` 로 왔다.**

```
README.md    tags=5  entities=[]
벡터설계.md    tags=6  entities=[]
아키텍처.md    tags=6  entities=[]
메모.md      tags=6  entities=[]
```

대신 태그가 **34개**로 폭증했고, 그 안에 엔티티가 되어야 할 고유명사가 들어가 있다 —
`SQLite` · `CorpBrain` · `nomic-embed-text` · `커피머신` · `코어-어댑터패턴`.

원인은 스펙 §4.2의 결정이다. `entities` 는 `properties` 에는 있지만 **`required` 에는
없다**(v0.6 grill V2). 프롬프트로만 요청받는 로컬 모델은 나열된 필드를 고르게 채우지만,
`tool_use` 로 스키마를 강제받는 클라우드 모델은 **필수 필드를 확실히 채우고 선택 필드는
건너뛴다.**

파급이 「관련 문서」까지 간다. 태그가 34개나 되면서 문서 간에 **거의 겹치지 않아**
(`TAGGED_WITH` 36개 / 고유 태그 34개), 「관련 문서」에 «공유 태그» 근거가 한 줄도 나오지
않았다. 엔티티도 비어 있으니 **근거가 사실상 유사도 하나로 줄었다.**

##### 그런데 태그 폭증은 고쳐지지 않았다 ★

`entities` 가 채워지면 태그로 새던 고유명사가 줄어들 것이라는 예상은 **빗나갔다.**

| | v0.6.0 | v0.6.1+ |
|---|---|---|
| 문서당 평균 태그 | ≈6.0 | 5.3 |
| **2개 이상 문서를 잇는 태그 비율** | 거의 0 | **10%** (114개 중 11개) |
| 2개 이상 문서를 잇는 엔티티 비율 | — | **30%** (83개 중 25개) |

문서당 태그 수는 거의 그대로이고, 태그는 여전히 **10%만** 문서를 잇는다. 「관련 문서」에
«공유 태그» 근거가 28줄 나온 것은 태그가 좋아져서가 아니라 **문서 수가 4배(6 → 24)로 늘어
우연한 겹침이 생겼기 때문**으로 보는 편이 안전하다.

- **연결을 만드는 것은 엔티티다.** 2개 이상 문서를 잇는 비율이 엔티티 30% 대 태그 10%로
  3배이고, 상위 연결 노드도 엔티티 쪽이 압도적이다 — `연구개발팀`(8문서) · `재무팀`(6) ·
  `마케팅팀`(4) · `인사팀`(4) 대 태그 `아키텍처`(4) · `2026년`(3).
- **v0.7 issue #49 와 정면으로 얽힌다.** #49 는 검색에서 `CONTAINS_ENTITY` 확산이 **손해**라고
  실측했다 — 부서명 엔티티가 선택성이 없어 `인사팀` 하나로 문서 10개가 동점으로 끌려 들어온다.
  같은 성질이 여기서는 **이득**이다(「관련 문서」는 top-k 경쟁이 아니라 근거 표시다).
  즉 「부서명 엔티티」는 용도에 따라 값이 갈리며, #49 를 판단할 때 이 실측을 함께 봐야 한다.
- 태그 품질 자체(고유명사가 태그로 새는 것)는 이번 전환으로 **해결되지 않았다.** 별도 판단

#### 미결 사항 — `v0.6.0` 태그 전에 판단이 필요하다

1. **유사도 엣지를 어떻게 할 것인가** (발견 1). 원인이 임베딩 모델로 좁혀졌다.
   - 기본 임베딩 모델을 `bge-m3` 로 바꾼다 — 품질은 해결되나 기존 인덱스가 무효화되는
     **BREAKING**이고(모델 혼입 방지) 다운로드가 0.3GB → 1.2GB로 는다. v0.6은 BREAKING이
     아니라고 약속했다(USAGE §1).
   - `nomic-embed-text` 를 유지하고 임계치만 조정한다 — **효과 없다.** 순서가 틀렸다.
   - 절대 임계치를 문서당 상대 순위로 바꾼다 — 스케일 프리라 모델별 튜닝이 필요 없지만,
     `nomic` 에서는 여전히 1/4다(모델이 나쁘면 순위도 나쁘다).
   - 현행 유지 + 문서화 — 유사도 항목의 품질이 임베딩 모델에 달렸음을 USAGE에 명시하고
     `--embed-model bge-m3` 를 권장한다. 기본 경험은 그대로 약한 채 나간다.
2. **로컬 7b 모델의 요약 실패율** (발견 2). 프롬프트를 손볼 것인지, 실패를 그대로 둘 것인지.
3. **태그/엔티티 층위 혼동과 환각** (발견 3·4). 프롬프트 강화 대상인지, 모델 한계로 수용할지.
4. **`entities` 를 선택 필드로 둔 결정(§4.2)을 유지할 것인가** (실험 A). 클라우드에서 문서
   6개 중 5개가 빈 배열로 왔다. `required` 에 넣으면 `tool_use` 가 강제하므로 클라우드에서는
   반드시 채워지고, 그러면 §4.2가 우려한 "엔진에 따라 생성되는 위키 개수가 달라진다"는
   일도 일어나지 않는다(스키마 강제라 누락 자체가 불가능하다). 로컬은 종전대로 선택으로
   두면 문서 손실 위험도 그대로 없다. 다만 그 경우 §4.2의 "엔진별로 필수 여부를 달리하지
   않는다"는 결정을 뒤집게 되므로 별도 판단이 필요하다.

셋 다 CorpBrain 코드의 결함이 아니라 **실제 모델 품질** 문제이며, 스텁을 쓰는 자동 테스트가
원리적으로 잡을 수 없는 영역이다 — 실행 H를 만든 목적이 정확히 이것이었다.

#### 임계치 산출 — 깨끗한 간극이 없다 (§4.1 "전원 실패" 케이스)

채택 모델의 관련 쌍(27개)·무관 쌍(249개) 코사인 분포:

```
관련 쌍  범위 0.4276 ~ 0.6981
무관 쌍  범위 0.1987 ~ 0.7008

관련 쌍 최저(0.4276) < 무관 쌍 최고(0.7008) — 간극 없음
```

관련 쌍 최저보다 높은 무관 쌍이 28개나 돼(249개 중), §4.2가 정한 "관련 최저·무관 최고의
중간값" 방식은 쓸 수 없었다. 스펙 §4.2가 예비한 대체 기준으로 **관련 쌍 코사인 값의
중앙값**을 썼다.

```
DEFAULT_SIMILARITY_THRESHOLD = 0.5717153219583704   (관련 쌍 27개의 중앙값)

이 임계치(>=)에서:
  관련 쌍 재현율(recall)     14/27 (51.9%)
  무관 쌍 오탐(false positive)  2/249 (0.8%)
```

정밀도를 재현율보다 우선했다 — 무관한 문서가 「관련 문서」에 섞여 들어가는 실행 H의 실패
패턴(허브 현상)을 피하는 것이 이번 재판단의 목적이었으므로, 관련 쌍을 절반 정도만 잡더라도
오탐을 249쌍 중 2개로 억제하는 쪽을 택했다.

#### 발견 — 클러스터 내부 근접성이 명시적 참조보다 강하게 작용한다

미스(top-1이 정답 밖) 4건 전부 **같은 클러스터 안의 다른 문서**가 1위를 차지했다.

```
인사/채용계획.md   1위이웃=인사/평가제도.md (0.6368)   정답=온보딩·조직개편
인사/평가제도.md   1위이웃=인사/채용계획.md (0.6368)   정답=온보딩
재무/예산계획.md   1위이웃=재무/원가분석.md (0.7008)   정답=지출보고·투자계획
재무/원가분석.md   1위이웃=재무/예산계획.md (0.7008)   정답=지출보고·투자계획
```

`재무/예산계획.md`와 `재무/원가분석.md`는 본문에서 서로를 언급하지 않도록 의도적으로
설계했지만(코퍼스 설계 노트, §3.2), 둘 다 "예산·집행률·숫자" 어휘를 많이 공유해 임베딩
공간에서는 명시적으로 참조하는 문서 쌍보다 오히려 더 가깝게 나왔다. **문서 간 명시적 참조
관계와 임베딩 유사도는 서로 다른 신호다** — `REFERENCES`가 작성자의 의도를 담는 것과 달리
`SEMANTICALLY_SIMILAR`는 어휘·주제 근접성을 담으므로, 같은 클러스터 안에서는 둘이 갈릴 수
있다는 것을 이번 24문서 표본에서 처음 확인했다(6문서 표본은 클러스터당 문서가 적어 이
현상을 드러내지 못했다).

이는 그래프 설계(v0.6 스펙 §4.1)가 애초에 4종 엣지를 분리해 둔 이유와도 맞는다 — 하나의
"관련도" 점수로 뭉치지 않고 근거를 따로 보여주는 쪽이 이런 어긋남에 더 강건하다.

#### 보강 — 순위 기반 지표(MRR·Recall@3)로 재검증

top-1 적중률은 `bge-m3`·`bona/bge-m3-korean`·`hf.co/mykor/KURE-v1-gguf` 세 모델을 전부
17/22로 묶었다. 이진 지표(1위가 맞았는가/틀렸는가) 하나로는 세 모델의 차이가 가려질 수
있어, 기존 실측 데이터(전 쌍 코사인, 재측정 없음)로 순위 기반 지표를 추가로 계산했다.

- **MRR(Mean Reciprocal Rank)**: 문서마다 "의도된 관련 문서가 코사인 순위 몇 위에 처음
  나오는가"의 역수(1위=1.0, 2위=0.5, 3위=0.33 …)를 평균한다. top-1이 아니라 «놓쳤어도 얼마나
  가까이 놓쳤는가»까지 반영한다.
- **Recall@3**: 상위 3위 안에 의도된 관련 문서가 하나라도 있으면 적중으로 센다.

```
모델                          top-1 적중    MRR      Recall@3
nomic-embed-text              6/22 (27%)   0.4581   12/22 (55%)
bge-m3                       17/22 (77%)   0.8712   21/22 (95%)
bona/bge-m3-korean           17/22 (77%)   0.8674   21/22 (95%)
hf.co/mykor/KURE-v1-gguf     17/22 (77%)   0.8864   22/22 (100%)
qwen3-embedding:4b           18/22 (82%)   0.9091   22/22 (100%)  ← 채택
```

**세 모델의 top-1 동점은 진짜 동점이 아니었다.** `KURE-v1-gguf`가 MRR·Recall@3 모두에서
나머지 둘을 앞선다 — top-1에서 놓친 문서 대부분이 2~3위 안에는 정답을 두고 있었다는 뜻이다.
`bona/bge-m3-korean`(개인 업로드, 이름만 "한국어 특화")은 오히려 원본 `bge-m3`보다 근소하게
낮았다 — "한국어 특화"라는 이름값이 이 표본에서는 확인되지 않았다.

**채택 결정은 바뀌지 않는다.** `qwen3-embedding:4b`는 이 두 지표에서도 여전히 최고(MRR
최고, Recall@3는 `KURE-v1-gguf`와 공동 1위)다 — top-1 하나만 보고 내린 결정이 더 폭넓은
지표로도 뒤집히지 않았다.

**왜 `bge-m3`와 `KURE-v1-gguf`가 top-1에서 비슷했는가**: `KURE-v1-gguf`는 `bge-m3`를
한국어 질의-문서 200만 쌍으로 파인튜닝한 모델이다(출처: `nlpai-lab/KURE-v1`, 고려대
NLP랩). 코사인 절댓값은 다르지만(전 쌍 평균 절대차 0.0213) 22개 평가 대상 문서 중 20개에서
"1위 이웃"이 완전히 같았다(나머지 2개: `재무/회계정책.md`, `마케팅/소셜미디어전략.md`) —
파인튜닝이 유사도의 스케일은 재조정했지만 이 코퍼스에서의 상대 순위는 크게 바꾸지 못한
것으로 보인다.

**`KURE-v1-gguf`를 선택 가능한 대안으로 제공한다** — 기본값은 그대로 `qwen3-embedding:4b`
지만(전 지표 최고), `KURE-v1-gguf`가 근소한 차이(2위)로 뒤따르고 출처가 더 명확히
한국어 특화(고려대 NLP랩 원본)라 `docs/USAGE.md` §13.5에 권장 대안으로 문서화한다. 코드
변경은 없다 — `--embed-model`은 이미 임의 모델명을 받는다.

#### 나머지 3종 엣지

임베딩과 무관한 `TAGGED_WITH`·`CONTAINS_ENTITY`·`REFERENCES`는 이번 스모크의 측정 대상이
아니다(실행 H에서 이미 정상 동작 확인, issue #42도 이 셋은 "임베딩과 무관하며 정상 동작"
이라고 명시). 이번 스크립트는 `corpbrain scan`을 실행하지 않고 순수 임베딩 API만 호출하므로
그래프·위키 산출물 자체는 만들어지지 않았다 — 그 통합 확인은 다음에 실제로 채택 모델로
`scan`을 돌릴 때 자연히 재현된다.

#### 결론 — 실행 H 미결 사항 1번 해소

실행 H가 남긴 선택지 중 **"기본 임베딩 모델을 바꾼다"**를 택했다. `nomic-embed-text` →
`qwen3-embedding:4b`, `DEFAULT_SIMILARITY_THRESHOLD` `0.75` → `0.5717153219583704`로
`corpbrain/core/config.py`에 반영했다(§4.3). MRR·Recall@3로 재검증해도 같은 모델이 최고였다
(위 "보강" 절). 이는 스펙 §2가 이미 승인한 **파괴적 변경**이다 — 기존 벡터 인덱스가 모델
불일치로 막히며(기존 `PreconditionError` 메커니즘, 새 코드 없음), 안내는 `docs/USAGE.md`
§13.5에 있다. 2위 모델 `hf.co/mykor/KURE-v1-gguf`는 기본값으로 삼지는 않되 §13.5에 선택
가능한 대안으로 문서화했다.

#### 원인 — 고차수 엔티티 노드 (태그가 아니었다)

엣지 종류를 갈라 같은 스윕을 돌렸다(스펙 §4.8 6번이 `--expand-edges` 스윕을 명시한다).
기준선은 모두 MRR 0.2056 / Recall@3 0.4000. 아래 표와 그다음 `--top-k` 비교의 지표는
`docs/smoke/graph_decay_variants.json` 에 있으며, 그 파일의 `args` 를 스윕 스크립트에
그대로 주면 쿼리별 상세까지 재생성된다.

| `--expand-edges` | α ≤ 0.65 | α 0.70~0.85 | α=0.90 | α=0.95 |
|---|---|---|---|---|
| 기본 3종 | 기준선과 동일 | 0.2056 / 0.3667 | 0.1900 / 0.2333 | 0.2022 / 0.3000 |
| `CONTAINS_ENTITY` 단독 | 기준선과 동일 | 0.2056 / 0.3667 | 0.1900 / 0.2333 | 0.2022 / 0.3000 |
| `CONTAINS_ENTITY,REFERENCES` | 기준선과 동일 | 0.2056 / 0.3667 | 0.1900 / 0.2333 | 0.2022 / 0.3000 |
| `REFERENCES` 단독 | 기준선과 동일 | 기준선과 동일 | 0.1889 / 0.3333 | 0.2022 / 0.3333 |
| `TAGGED_WITH` 단독 | 기준선과 동일 | 기준선과 동일 | **0.2133** / 0.3333 | **0.2333** / 0.3333 |

**엔티티 단독이 기본 3종과 소수점까지 같다 — 손해 전부가 엔티티에서 나온다.** 스윕 전
가설은 「태그가 후보를 대량으로 만든다」였는데(#42가 관측한 태그 폭증), 실측이 그 가설을
뒤집었다.

그래프 DB에서 노드 차수를 직접 세면 이유가 드러난다.

```
가장 많은 문서를 잇는 노드
  Entity  인사팀      문서 10개   ← 23문서 중 43%
  Entity  연구개발팀   문서  6개
  Entity  마케팅팀    문서  4개
  Entity  재무팀      문서  4개
  Tag     예산        문서  3개   ← 태그 중 최대
  Tag     인사팀      문서  3개

2개 이상 문서를 잇는 노드 수:  Entity 14/49 · Tag 7/77
```

요약 모델이 뽑는 엔티티가 대부분 **부서명**이라 선택성이 없다. 시드가 `인사팀`을 가지면
그 엔티티를 가진 문서 10개가 한꺼번에 `시드 × α` 동점으로 후보에 들어와 코사인 2~5위의
정답을 밀어낸다. v0.7 스펙 §5가 「흔한 태그로 인한 동점 다발」을 알려진 특성으로 적어 둔
그 현상이며, **태그가 아니라 엔티티에서** 일어났다.

반대로 태그는 2개 이상 문서를 잇는 노드가 77개 중 7개뿐(최대 3문서)이라 후보를 거의
만들지 않는다. 그래서 `TAGGED_WITH` 단독만이 **전체 실험에서 기준선보다 MRR이 높은
설정을 낸다** — α=0.9에서 0.2133, α=0.95에서 0.2333(기준선 0.2056). 다만 쿼리 15개에서
+0.008 · +0.028 수준이고 Recall@3은 두 경우 모두 기준선(0.4000)보다 낮은 0.3333이라,
「태그 확산이 이롭다」고 말하기에는 표본이 얇다.

#### `--top-k` 특유의 현상이 아니다

23문서에서 `--top-k 5`는 코퍼스의 22%라 확산 몇 개만 들어와도 정답이 밀려난다. 이것이
top-k 선택 탓인지 갈랐다.

```
--top-k 3    기준선 MRR 0.1889 / R@3 0.4000  →  α=0.9  0.1333 / 0.2333
--top-k 5    기준선 MRR 0.2056 / R@3 0.4000  →  α=0.9  0.1900 / 0.2333
--top-k 10   기준선 MRR 0.2668 / R@3 0.4000  →  α=0.9  0.1872 / 0.3000
```

세 값 모두 α≤0.65에서 기준선과 동일하고 α≥0.70부터 단조 하락한다. 같은 방향이다.

#### 발견 — top-1 적중률은 구조적으로 α를 판별할 수 없다

확산 문서의 점수는 `max(자기 코사인, 시드 × α)`이고, 확산 문서는 정의상 코사인 top-k
밖이라 자기 코사인이 1위 코사인보다 작다. `α < 1`이므로 `시드 × α` 도 1위 코사인 미만이다.
따라서 **최종 1위는 언제나 코사인 1위 문서이며, α가 무엇이든 바뀌지 않는다.**

이 실측에서 top-1 적중률이 전 설정 0.00%로 고정된 것이 그 결과다(쿼리 세트를 일부러
어렵게 골랐기 때문에 0%이고, 쉬운 세트였다면 전 설정이 같은 높은 값으로 고정된다).
스펙 §4.8 4번의 1순위 키는 α 선택에 기여할 수 없고 실질 결정은 MRR → Recall@3가 한다.
**규칙 자체는 그대로 성립하므로(2·3순위 키가 받는다) 고치지 않고 사실만 기록한다.**

#### 쿼리 세트를 두 번 다시 쓴 기록

이 실측에서 가장 오래 걸린 것은 스윕이 아니라 쿼리 세트였다. 초안이 두 가지를 연달아
어겼고, 둘 다 측정을 무력화하는 종류였다.

1. **정답 라벨을 그래프 구조로 만들었다.** 「A가 B를 참조한다」를 보고 B를 A 쿼리의 정답에
   넣으면 "그래프가 정답을 잘 맞힌다"가 자명해져 측정이 자기충족적이 된다. 15개 전부를
   본문과 대조해 다시 라벨링했고, 답을 담지 않고 **가리키기만 하는 문서 8건**을 뺐다.
2. **쿼리를 문서 본문을 바꿔 말해 만들었다.** 어휘가 겹쳐 임베딩이 정답을 그냥 1위로
   올린다 — 재작성 전 세트는 **15개 전부 최상위 정답이 코사인 1위**였고, 확산은 1위를
   바꿀 수 없으므로 α가 아무것도 못 바꿨다. 문서 어휘를 피한 구어체 후보 51개를 새로 쓰고
   `--no-graph` 순위를 실측해 15개를 골랐다(정답이 top-5 밖인 A형 7 · 2~5위인 B형 8).

선별 기준은 **「정답이 코사인 1위가 아니다」(난이도)뿐**이고, 그래프를 켠 결과는 선별이
끝난 뒤에 봤다 — 「그래프가 잘 찾아내는 쿼리」로 고르면 스윕이 증명하려는 것을 전제하게
된다. 절차의 요점은 `docs/smoke/README.md` §6.5에 옮겨 적었다.

3. **사용자 검토에서 라벨 1건이 더 빠졌다** [2026-08-26 · 스펙 §4.8 2번]. 「외부 대행사가
   만든 산출물은 누가 확인하나」의 정답에서 `마케팅/소셜미디어전략.md`(코사인 2위)를 뺐다 —
   그 문서에는 「대행사」가 한 번도 나오지 않고, "콘텐츠 발행 전 최종 검수는 마케팅팀 채널
   담당자가 맡는다"는 대행사 산출물이 아니라 자기 채널 콘텐츠 전반을 말한다. 세션이 만든
   초안이 원칙 ①을 세 번째로 어긴 자리였고, **그 유형은 초안을 만든 쪽이 다시 읽어도 잘
   보이지 않는다** — §4.8이 이 단계만 사람에게 남긴 이유가 그것이다.
   - 이 쿼리는 정답 1개(파트너십제휴, 코사인 9위)의 순수 A형이 됐고, 위의 모든 수치는
     **정정 후 재측정한 값**이다. 기준선이 MRR 0.2389 → 0.2056, Recall@3 0.4333 → 0.4000
     으로 내려갔지만 **α 선택도 결론도 바뀌지 않았다** — 여전히 α=0.5가 뽑히고, 어떤 α도
     기준선을 넘지 못하며, 손해는 그대로 엔티티에서 나온다.
   - 라벨 근거를 적은 `note` 필드의 인용 3건이 따옴표 안인데도 원문 그대로가 아니었던 것도
     함께 고쳤다(내용은 맞았다). 15개 전 항목의 인용을 코퍼스 본문과 기계 대조해 불일치
     0건을 확인했다.

#### 결론 — α는 확정하고 기본 확산 엣지는 그대로 둔다

- `DEFAULT_GRAPH_DECAY = 0.5` 로 확정했다(`corpbrain/core/config.py`). 규칙이 낸 답을
  그대로 따르되, **그 값이 「이 코퍼스에서는 확산이 개입하지 않는 지점」이라는 사실**을
  스펙 §0 · `docs/USAGE.md` §6.3에 함께 적었다. #42가 유사도 임계치의 임베딩 모델
  종속성을 §13.5에 적어 둔 것과 같은 방식이다.
- **기본 `--expand-edges`는 바꾸지 않는다.** 진단된 원인은 `CONTAINS_ENTITY`지만 근거가
  코퍼스 1개·쿼리 15개이고, 기본값 변경은 스펙 §4.2의 결정을 뒤집는 일이라 후속 이슈로
  넘긴다. 우회법(`--expand-edges TAGGED_WITH,REFERENCES`)은 `docs/USAGE.md` §6.3에 있다.
- **기능을 되돌리지 않는다.** 확산은 설계대로 작동했고(위 「확산은 작동했다」 절), 이
  코퍼스의 엔티티 품질에서 손해가 났을 뿐이다. `--graph-decay` 로 언제든 올릴 수 있고,
  엔티티가 선택적인 코퍼스에서는 다른 결과가 나올 수 있다.
- **남은 후속 과제**: ① 엔티티 추출이 부서명으로 쏠리는 문제(요약 프롬프트 조정 또는
  고차수 노드 감쇠) ② `개발/README.md`처럼 기본 모델이 요약하지 못하는 문서의 처리
  ③ 더 큰 코퍼스에서의 재측정.

```
중단됨 — 요청에 따라 스캔을 멈췄습니다. 그때까지 생성된 위키는 그대로 남습니다.
  - 그래프 미반영 — 다시 스캔하면 반영됩니다.
```

**24.7초는 진행 중이던 문서의 요약 호출이 끝나기를 기다린 시간**이다 — 「진행 중인 문서를
마친 뒤 멈춘다」는 계약 그대로이며, 스펙이 경계한 최악(소켓 타임아웃 300초)의 1/12이다.
다만 버튼을 누르고 25초를 기다리는 것은 짧지 않으므로, 화면이 그동안 「멈추는 중…」으로
바뀌어 있는 것이 필수라는 점이 실측으로 확인됐다.

#### K1 — 진행 표시는 그래프 단계까지 이어진다. 다만 **최대 47초의 무음 구간**이 있다

```
SSE 프레임                167건
프레임 간격 중앙값          0.0초
최대 무음 구간             47.1초       ← 문서 1건의 요약이 도는 동안
그래프 단계 프레임          25건
그래프 구간 최대 무음        0.4초       ← T4가 겨냥한 그 구간
순서: snapshot → run_started → file_started → file_skipped → file_stage
      → model_loading → file_generated → graph_started → related_injected
      → graph_finished → run_finished
결과: 22 생성 / 2 스킵 (up_to_date 1 · LLM JSON 파싱 실패 1)
```

- **T4가 고치려던 문제는 실제로 사라졌다.** 마지막 `file_generated` 이후 `RunFinished`까지가
  통짜 침묵이던 구간에 이제 25개 프레임이 들어오고 그 안의 최대 간격이 **0.4초**다.
- **남은 47.1초 무음은 파일 루프 안쪽**이다. `file_stage`(요약 시작)와 `file_generated` 사이에
  이벤트가 없고, 그 사이가 곧 LLM 호출 시간이다. 화면은 그동안 같은 파일 이름과 같은 카운터를
  보여 준다 — **K4(사용자 몫)가 판정할 자리가 정확히 여기다.** 토큰 단위 진행 이벤트를 더하는
  것은 이 슬라이스의 범위 밖이므로(§4.7은 이벤트 11종으로 못박았다), **화면 쪽에서 줄였다** —
  진행 카드가 마지막 프레임 이후 흐른 시간을 더해 `경과 mm:ss · ETA mm:ss · <단계>` 를 1초마다
  다시 그린다. 서버 값을 재계산하는 것이 아니라 **이미 받은 값에서 시간만 흘리는** 표시이며,
  다음 프레임이 오면 그 값으로 덮인다. 어휘(`경과`·`ETA`·단계 이름)는 CLI
  `render_status_line()` 이 쓰는 것을 그대로 쓴다. 그럼에도 **문서 단위 진행률은 여전히 47초
  동안 움직이지 않으므로**, 이것으로 충분한지는 K4 가 판정한다.
- `LLM JSON 파싱 실패` 1건은 v0.7 실행 J가 이미 기록한 「기본 모델이 요약하지 못하는 문서」와
  같은 건이다(`docs/SMOKE.md` 실행 J 「남은 후속 과제」 ②). 개별 파일 실패가 전체 실패로
  위장하지 않는다는 v0.1 §5 방침대로 나머지 22건은 정상 처리됐다.

#### K3 — 실제 규모에서 서버는 문제없다. 읽히는지는 눈이 판정한다

```
노드 149  (Document 23 · Entity 49 · Tag 77)
엣지 210  (TAGGED_WITH 86 · CONTAINS_ENTITY 81 · REFERENCES 37 · SEMANTICALLY_SIMILAR 6)
GET /api/graph   22ms · 60.0KB
```

- **`iter_edges()` 한 번으로 전 엣지를 받는 것이 실제로 싸다** — 210 엣지에 22ms다. 전 노드에
  `neighbors()`를 돌렸다면 149회의 쿼리와 중복 제거가 필요했다(§4.3.1이 배제한 그 방식).
- **§5가 경계한 「프로토타입의 자작 canvas 물리가 17노드로만 검증됐다」는 이 구현에 해당하지
  않는다.** 물리 시뮬레이션을 쓰지 않고 종류별 동심원으로 결정적으로 배치하므로 149노드에서도
  프레임 예산 문제가 없다. 남는 것은 **읽히는가**이며 그것이 K5(사용자 몫)다.
- 엔티티 49개·태그 77개는 v0.7 실행 J가 진단한 「엔티티가 부서명으로 쏠린다」와 같은 분포다.
  그래프 화면은 그 분포를 있는 그대로 보여 준다 — 상한·필터를 두지 않기로 한 결정(§5 ·
  issue #58)의 실물이 이 숫자다.

#### 세션이 함께 확인한 것 (자동 테스트가 덮지 않는 배선)

같은 서버에 붙어 전 엔드포인트를 한 번씩 훑었다 — 계량 200, 진행 중 두 번째 스캔 **409**,
`Origin` 없는 POST **403**, 폴더 없는 계량 **400**, 대시보드·그래프·위키 트리(`source=graph`)·
위키 상세(front-matter 5키 · 관련 문서 해석)·검색·설정(PII 7종) 전부 200.

#### 사용자 몫 3항목 — **확인됨** [2026-08-28]

기계로는 판정할 수 없어 **눈으로만** 확인된다. 위 K1·K3의 숫자가 그 판단의 재료였다.
사용자가 실제 브라우저에서 셋을 모두 확인했고, **되돌릴 만한 결함은 보고되지 않았다.**

- **K6** — 클릭 가능한 요소가 전부 키보드로 닿고 포커스 링이 보이는가. 사이드바·폼·트리 항목·
