# 벡터 인덱스 설계

## 목표

문서마다 임베딩 벡터 하나를 만들어 두고, 자연어 질의와 코사인 유사도로 비교해 가까운
문서를 찾는다. 연구개발팀이 외부 의존성 없이 시작할 수 있는 가장 단순한 형태를 골랐다.

## 저장소

표준 라이브러리 SQLite만 쓴다. `vectors` 테이블 하나에 문서 식별자, 벡터 JSON,
메타데이터 JSON을 담고, `meta` 테이블에 이 인덱스를 만든 임베딩 모델 이름을 기록한다.

모델 이름을 기록하는 이유는 혼입을 막기 위해서다. 서로 다른 모델로 만든 벡터는 차원도
의미 공간도 달라 비교가 무의미하다. 인덱스가 이미 다른 모델로 만들어져 있으면 스캔을
거부하고, 검색은 인덱스에 적힌 모델을 강제로 쓴다.

## 임베딩 모델

`nomic-embed-text`를 기본으로 한다. 로컬 Ollama에서 돌고 한국어 문서에서도 쓸 만한
결과를 낸다. 모델이 설치돼 있지 않으면 스캔 전에 확인해 알린다.

## 유사도 계산

코사인 유사도를 순수 파이썬으로 계산한다. 스캔 상한이 기본 50건이라 전수 비교로도
충분하다. 외부 벡터 검색 라이브러리를 붙이는 것은 규모가 커진 뒤에 다시 판단한다.

## 알려진 한계

- 문서를 청크로 나누지 않는다. 긴 문서는 앞부분만 요약 입력이 되고 그 요약에서 벡터를
  만들기 때문에, 문서 뒷부분의 내용은 검색에 잡히지 않는다.
- 인덱스 스키마가 바뀌면 자동으로 옮기지 않는다. 파일을 지우고 다시 만들도록 안내한다.
- 원격 저장소나 여러 사용자의 동시 접근은 다루지 않는다.
