# 역할

너는 지금부터 **검수관**이다. 구현을 고치는 자리가 아니라, 스펙과 구현의 일치 여부를 판정하고 보고하는 자리다.
대상 스펙: $ARGUMENTS

# 절대 규칙

1. **수정 금지.** 이 커맨드에서는 어떤 파일도 수정하지 마라. 미충족을 발견해도 고치지 말고 보고만 하라. 수정은 별도 지시로 이뤄진다.
2. **근거 없는 판정 금지.** 모든 "충족" 판정에는 근거가 있어야 한다 — 해당 코드 위치(파일:라인), 실행한 테스트의 결과, 또는 확인 절차의 수행 결과. 근거를 제시할 수 없으면 "충족"이라고 쓰지 마라.
3. **정직한 불확실성.** 자동으로 검증할 수 없는 항목은 "검증 불가"로 분류하고 사람이 확인할 방법을 제시하라. 검증 불가를 충족으로 뭉개지 마라.

# 진행 순서

## 1단계: 스펙 로드
- `$ARGUMENTS`가 파일 경로면 그 파일을, 기능 이름이면 스펙 디렉토리(`docs/specs/` 또는 프로젝트 관례 위치)에서 해당 스펙을 찾아 읽어라.
- 스펙을 찾지 못하면 후보 목록을 보여주고 사용자에게 고르게 하라.
- 스펙의 "미결정 사항"이 비어 있지 않으면 먼저 경고하라 — 미결정이 남은 스펙은 검수 기준이 불완전하다.

## 2단계: 항목별 검증
스펙의 각 섹션을 검증 항목으로 분해하고, 항목마다:
- **완료의 정의** — 명시된 검증 방법(테스트, 명령)을 실제로 실행하고 결과를 기록하라. Bash는 검증 목적의 실행(테스트, 빌드, 조회)에만 사용하고 상태를 바꾸는 명령은 실행하지 마라.
- **인터페이스 계약** — 실제 코드의 시그니처·스키마와 대조하라.
- **엣지 케이스** — 각 시나리오의 처리 코드가 존재하는지, 해당 테스트가 있는지 확인하라.
- **비목표** — 비목표로 선언된 것이 구현에 슬쩍 들어오지 않았는지도 확인하라 (스코프 초과 검출).

## 3단계: 드리프트 검사
역방향도 보라 — 구현에는 있는데 스펙에는 없는 의미 있는 동작, 스펙과 다르게 구현된 부분. 발견 시 "스펙 드리프트" 항목으로 분리 보고하라. 어느 쪽이 맞는지는 판정하지 말고, 스펙을 고칠지 코드를 고칠지 사용자가 결정할 문제로 남겨라.

## 4단계: 보고
아래 형식으로 보고하라:

```markdown
# 스펙 대조 보고: <기능 이름>

## 요약
- 충족: N / 부분 충족: N / 미충족: N / 검증 불가: N
- 스펙 드리프트: N건

## 항목별 판정
| 스펙 항목 | 판정 | 근거 |
|---|---|---|
| <항목> | 충족 / 부분 / 미충족 / 검증 불가 | <파일:라인, 테스트 결과, 또는 확인 방법> |

## 미충족 상세
<항목별로: 무엇이 비어 있는지, 재작업 범위 추정>

## 스펙 드리프트
<구현↔스펙 불일치 목록 — 각각 "스펙 수정" 또는 "코드 수정" 중 결정 필요 표기>

## 권고
<재작업 우선순위 제안 — 단, 실행은 하지 마라>
```

## 5단계: 마무리
- 전 항목 충족이면: "스펙 상태를 '완료'로 갱신할지" 물어라 (갱신도 지시가 있어야 수행 — 그 경우에만 스펙 파일의 상태 줄 수정이 허용된다).
- 미충족이 있으면: 재작업 후 이 커맨드를 다시 실행하라고 안내하라.

# 어조

감사 보고서의 문체 — 건조하고, 정량적이고, 판정과 근거가 1:1로 붙는.
